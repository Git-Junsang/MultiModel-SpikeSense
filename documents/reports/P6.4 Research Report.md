# P6.4 보고서: USB mic demo(스피커 → 공기 → mic → FPGA)

작성일: 2026-11-16

P5.4에서 mic 2개와 가상 트랙 1,022개로 1,024트랙 실행을 확인했다. 이번에는 demo 실행 파일 `software/host/demo.py`를 만들고, Bluetooth 스피커 2대로 기계 소리를 틀어 mic로 받은 판정이 들려준 소리와 맞는지 확인했다. 보드는 PCIe slot에서 떼어 12 V 어댑터로 단독 구동했다. 수치는 따로 적지 않으면 보드 실측이다.

## 1. 요약

### 1.1 환경

| 항목 | 값 |
|---|---|
| Host | 라즈베리파이 5, Debian 13. 계산 thread CPU 3 고정 |
| 보드 | P5.2 최종 bitstream을 QSPI에서 부팅(PCIe slot 없이 12 V 어댑터), Pi `eth0`와 1 Gb/s 직결 |
| mic | Generalplus USB mic 2개(`Microphone` 트랙 0, `Microphone_1` 트랙 1), 48 kHz mono |
| 스피커 | Bluetooth 2대. Anker PowerConf(트랙 0, 통화용 HFP·mSBC 16 kHz), ABKO BSL110(트랙 1, A2DP·SBC). 50 cm 간격, mic는 스피커에 붙임 |
| 트랙 | 트랙 0 pump_id04, 트랙 1 slider_id04, 트랙 2–1,023은 가상 트랙(모델 i % 40) |
| 들려준 소리 | 트랙 0·1은 5 s마다 (정상, 이상) → (정상, 정상) → (이상, 이상) 반복. 가상 트랙은 90% 정상, 10% 이상(§3.4) |

### 1.2 실험과 결과

- 스피커 지연 보정(§3.1): 재생 시작부터 mic 도착까지 Anker 132–149 ms(HFP), BSL110 300–329 ms. 실행마다 잡음 burst로 다시 잰다.
- 공기 중 판정(§3.2): 음량 보정 뒤 193 s에서 세트 안 판정이 들려준 소리와 맞았다(트랙 0 151/151, 트랙 1 150/150). 보정 전 트랙 1은 136/149였다. 촬영 실행 두 번(40 s, 73 s)에서도 170/170이었다. 판정이 쉬운 파일 한 쌍을 반복해 들려준 경로 확인이므로 이 일치 수를 정확도로 쓰지 않는다.
- 재생 실패(§3.3): PipeWire가 스피커를 가끔 찾지 못해 재생이 조용히 실패했다. 트랙마다 다시 트는 구조로 고친 뒤 실패가 판정에 영향을 주지 않았다.
- 정확도(§3.4): end-to-end 정답률은 92.9%다. mic 트랙과 가상 트랙을 나누지 않은 1,024트랙 값이다. 가상 트랙마다 다른 위상으로 소리를 듣게 바꾼 최종 시험에서 가상 트랙 1,022개의 화면 정답률이 평균 92.9%(90.0–94.6%)였고, 같은 시험의 트랙 0·1(52/52, 53/53)을 더해도 92.9%다. 같은 소리의 Python 기준 정답률은 정상 92.5%, 이상 95.6%다.

| 시험 | 길이 | 트랙 0 | 트랙 1 | 추론 요청 손실·`LATE` | response time 최대 |
|---|---:|---|---|---|---:|
| Anker만 (A2DP) | 198 s | 153/153 | — | 0 / 6,310,812 | 6.89 ms |
| 두 대, BSL110 음량 0.73 | 193 s | 151/151 | 136/149 | 0 / 6,145,024 | 7.42 ms |
| 두 대, 음량 1.0 | 193 s | 151/151 | 150/150 | 0 / 6,143,975 | 7.24 ms |
| 트랙별 재생 재시도 | 약 50 s | 41/41 | 39/39 | 미확인 | 미확인 |
| 최종(가상 트랙 위상차) | 68 s | 52/52 | 53/53 | 0 / 2,129,845 | 6.27 ms |
| 촬영 실행 1 | 40 s | 29/29 | 31/31 | 0 / 1,230,498 | 5.74 ms |
| 촬영 실행 2 | 73 s | 53/53 | 57/57 | 0 / 2,295,884 | 7.47 ms |

판정 수는 세트 안 판정(소리 1.024 s가 한 세트 안에 다 든 판정)만 셌다. 길이는 mmss_host `audio_s`다. 트랙별 재생 재시도 시험의 `run.log`는 다음 실행이 덮어써 summary가 없다. 길이는 판정 기록(49.6 s)으로 적었다. 촬영 실행 1의 판정 기록은 촬영 실행 2가 덮어썼다. 판정 수는 덮어쓰기 전에 Pi에서 센 값이다. 촬영 실행에서는 가상 트랙 정답률을 기록하지 않았다(demo.py는 트랙 0·1 판정만 파일로 남긴다).

### 1.3 결론

1. 스피커 → 공기 → mic → FPGA 경로가 가상 트랙과 함께 1,024트랙으로 동작한다. end-to-end 정답률은 mic와 가상 트랙을 나누지 않고 92.9%로 쓴다. mic 트랙에서 세트 안 판정이 모두 맞은 것은 판정이 쉬운 파일을 고른 경로 확인이라 mic 정확도(100%)로 쓰지 않는다.
2. 트랙 1이 놓친 것은 mic에 들어간 소리가 작아서였다. BSL110 음량을 올려 mic rms를 0.04에서 0.113으로 키우자 이상 판정 85/98이 98/98이 됐다.
3. 스피커 사이 간섭은 판정에 영향이 없었다. 반대쪽 스피커 소리는 방 소음 수준이거나 자기 스피커보다 약 14 dB 작다.
4. 1,024트랙 처리는 mic·공기 경로와 상관없이 손실 0이고, response time 최대는 7.47 ms 이하다.

### 1.4 한계와 남은 결정

- 트랙마다 정상·이상 파일 1개씩을 13바퀴 반복했고, 파일은 Python 기준 판정이 쉬운 것으로 골랐다. 경로 확인이며 성능 근거가 아니다. 성능은 P5.3 평가 파일 전체로 본다.
- mic 입력에서 FPGA 출력을 snn_int8과 bit 비교하지 않았다(sudo가 필요하다).
- 가상 트랙을 메모리에 올리는 Host program으로는 90 s만 돌렸다. 300 s 시험은 하지 않았다.

## 2. 구성

### 2.1 demo.py

| 명령 | 하는 일 |
|---|---|
| `prep`(개발 서버) | 스피커 소리 `speaker0·1.wav`, 가상 트랙 `virtual.wav`(160채널 50 s)와 정답 `virtual_labels.json`, map을 만든다. 스피커 소리를 세트 순서대로 3바퀴 이어 넣은 Python 기준 판정이 세트 안에서 모두 맞는지 확인한다 |
| `run`(Pi) | `stop` → `setup` → 스피커마다 지연 보정 → `mmss_host run --mic ... --in virtual.wav` → 재생과 화면 → Ctrl-C에서 `stop` |

화면은 0.2 s마다 같은 자리에 다시 그린다(영문). 트랙 0·1은 줄마다 장비, 들려주는 소리, 추론, 맞음·틀림을 보인다. 가상 트랙은 한 칸이 한 트랙이고 `o` 정상 추론, `x` 이상 추론, 초록 맞음, 빨강 틀림, `·` 대기다.

### 2.2 리셋 규칙

판정 하나는 소리 1.024 s(frame 31개)로 정한다. 판정 줄을 받은 시각 t의 소리를 [t − 1.074 s, t]로 본다(여유 0.05 s). 세트 시작은 재생 시작 + 잰 지연 + 5 s × 세트 번호다. 소리가 한 세트 안에 다 든 판정만 보이고, 세트가 바뀌면 그 트랙 판정을 지운다. 그래서 세트 시작 뒤 1.2–2.0 s 동안 `waiting`이다. 가상 트랙도 판정의 소리부터 지금까지 정상↔이상이 바뀌지 않은 판정만 보인다(경계 ± 0.3 s 제외).

mmss_host는 정적 링크라 stdout이 pipe면 4 KiB씩 모여 늦게 나온다. demo.py는 pty로 받아 판정을 줄마다 받는다.

## 3. 결과

### 3.1 스피커 지연 보정과 간섭

`run`은 mmss_host를 띄우기 전에 스피커마다 0.5 s 잡음 burst를 재생하고 그 트랙 mic로 녹음해 정규화 상관 최대에서 지연을 잰다. Mic 샘플 0의 도착 시각은 읽을 때마다 (읽은 시각 − 받은 샘플 수 / 48 kHz)의 최솟값으로 구한다.

| 항목 | 처음 | 고친 뒤 |
|---|---|---|
| 첫 재생 | 쉬던 Bluetooth 스피커는 첫 소리가 늦어 3 s 녹음 창을 넘겼다(상관 0.01) | 3번 재고 첫 번은 버린다 |
| burst 대역 | 24 kHz까지 퍼진 잡음은 HFP(8 kHz 이하)를 지나면 상관 0.04 | 6 kHz 아래로 거른 잡음: 상관 0.14–0.38 |

| 스피커 | 지연(한 실행 안 2번) | 자기 mic rms | 반대쪽 mic rms |
|---|---|---|---|
| Anker, HFP | 132–149 ms | 0.078 | 0.014 |
| Anker, A2DP(혼자 연결) | 290–333 ms | 0.06 | 0.013 |
| BSL110, A2DP | 300–329 ms | 0.113 | 0.020 |

방 소음 rms는 0.012다. 음량은 PipeWire 출력 1.0이다(Anker는 HFP에서 1.0이 최대 0.078). 녹음 최댓값은 0.54–0.59(최대치 1.0)이고 잘린 샘플은 0%다.

### 3.2 공기 중 판정

Anker만 연결했을 때 트랙 0은 세트 안 판정 153/153을 맞혔다. 정상의 P(이상) 평균은 0.00, 이상은 1.00이다. 시험 중 사람이 움직인 소리가 섞였지만 틀린 판정은 없었다.

두 대를 연결하고 BSL110 음량이 0.73일 때 트랙 1은 정상 51/51, 이상 85/98이었다. 놓친 이상 판정은 매 바퀴 이상 세트의 2–4번째 판정(slider 이상 파일의 2.5–4.5 s 구간)에 몰렸다. software에서는 이 구간도 여유 8.27 이상으로 맞았다. 음량을 1.0으로 올려 mic rms를 0.04에서 0.113으로 키우자 150/150이 됐다.

### 3.3 재생 실패와 고친 것

| 문제 | 증상 | 고친 것 |
|---|---|---|
| 두 번째 A2DP | BlueZ `Unable to select SEP`. 나중에 붙는 스피커는 연결이 안 되거나 HFP로 붙는다 | BSL110을 먼저 연결한다. Anker는 HFP로 쓴다(§3.2의 결과는 이 상태) |
| 끊긴 스피커 | `pw-play --target`의 node가 없으면 기본 출력으로 재생돼 다른 스피커에서 소리가 났다 | `node.dont-fallback = true`. 끊긴 트랙은 재생하지 않고 화면에 `speaker lost` |
| WirePlumber가 node를 못 찾음 | 있는 node도 가끔 `defined target not found`. 재생이 조용히 실패해 트랙 1이 반대쪽 pump 소리만 들었다(재시도 없을 때 16/41) | 0.3 s 안에 끝나면 다시 튼다(37/45). 그보다 늦게 실패한 바퀴가 남아, 트랙마다 따로 15 s 바퀴를 돌며 끝나면 바로 다시 틀게 했다(39/39, 실패 10번 모두 복구) |
| Ctrl-C 두 번 | 정리 중에 끊겨 `mmss_host stop`을 건너뛸 수 있다 | 정리 중에는 SIGINT를 무시한다 |

### 3.4 가상 트랙

| 구성 | 소리 | 화면 정답률 | 문제 |
|---|---|---|---|
| P5.4 | fan_id01 정상 파일 하나를 모든 모델에 | 의미 없음 | 모델과 장비가 다르다 |
| 40채널 | 모델마다 첫 정상 10 s + 첫 이상 10 s | 78–95%(Python 84%) | 모든 트랙이 10 s마다 함께 바뀐다 |
| 160채널 | 채널마다 정상 45 s + 이상 5 s(위치는 채널마다), 판정 여유가 큰 파일 | 86–98%(Python 92.5%·95.6%) | 같은 채널 트랙 6–7개가 같은 소리를 동시에 들어 격자 무늬가 320트랙마다 반복 |
| 160채널 + 위상차 | 위와 같다. mmss_host가 트랙 i를 (i − 2) × 104,729샘플 늦춰 읽는다 | 평균 92.9%(90.0–94.6%) | 없음. 같은 줄 쌍 0, 이상 재생 86–119트랙 |

위상차는 `run.c`가 mic + wav 입력에서 wav 전체(256 MB)를 채널마다 이어 붙여 메모리에 올려 구현했다(06 §2). 섞인 채로 두면 frame마다 320 B씩 건너뛰어 읽어 메모리 접근이 늘어난다. 파일 입력 경로는 `make check` 21항목이 그대로 통과했다. 화면 정답은 가상 트랙 샘플 0을 mmss_host 시작 + 0.1 s로 어림한다. 정답률이 Python 예상과 맞아 이 어림은 경계 여유 0.3 s 안이다.

판정은 모든 트랙이 0.992 s마다 31 ms 안에 끝난다(offset 40개가 32 ms 안). 화면 갱신이 트랙마다 다른 것은 소리가 바뀌는 시각이 트랙마다 달라서다.

## 5. 실행

```bash
# 개발 서버: 소리 파일과 map
python3 software/host/demo.py prep
make -C software/host && make -C software/host check
# Pi 작업 폴더(~/mmss_demo, 저장소 root와 같은 상대 경로)에 mmss_host, demo.py, software/dataset/demo/, models_l64, pi_group.csv를 두고
python3 software/host/demo.py run --speaker bluez_output.90_BF_D9_64_44_13.1 --speaker bluez_output.DE_0D_A5_2C_78_37.1
```

원자료는 `hardware/board_test/p64_meas/result/mic_judge_<시험>.csv`다(트랙 0·1 판정마다 받은 시각, 판정, P(이상), 재생 중인 소리, 세트 안 판정인지). 시험 이름은 `anker_only`, `2spk_vol073`, `2spk_vol100`, `2spk_noretry`, `2spk_retry03s`, `2spk_pertrack`, `virt160`, `virt160_phase`, `film2`다.
