# P5.3 보고서: 목표 부하에서 음원부터 판정까지

작성일: 2026-10-25

Host program `mmss_host`(P4.8)를 sub1에서 돌려, 40개 모델의 평가 파일 12,671개를 1,024트랙 실시간으로 보드에 보냈다. Host가 음원에서 mel 특징을 만들어 보내면 FPGA가 추론해 출력 membrane potential을 돌려주고, Host가 판정한다. FPGA 출력이 software와 bit 단위로 같은지, 파일 단위 AUC, response time과 처리량을 쟀다. Host는 임시로 sub1(Xeon)이고 라즈베리파이 5가 아니다.

## 1. 요약

### 1.1 환경

| 구분 | 내용 |
|---|---|
| Host | sub1(Xeon W-2255). `mmss_host`를 x86으로 빌드(gcc `-O2 -march=native`, 정적 링크), 계산 thread를 CPU 3에 고정. 채널 상한만 고쳤다(§4) |
| 보드 | P5.2 최종 bitstream(수신 tap 8, 송신 −80단계), `eno1` 직결 |
| 입력 | 40개 모델의 평가 파일 12,671개(정상 7,858, 이상 4,813). 학습에 쓰지 않은 test 파일이다(02 §3). 파일 수에 비례해 모델마다 12–81트랙, 모두 1,024트랙(DDR3 트랙 256) |
| 실행 | 1,024채널 raw 166.7 s를 실시간 속도(`--pace`)로 읽는다. setup의 PNU 표는 Xeon 모델 그룹 지연 표(P3.25)와 jitter 800 µs |
| 판정 | 판정 주기 31 frame마다 softmax P(이상). 파일 점수 = 파일 안 주기 점수 평균. 파일 단위 ROC-AUC(02 §3, §5) |
| 기준 | ① Host가 보낸 입력(tcpdump)에 `snn_int8.forward`(12 bit 저장) ② Python 전체 경로(`p325_mel_load.mel_db` + seg 정규화 + `quantize_input` → `snn_int8`) ③ software 평가(`realtime_norm.py`): 학습 특징(파일 정규화), seg 정규화 |

### 1.2 결과

| 질문 | 답 |
|---|---|
| FPGA 출력 | 평가에 쓴 판정 주기 129,755개(추론 4,022,405개)의 out0·out1이 ①과 모두 같다 |
| Host 특징 | 값 160,896,200개 중 858개가 Python 특징과 1 다르다. 추론 요청 858개에서 1개씩이다 |
| Host 판정 | 판정 170,970개가 보드 출력으로 Python이 구한 판정과 같다 |
| AUC 평균(40개 모델) | 보드 0.93825, Python 전체 경로 0.93825, software seg 정규화 0.94007, 학습 특징 0.95537 |
| AUC 0.9 이상 | 보드 33/40, 학습 특징 35/40 |
| 처리량 | 166.7 s 동안 추론 5,330,965개(초당 31,988개). FPGA가 모두 받고 모두 냈다(`REQ_DROP` 0) |
| response time(Host 수신 − `t_host`) | 중앙값 3.76 ms, p99 11.5 ms, 최대 13.5 ms. 32 ms를 넘은 결과는 0 |
| FPGA 시간(`t_done − t_in`) | 중앙값 104 µs, p99 412 µs, 최대 477 µs |
| 연산 | 추론당 492 cycle(4.9 µs). 연산이 바쁜 시간 15.7%, weight를 기다리며 멈춘 시간 5.1% |
| DDR3 | 추론당 5.54 KiB(weight 5,143 B + membrane potential 535 B), 182 MB/s. Batch의 93%가 weight를 적재했다 |
| 결과 손실 | 38개(100만 개당 7개). FPGA는 보냈고 Host가 받지 못했다. 그 판정 주기 38개는 판정하지 않았다 |

### 1.3 결론

1. 보드 경로의 정확도는 같은 입력을 쓴 software와 같다. FPGA 출력이 bit 단위로 같다. 남은 AUC 차(평균 3 × 10⁻⁶, 모델별 최대 0.00011)는 Host C 특징과 Python 특징의 반올림 차이 858개에서 온다.
2. 학습 평가(0.9554)보다 0.017 낮은 것은 hardware 때문이 아니라 실시간 seg 정규화 때문이다. software에서 같은 정규화를 쓰면 0.9401이다(−0.015, P3.21과 같다). 나머지 −0.0018은 Host의 frame 경계(모델 offset, 가운데 padding 없음)가 학습 특징과 달라서다. ToyCar 3개가 0.14–0.16 떨어진다. 실시간 정규화를 정하고 다시 학습할 문제다(P2.9). 뒤에 재학습 없이 정규화만 바꿔 같은 입력의 보드 AUC가 0.9531이 되었다([P2.9 보고서](<P2.9 Research Report.md>)).
3. 목표 부하(1,024트랙 실시간)에서 deadline 32 ms를 넘은 결과는 없다. Response time의 대부분은 Host 쪽 대기다(block 도착 → 계산 시작 중앙값 2.66 ms). FPGA 안 시간은 0.5 ms 이하다.

## 2. 방법

### 2.1 입력 배치

트랙마다 channel 하나를 주고 평가 파일을 차례로 싣는다. 파일마다 판정 주기 12개 칸(12 × 31 × 512 = 190,464샘플)을 준다. 학습 평가와 같은 수의 앞 주기(10 s 파일은 10개, ToyCar의 11 s 파일은 11개)만 쓴다. 이 주기들의 frame은 모두 파일 안에 든다. 나머지 주기는 다음 칸과 걸치므로 버린다. 모델 m의 frame k는 샘플 [O_m + 512k, O_m + 512k + 1,024)이고 O_m은 Host와 같은 offset이다. 판정 주기마다 `RESET_STATE`와 seg 정규화가 새로 시작하므로 주기끼리 영향이 없다.

1,024채널 166.7 s는 5.09 GiB다. WAV 머리말의 데이터 크기(32 bit)를 넘을 수 있어 머리말 없는 raw로 넘겼다.

### 2.2 실행

```text
sub1  bitstream(JTAG) → mmss_host setup(모델 image 40개 적재·확인 1.2 s, 설정, PNU 표, SOFT_RESET, RUN)
      → tcpdump(Host → FPGA 추론 요청) + mmss_host run --pace --log → mmss_host stop(counter)
main  p52_acc.py ref: 보낸 입력·보드 결과·Host 판정을 기준 ①②③과 비교
```

## 3. 결과

### 3.1 정확도

| 구분 | AUC 평균 | 0.9 이상 | 보드와 차이(평균, 최소~최대) |
|---|---:|---:|---|
| 보드(Host 특징 → FPGA → Host 판정) | 0.93825 | 33 | |
| Python 전체 경로 | 0.93825 | 33 | 0.000003, −0.00011–0.00011 |
| software, seg 정규화 | 0.94007 | 33 | −0.0018, −0.037~+0.018 |
| software, 학습 특징(파일 정규화) | 0.95537 | 35 | −0.017, −0.162~+0.096 |

| pump_id00 | 0.888 | 0.804 | 0.798 |

### 3.2 속도

| 구간 | 중앙값 | p99 | 최대 |
|---|---:|---:|---:|
| block 도착(`t_host`) → Host 계산 시작 | 2.66 ms | 10.7 ms | 12.9 ms |
| Host 계산(모델 그룹, 평균 25.6개) | 0.23 ms | 1.47 ms | 2.29 ms |
| Host 계산 끝 → 송신 끝 | 5.5 µs | 23 µs | 75 µs |
| FPGA 대기(`t_start − t_in`) | 99 µs | 407 µs | 471 µs |
| FPGA(`t_done − t_in`) | 104 µs | 412 µs | 477 µs |
| 전체(Host 수신 − `t_host`) | 3.76 ms | 11.5 ms | 13.5 ms |

- FPGA 대기는 대부분 같은 모델 추론 요청이 다 모일 때까지와 weight 적재다. 결과 기준 평균 batch는 33.4개다.
- 40개 모델이 32 ms마다 offset 순서로 한 번씩 오고 entry가 4개라, 같은 모델이 다음 주기까지 cache에 남지 않는다. 그래서 batch마다 weight를 적재한다. 적재 1,249번/s, 182 MB/s는 DDR3 실측 대역(P3)보다 훨씬 작다.
- Host는 4 ms block(64샘플) 단위로 읽고, 그 안에서 끝난 모델 그룹을 차례로 계산한다. 계산이 다음 block까지 끝나지 않은 횟수(`overrun`)가 19,179번(block의 46%)이었다. 계산 자체(0.23 ms)보다 계산 시작이 늦는 원인은 따로 보지 않았다.

### 3.3 결과 손실

빠진 결과 38개 중 36개는 같은 frame에서 이어진 트랙 3개씩 12번이다(예: 트랙 88·89·90의 frame 616). 나머지 2개는 하나씩이다. FPGA counter로는 모두 보냈다(`RES_OUT` = `REQ_IN`). Host의 UDP 수신 buffer 오류는 0이다. Host NIC의 `rx_errors` 17은 bitstream을 쓸 때 링크가 다시 올라오며 생긴 것이고, 실행 중에는 늘지 않는다. Host → FPGA 추론 요청은 하나도 빠지지 않았다. 원인은 뒤에 Host NIC(sub1의 Intel I219)의 절전으로 확인했다. 링크가 50 µs 넘게 조용하다가 frame이 다시 오면 드물게 약 15 µs 분량을 오류 표시 없이 잃는다([결과 손실 보고서](<P5.3 Result Loss Research Report.md>)).

## 4. 검증과 한계

- Host는 sub1(Xeon)이다. Response time의 Host 부분은 라즈베리파이 5와 다르다. 라즈베리파이 5에서는 1,024트랙 처리량과 모델 그룹 지연(P3.16 측정 1)을 다시 잰다.
- `software/host/run.c`의 입력 채널 상한을 256에서 1,024(`MAX_TRACKS`)로 고쳤다. buffer 크기 검사(block × 채널 ≤ 2,048 × 256)는 그대로 둔다. 다른 code는 고치지 않았다.
- 실시간 정규화는 임시로 seg 방식이다(02 §5 미정). 정확도 손실은 정규화와 frame 경계에서 온다.
- 결과 손실 38개는 sub1 Host NIC의 절전에서 온다. FPGA, 보드 PHY, RGMII timing, 케이블은 원인이 아니다([결과 손실 보고서](<P5.3 Result Loss Research Report.md>)). 같은 조사에서 Host가 쉬지 않을 때 response time이 평균 4.8 → 2.9 ms로 줄어, 위 response time에도 Host 절전에서 깨어나는 시간이 들어 있다.
- PNU 표는 Xeon에서 잰 모델 그룹 지연 표다. Cache 효율은 이 시험의 목적이 아니었다.
- 큰 산출물(결과 CSV 536 MiB, 추론 요청 pcap 359 MiB, 입력 raw 5.09 GiB)은 sub1 `~/mmss_jobs/p52_acc/`에 있다. 저장소에는 요약과 판정만 둔다(`hardware/board_test/p53_meas/result/`).

