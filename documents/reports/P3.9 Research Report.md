# P3.9 보고서: architecture spec 동결

작성일: 2026-10-13

이 보고서는 P3.9에서 구현 구성을 정한 경과와 근거를 모은다. 규격 자체는 ARCH_SPEC.md에 있다. 값은 모두 simulation이다. DDR3·PCIe 비용에는 보드 실측을 썼다.

## 1. 요약

### 1.1 환경

| 구분 | 조건 |
|---|---|
| Simulator | `sim_core` rev 4(비교), rev 5(ARCH_SPEC DMA 크기) |
| 트랙 | 1,024, membrane potential DDR3 |
| 설계 | A 전체 cache · 한 번에 (그림 21은 A 한 줄씩, D stream 포함) |
| Scheduler | FCFS, EDF, Grouping, Dysta, Timeout, SlackBatch-Lite, SlackBatch |
| 시나리오 | uniform, skewed, synchronized, intermittent, skewed-synchronized, fluctuating × seed 20 |
| 악조건 | 기준, Host 주기 2 ms, PCIe 꼬리 +700 µs, control overhead +20 %, DDR3 2.0 GB/s |
| 구성 | L·256, XL·256, L·64, XL·64 lane |

### 1.2 결과

| 항목 | 결과 |
|---|---|
| 구현 구성 | L, 64 lane, membrane potential DDR3, cache entry 10개 |
| L·64 SlackBatch | miss 0, 악조건 5개 miss 0, 최대 응답 시간 29.0 ms |
| L·64 SlackBatch 대 Grouping | off-chip −80 %, 추정 energy −78 % |
| XL·256 SlackBatch 대 Grouping | off-chip −59 %, 추정 energy −56 % |
| SlackBatch guard 개선 | L·64 악조건 miss 9건 → 0건 |

### 1.3 결론

L 모델을 64 lane으로 구현한다. SlackBatch는 L에서도 miss 0으로 전송을 가장 적게 쓴다. 모델이 커지면(XL) 다른 정책이 무너지는 조건이 늘어 SlackBatch와의 차이가 커진다.

XL은 scheduler 효율을 보이는 확장 실험으로 쓴다. XL·256 lane simulation에서 SlackBatch는 악조건 5개를 포함해 miss 0이고, 추론 요청당 추정 동적 energy는 6.0 µJ로 Grouping(13.7 µJ)의 44 %다. XL·256 lane은 RTL로 만들지 않으므로 timing과 resource는 확인하지 않았다.

SlackBatch의 guard를 고쳤다. 처리 순서에 따른 cache 교체와 남은 일에 비례한 여유를 반영한다.

## 2. 동결 경과

| 날짜 | 구성 | 이유 |
|---|---|---|
| 10-12 | XL_aug, 256 lane, entry 2 | P3.8 제안안 채택 |
| 10-13 | L, 64 lane, entry 10 | 아래 |

XL에서 L로 바꾼 이유:

- P3.6에서 미리 정한 XL 채택 기준을 통과하지 못했다. 무작위 겹침에서 XL_aug − L_aug = +0.0055였고 기준은 +0.01이었다.
- 겹친 소리 정확도를 올린 것은 증강이었다(L → L_aug +0.065).
- L은 64 lane으로 1,024트랙을 처리한다. 256 lane의 timing 위험이 사라진다.

Checkpoint는 지금 증강 없는 L이다. 데이터셋과 학습을 개선한 L_aug로 바꾼다. 바꿀 때는 export와 golden만 다시 만든다.

Lane은 64로 정했다. 1,024트랙을 처리하는 가장 작은 구성이다. 32 lane의 상한은 672트랙이었다.

네 구성을 같은 조건으로 돌렸다. Timeout W는 구성마다 같은 절차로 정했다. 조정 seed 100~104에서 miss가 없는 가장 큰 W(1 ms 단위)다.

부하는 1,024를 Grouping 상한으로 나눈 값이다. XL·64는 1,024트랙에서 모든 정책이 miss를 냈다(FCFS·EDF 100 %, 나머지 약 95 %).

그림: `fig20`, `fig21`. 같은 행은 같은 축이다.

### 3.1 해석

L·64에서 SlackBatch는 miss 0으로 전송이 가장 적었다. Grouping보다 80 % 적고 Timeout보다 45 % 적다.

XL·256에서는 차이가 커졌다.

- FCFS·EDF miss가 52 %에서 100 %로 늘었다.
- Dysta는 L·64에서 악조건 miss가 없었지만 XL에서는 84건을 냈다.
- Timeout 대비 전송 차이가 45 %에서 53 %로 커졌다.

Grouping 대비 절감률은 L이 더 크다(L·64 80 %, XL 59 %). "XL에서 차이가 커진다"는 Grouping 대비 비율에는 맞지 않는다.

L·256은 부하가 27 %로 가볍다. Timeout이 22 ms를 기다려도 되어 전송이 SlackBatch와 거의 같았다(10.0 대 9.5 KB). 부하가 XL과 비슷한 L·64(75 %)에서는 Timeout W가 7 ms로 줄고 차이가 다시 벌어졌다.

## 4. SlackBatch guard 개선

### 4.1 문제

L·64에서 P3.8 정의(v0)는 guard가 모르는 악조건 2개에서 miss를 냈다. 모두 skewed 시나리오였다.

| 악조건 | v0 miss | v0 최대 응답 시간 |
|---|---:|---:|
| PCIe 꼬리 +700 µs | 2 | 32.2 ms |
| control overhead +20 % | 7 | 32.4 ms |

원인은 두 가지였다.

1. Guard는 모델마다 적재 비용을 판단 시점의 cache 상태로 봤다. 앞 모델을 적재하면 뒤 모델이 cache에서 밀려나는데 이를 반영하지 않았다. Entry가 10개라 0으로 본 모델이 많았다.
2. 고정 여유 `SLACK` 4 ms가 남은 일의 양에 비례하는 오차를 덮지 못했다. L·64는 대기 중인 일이 많다.

### 4.2 고친 점

| 항목 | v0 | 동결 |
|---|---|---|
| 대기 판단 | 다음 도착 시각을 앎 | `now + 1 ms`로 판단 (하드웨어 규칙) |
| 적재 비용 | 판단 시점 cache 상태 | 처리 순서대로 LRU 교체를 따라감 |
| 여유 | 고정 4 ms | 고정 4 ms + 남은 일 × α, α = 51/256 ≈ 0.2 |

α는 L·64에서 비교해 정했다(rev 5, 악조건 5개).

| Guard | 악조건 miss | 최대 응답 시간 | KB/추론 요청 |
|---|---:|---:|---:|
| 하드웨어 대기 규칙 | 0 | 31.8 ms | 9.7 |
| + cache 교체 반영 | 0 | 30.9 ms | 9.7 |
| + α 0.1 | 0 | 29.8 ms | 9.8 |
| + α 0.2 | 0 | 29.3 ms | 9.8 |

α를 키워도 전송은 거의 늘지 않고 deadline 여유가 늘었다. α 0.2는 악조건 "control overhead +20 %"와 크기가 같다. 같은 악조건으로 평가했으므로 이 선택은 낙관적일 수 있다.

### 4.3 결과

새 정의를 네 구성에 다시 돌렸다. 다른 정책의 결과는 SlackBatch와 독립이라 그대로 두고 SlackBatch 두 줄만 바꿨다(`merge_results.py`).

| 구성 | v0 악조건 miss | 새 정의 악조건 miss | v0 KB | 새 정의 KB | v0 상한 | 새 정의 상한 |
|---|---:|---:|---:|---:|---:|---:|
| L·64 | 9 | 0 | 9.4 | 9.7 | 1,216 | 1,360 |
| XL·256 | 0 | 0 | 31.0 | 32.3 | 1,264 | 1,264 |

새 정의는 전송을 약 3~4 % 더 쓰지만 L·64의 악조건 miss를 없앴다. 처리 상한도 Grouping과 같아졌다.

SlackBatch-Lite도 같은 개선을 넣었다. 두 정책은 guard 식(누적 대 합계)만 다르다.

## 5. 검토 반영

ARCH_SPEC 초안 검토에서 나온 6건을 고쳤다.

| 지적 | 조치 |
|---|---|
| DMA 크기와 비용 register 불일치 | Simulator rev 5에 실제 DMA 크기를 넣고 비용 register를 다시 계산 |
| Drop 추론 요청이 miss에서 빠짐 | 결과를 받지 못한 추론 요청도 miss로 정의 |
| 판정 주기 미정 | 학습과 같은 31 frame segment, segment마다 `RESET_STATE` |
| Slice prefetch 원칙과 충돌 | Prefetch는 모델 단위, slice는 simulation 비교 설계로 명시 |
| Scheduler 정수 규칙 부족 | 시간 단위, wrap, 동률, 판단 시점, α 곱셈 규칙 추가 |
| State write와 다음 추론 요청 순서 | 쓰기 응답 뒤 결과를 쓰고 slot을 비움 |

검토 중 위험 하나를 더 찾았다. 학습 mel은 파일 단위로 정규화했지만 실시간 전처리는 파일 최대값을 모른다. P4.8에서 다룬다.

## 6. 검증과 한계

확인함:

- 네 구성 × 7정책 × 3설계, 6시나리오 × seed 20, 악조건 5개
- Timeout W 조정 절차를 code로 옮기고 XL에서 P3.8 값(5, 5, 2 ms)이 다시 나옴
- Simulator self-test 44개 통과 (cache 교체 반영 21a·21b, 비례 여유 22 추가)
- L·64 export·golden (P3.10)

한계:

- 모든 결과는 simulation이다. RTL resource와 board 성능은 확인하지 않았다.
- α는 평가에 쓴 악조건과 같은 크기다.
- Energy는 추론 요청당 동적 energy 추정이다. 정적 전력과 lane 수에 따른 회로 전력은 빠져 있다.
- XL·64는 1,024트랙에서 과부하라 정책 비교에 쓰지 않는다.
- Simulator는 실수 µs로 계산한다. ARCH_SPEC의 정수 규칙과의 차이는 P4.5에서 확인한다.
