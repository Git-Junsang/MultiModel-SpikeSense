# P5.4 보고서: USB mic 입력과 end-to-end 시험

작성일: 2026-11-15

P4.8에 남아 있던 mic 입력을 Host program `mmss_host`에 넣었다. 그 뒤 라즈베리파이 5, USB mic 2개, 보드로 1,024트랙 end-to-end를 300 s 돌렸다. 같은 작업에서 Host의 frame 경계를 FPGA 주기에 맞추는 보정(`--pace`, `--mic`)을 넣고 `MARGIN_US`를 정했다. P6.4 데모 구성을 보려고 mic 2개와 wav를 읽는 가상 트랙 1,022개를 섞은 1,024트랙도 300 s 돌렸다. 수치는 따로 적지 않으면 보드 실측이다.

## 1. 요약

| mic | Generalplus MUSIC-BOOST USB mic 2개, 48 kHz mono, ALSA period 4 ms, buffer 16 ms |

### 1.3 결론

1. USB mic → Host → FPGA → 결과가 1,024트랙에서 동작한다. 300 s 동안 결과 손실, 32 ms 초과, xrun이 없었고 판정 주기 308,224개를 모두 판정했다. Mic 2개에 가상 트랙 1,022개를 섞어도 같다. 가상 트랙의 모델별 이상 판정 비율은 같은 wav를 쓴 P3.16과 상관 0.999다.
2. Frame 경계 보정이 동작한다. Mic clock이 FPGA보다 58.8 ppm 느려 Host가 frame 끝을 281샘플 옮겼다. 그래서 nominal frame 끝 뒤 도착이 처음부터 끝까지 같은 범위에 있었다. 보정하지 않으면 5분에 17.6 ms 밀린다.
3. Resampler는 scipy와 1 LSB 안에서 같다. Group delay 0.625 ms는 mic–Host 지연 쪽에 두고, 계산 시간만 Host 처리 지연에 넣는다([01_OVERVIEW.md](../design_references/01_OVERVIEW.md) §4).
4. Mic 입력의 Host 처리 지연은 두 mic의 block 도착 위상 차에 따라 달라진다. Host가 mic 2개를 한 loop에서 차례로 읽으므로, 한 mic의 block이 먼저 와도 다른 mic의 block을 기다린다. 위상 차가 1,016 µs인 §3.3 실행은 파일 입력보다 p99에서 2.5 ms 길었다. 16 µs인 §3.4 실행은 파일 입력과 같았다(p99 2.45 ms). 최대 response time은 8.84 ms로 deadline 32 ms 안이다.
5. `MARGIN_US`는 250 µs로 정했다. 결과 링크 지연 최대 126 µs(P3.16)에 시각 오차 예산 100 µs(06 §5)를 더하고 올림한 값이다.

### 1.4 한계와 남은 결정

- FPGA 출력을 snn_int8과 bit 비교하지 않았다. 보낸 추론 요청을 잡는 tcpdump에 sudo가 필요한데 Pi의 sudo 인증이 없었다. 같은 Host → FPGA 경로의 bit 일치는 P5.3에서 확인했다.
- 판정 값의 정확도는 보지 않았다. Mic는 방 소리를 받았고 정답이 없다. 이 시험은 통합 시연이며 목표 트랙 성능의 근거가 아니다.
- Governor를 performance로 바꾸지 못했다. ADC·USB 고정 지연은 loopback 장치가 없어 재지 않았다.
- Mic 3개 + 가상 트랙 1,021개(P6.4 데모 구성)는 mic가 2개뿐이라 돌리지 않았다. §3.4 실행은 두 mic의 block이 거의 함께 와서 기다림이 없었다. 위상 차가 큰 실행에서 mic 0을 따르는 가상 트랙의 Host 처리 지연이 얼마나 길어지는지는 재지 않았다.
- §3.3 실행의 binary는 모델 그룹 기록의 `t_host`를 두 mic 중 늦은 도착으로 남겼다. 표의 Host 처리 지연은 추론 요청마다 자기 mic의 `t_host`로 다시 구한 값이다(§3.3). §3.4 실행은 기록을 고친 binary(가장 이른 도착)로 돌렸다.

## 2. 설계

### 2.1 Mic 입력

`software/host/mic.c`가 ALSA 커널 interface(ioctl)로 capture 장치를 연다. libasound를 쓰지 않으므로 정적 링크를 유지한다. Pi에는 ALSA 개발 header가 없다.

| 항목 | 값 |
|---|---|
| 형식 | 48 kHz S16_LE mono. 시험한 mic는 16 kHz를 지원하지 않는다 |
| period, buffer | 192 frame(4 ms = 16 kHz 64샘플 block), 4 period(16 ms). P3.16에서 buffer 8 ms 이상은 부하에서도 xrun이 없었다 |
| `t_host` | block 마지막 샘플의 도착 = `htstamp`(마지막 hw_ptr 갱신, CLOCK_MONOTONIC) − `avail` / 48 kHz. `read()`가 돌아온 시각이 아니다 |
| 시작 | 모든 mic를 설정한 뒤 첫 read 바로 전에 함께 시작한다. USB 장치 하나를 시작하는 데 16 ms 넘게 걸려 첫 mic가 시작 직후 xrun을 낸다. Frame은 1.1 s 뒤에 시작하므로 그 전 xrun은 세지 않는다 |
| xrun | 다시 시작하고, 그 mic의 도착 추정을 새로 한다. 빠진 샘플은 채우지 않는다 |

`run --mic ID[,ID...]`로 쓴다. ID는 ALSA card 이름(`/proc/asound/<ID>`)이다. Mic 하나가 채널 하나이고 트랙 i는 채널 i % (mic 수)를 쓴다.

`--in` wav를 함께 주면 트랙 0 … (mic 수 − 1)만 mic를 쓰고 나머지는 가상 트랙이 된다. 가상 트랙 i는 wav 채널 (i − mic 수) % (wav 채널 수)를 쓴다. Host는 loop 한 번에 mic block을 모두 읽은 뒤 wav 64샘플을 읽어 같은 샘플 번호로 넣고, wav 끝에서는 처음으로 돌아간다. 가상 트랙의 frame 경계 보정(adj)과 `t_host`는 mic 0의 값을 쓴다.

### 2.2 Resampler

48 kHz를 16 kHz로 줄인다. FIR은 scipy `resample_poly(x, 1, 3)`의 기본값과 같다. 61 tap, Kaiser(β 5), cutoff 8 kHz, 합 1로 정규화한다. 출력 j = Σ h[i] x[3j − i]로 지난 샘플만 쓰므로 다음 block을 기다리지 않는다. 대신 출력이 `resample_poly`보다 10샘플(0.625 ms) 늦다. 이 group delay는 frame이 그만큼 앞선 소리를 담게 할 뿐이라 mic–Host 지연 쪽에 둔다. 계산량은 mic 하나에 초당 98만 번의 곱셈-덧셈(계산)이다.

### 2.3 Frame 경계 보정

FPGA PNU는 FPGA 주기의 nominal frame 끝 시각 `O_m + kT`를 기준으로 경과 시간을 잰다. 그래서 Host는 frame 끝 샘플이 그 시각에 도착하도록 frame 경계를 맞춘다([06_HOST_INTERFACE.md](../design_references/06_HOST_INTERFACE.md) §5). 고치기 전 P3.16 실행은 시작 위상이 −11.8 ms, +8.7 ms 어긋나 있었다.

- 공통: `run` 시작 때 구한 clock 차이로 FPGA 주기 경계(`NOW_US` mod 32,000 = 0)에 해당하는 Host 시각 t0를 정한다.
- `--pace`: block을 FPGA 시각으로 t0 + n / 16 kHz에 보낸다. 실행 중 clock 차이가 바뀐 만큼 Host 시각을 옮긴다.
- `--mic`: 샘플이 들어오는 속도를 Host가 정할 수 없다. 그래서 mic마다 샘플 0의 도착 시각 τ를 추정하고 frame 끝 샘플 번호를 adj = (t0 − τ) × 16 kHz만큼 옮긴다. τ는 (FPGA 시각 기준 block 도착 − 받은 샘플 수 / 16 kHz)의 1초 창 최솟값이다. 최솟값을 쓰는 것은 USB 전달 흔들림이 도착을 늦추는 쪽으로만 생기기 때문이다. Mic clock drift와 Host–FPGA clock 차이가 모두 τ에 들어간다. 오디오 값은 고치지 않고 자르는 위치만 옮기므로 hop이 가끔 511·513샘플이 된다.
- 제한: 위상은 `NOW_US` mod 32,000으로 구하므로 setup 뒤 71.6분(`NOW_US` 되감김) 안에 run을 시작해야 맞다(코드 주석 `shortcut:`).

### 2.4 `MARGIN_US`

FPGA는 `t_done_us > t_host_us + DEADLINE_US − MARGIN_US`이면 `LATE`를 켠다. 결과가 FPGA를 떠난 뒤 Host에 닿기까지의 시간과 시각 맞추기 오차만큼 여유를 둔다. 결과 링크 지연 최대 126 µs(P3.16)와 시각 오차 예산 100 µs를 더해 250 µs로 정했다. 시각 맞추기 왕복은 P3.16 모든 조건에서 최대 42 µs였다. `setup`의 기본값이다(`--margin-us`로 바꿀 수 있다).

- 가상 트랙의 판정은 같은 wav를 읽은 P3.16 파일 입력(`pin3_performance_load0`)과 같다. 모델별 이상 판정 비율이 평균 0.008, 최대 0.064 다르고 상관은 0.999다. Mic만 쓴 §3.3 실행과 P3.16의 상관은 0.343이다. 그래서 가상 트랙에 wav 샘플이 맞게 들어갔다고 본다. 비율이 조금 다른 것은 frame 경계가 mic 0의 adj만큼 옮겨져 wav의 다른 위치를 자르기 때문으로 본다.
- Host 처리 지연이 §3.3(p99 4.96 ms)보다 짧고 파일 입력(P3.16, p99 2.45 ms)과 같다. 이번 실행은 두 mic의 block이 16 µs 차이로 거의 함께 와서 다른 mic의 block을 기다린 시간이 거의 없었다. 위상 차는 mic를 시작할 때 정해지고 실행마다 다를 수 있다. 위상 차가 큰 실행에서는 mic 0을 따르는 가상 트랙 전체가 다른 mic의 block을 최대 block 하나(4 ms)만큼 더 기다린다. 이 경우 §3.3과 같이 p99가 2.5 ms쯤 길어진다고 본다(재지 않음).
- 가상 트랙의 `t_host`는 mic 0의 block 도착이고, wav 샘플은 그 뒤 mic block을 모두 읽고 나서 넣는다. 그래서 가상 트랙의 Host 처리 지연에는 wav를 읽는 시간도 들어간다.

## 4. 다음 작업

1. Mic를 장치마다 따로 읽는다(poll 또는 thread). 다른 mic의 block을 기다리는 시간(p99 약 2.5 ms)이 없어진다. 가상 트랙은 mic 0을 따르므로, 이 기다림이 생기는 실행에서는 가상 트랙 전체가 같이 늦어진다(§3.4).
2. Mic 3개 + 가상 트랙 1,021개로 P6.4 데모 구성을 돌린다. Mic가 하나 더 필요하다.
3. 부하 조건 꼬리의 원인을 찾는다. SCHED_FIFO 조건은 Pi sudo가 필요하다(P3.16).
4. tcpdump로 mic 입력의 FPGA 출력도 snn_int8과 bit 비교한다(sudo 필요).
5. ADC·USB 고정 지연은 스피커와 mic를 붙인 loopback으로 잰다.
6. 설계 정본의 평가 수치(01·04·05·08)는 아직 Xeon 측정을 넣은 simulation 값이다. P3.17의 Pi 값으로 바꿀지 정한다.
