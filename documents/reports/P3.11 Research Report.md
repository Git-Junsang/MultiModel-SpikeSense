# P3.11 보고서: 비교군 공정성 재검토와 선행연구 비교

작성일: 2026-10-13

P3.9까지의 결론은 "L·XL에서 SlackBatch가 Dysta, Grouping, Timeout보다 낫다"였다. 이 보고서는 그 비교가 같은 조건이었는지 점검하고, 고칠 수 있는 것은 고쳐 다시 돌린 결과를 모은다. 선행연구 20편의 원문을 읽고 우리 simulator로 옮길 수 있는 정책을 비교군에 더했다. 값은 모두 simulation이다. DDR3·PCIe 비용에는 보드 실측을 썼다.

## 1. 요약

### 1.1 환경

| 구분 | 조건 |
|---|---|
| simulator | `sim_core` rev 4, P3.9 비교와 같은 비용 모델 |
| 구성 | L·64 lane(구현 구성), XL·256 lane(비교), 1,024트랙, membrane potential DDR3 |
| 설계 | A.전체cache 한 번에·한 줄씩, D.스트림 한 줄씩 |
| 조정 | seed 100~104 × 시나리오 6 × 조건 5(기준 + 악조건 4) |
| 평가 | seed 0~19 × 시나리오 6, 기준과 악조건 4개 |
| 정책 | Grouping(기준선), 선행연구식 7개, SlackBatch-Lite, SlackBatch |

### 1.3 결론

1. 조건을 맞춰도 DDR3 byte 결론은 유지된다. 같은 절차로 조정한 선행연구식 정책 중 SlackBatch가 miss 0을 지키며 가장 적게 읽는다. 하한보다 7 %(L·64), 10 %(XL) 많을 뿐이다. 다만 이것은 평균 트래픽 절감이다. DDR3가 느려질 때 버티는 한계는 Grouping과 같다(L·64 0.4 GB/s, §4.7).
2. 견고성 결론 하나는 철회한다. P3.9의 "XL에서 Dysta가 악조건에 무너진다"는 η를 조정하지 않은 결과였다.
3. 응답 시간은 기다리지 않는 정책(Clockwork Method, Dysta Method, Grouping)이 더 짧다. L·64 평균 6.2 ms 대 14.0 ms다. 대신 DDR3를 4배 쓴다.
4. 우리보다 나은 선행연구는 cache 교체 규칙이다(RT-Swap, Ogden 외). scheduler가 아니라 저장 정책 쪽이며, SlackBatch와 함께 쓸 수 있다.
5. 동결 저장 정책(A, LRU)은 SlackBatch와 맞지 않는다. BRAM을 그대로 쓰면 F·E(한 번에), BRAM을 아끼려면 B(한 줄씩, 195.5 tile)가 낫다(§4.8).
6. 동결 α 0.2를 유지한다. 공통 조정이 고른 α 0은 byte를 0.1 KiB 줄이지만 최대 트랙이 Grouping보다 낮아진다(§4.9).

### 1.4 한계와 남은 결정

- 비교군은 원문 시스템이 아니라 옮긴 정책이다. 선점, sparsity 예측, GPU 여러 대는 없다(§2.3).
- 교체 규칙 E 또는 F를 동결 구성에 넣을지 정해야 한다. PROPOSAL과 ARCH_SPEC 변경이 필요하다.
- PROPOSAL §5.2의 비교군(Dysta, Timeout)에 새 비교군을 넣을지 정해야 한다.

## 2. 비교 조건 재검토

### 2.1 P3.9까지의 비교군

비교군은 원 논문과 다르게 옮겼고, 조절값을 정한 방식도 정책마다 달랐다.

| 비교군 | 원문 | P3.9 구현 | 문제 |
|---|---|---|---|
| Grouping | 선행연구가 아니다. 이 프로젝트의 기준선 | 가장 오래 기다린 추론 요청의 모델, 대기 추론 요청 전부 | 논문 비교로 쓰면 안 됨 |
| Dysta | Sparse-DySta Alg. 2: 추론 요청 단위, layer 경계 선점, sparsity로 남은 시간 갱신, 벌점 항 | 모델 단위 batch. 남은 weight 전송을 점수에 넣음. 선점·sparsity·벌점 없음. η = 0.01 고정 | 원문에 없는 batch와 cache 정보를 받음(유리). η를 조정하지 않음(불리). 표 이름이 원문과 같음 |
| Timeout | Triton max queue delay, Clipper delayed batching | 가장 오래된 추론 요청이 W를 기다리면 Grouping처럼 처리 | W를 기준 조건에서만 고르고 악조건에서 평가(불리) |
| SlackBatch | 제안 | α = 51/256 | 평가 seed와 같은 악조건으로 α를 고름(유리) |

FCFS와 EDF도 선행연구가 아니다. 맨 앞 추론 요청 뒤로 이어지는 같은 모델 추론 요청을 묶는 판이다.

## 3. 선행연구 원문 검토

판정 기준은 하나다. 우리 simulator(compute array 1개, DMA 1개, 비선점 batch, 모델 40개, hard deadline)로 옮겼을 때 원문의 규칙이 남는가. 원문 PDF는 [papers/references/INDEX.md](../papers/references/INDEX.md)에 있다.

### 3.1 scheduler

| 논문 | 원문 핵심 | 우리 쪽 | 판정 |
|---|---|---|---|
| Sparse-DySta (MICRO'23) | 점수 = 남은 시간 + η(deadline 여유 + 벌점). layer 경계 선점, sparsity 예측. 원문에 η 값이 없고 공식 코드 기본값은 0.01 | Dysta Method(batch), Dysta Method(추론 요청 단위) | 비교 |
| Clockwork (OSDI'20) | GPU memory를 모델 cache로 쓰고 LRU로 교체. latest = deadline − 실행 시간. 못 맞출 추론 요청은 취소. 수요 기반 LOAD | Clockwork Method | 비교 |
| Symphony (arXiv 2308.07470) | 추론 요청을 하나 더 넣으면 못 맞추는 시각까지 미룬다. drop. 조절값 없음 | Symphony Method | 비교 |
| DeepRT (SEC'21) | 모델별 window(상대 deadline의 절반), job EDF, admission | DeepRT Method | 비교 |
| Shepherd (NSDI'23) | 가장 큰 feasible batch 먼저, 선점 문턱 λ | Shepherd Method(선점 없음) | 비교 |
| Clipper (NSDI'17) | AIMD batch 상한, 지연 batch | AIMD 신호(batch 시간 > SLO)가 우리 조건에서 걸리지 않아 Timeout과 같다 | Timeout으로 대신 |
| LazyBatching (HPCA'21) | 실행 중 노드 단위 합류, 선점. 일부러 기다리지 않는다 | 선점을 빼면 Grouping과 같다 | 제외 |
| PREMA (HPCA'20) | token 기반 선택, 선점 | 우선순위가 하나면 deadline을 보지 않는다 | 제외 |
| DREAM (ASPLOS'24) | 이종 가속기 점수, smart drop | 가속기 하나면 기다림 없는 점수 정책(Dysta Method 계열) | 제외 |
| Layerweaver (HPCA'21) | 연산 위주 layer와 memory 위주 layer를 교차 | 모델 구조가 같으면 원문 규칙상 꺼진다 | 제외 |
| Fluid Batching (arXiv 2209.13443) | 조기 종료 모델 하나, 선점하며 합류 | 다중 모델 문제가 아니다 | 제외 |
| EAS (CSCI'23) | ReRAM 공간 분할, 주기 deadline 여유로 weight 재기록 감소 | 대규모 수정 필요. 원리는 SlackBatch와 같은 방향 | 제외 |
| CD-MSA (TPDS'23), AI-MT (ISCA'20) | 초록만 확인 | | 보류 |

P3.8 코드는 지연 Grouping을 "LazyBatching류"라고 적었다. LazyBatching은 일부러 기다리지 않는다. deadline 여유 안에서 기다리는 선행연구는 Symphony와 DeepRT다. 주석을 고쳤다.

### 3.3 SNN과 PLIF

PLIF나 학습 threshold LIF를 FPGA·ASIC으로 구현한 논문은 찾지 못했다. 가장 가까운 SNAP-V(arXiv 2603.11939)는 뉴런마다 decay와 threshold를 설정한다. 추론 때 PLIF는 β·vth가 고정된 LIF라 우리 구조가 이미 그 형태다.

multi-tenant SNN 하드웨어도 찾지 못했다. Edge AI review(arXiv 2603.26722) §VIII-B-2는 membrane state를 저장·복원해 SNN 모델을 바꾸는 방식을 앞으로의 과제로만 적었다.

### 4.5 원문에 가까운 Dysta (L·64, A·한 번에)

추론 요청 하나씩 처리하는 Dysta Method(추론 요청 단위)는 miss 0, 악조건 5개도 miss 0이었다. DDR3는 37.0 KiB/추론으로 batch판 Dysta Method(40.8)보다 적다. η = 0이면 점수가 남은 처리 시간만 보게 된다. 그래서 cache에 있는 모델을 먼저 고르고, 같은 모델 추론 요청을 연달아 처리한다. cache hit rate는 0.664다. batch를 만들지 않아도 cache hit로 같은 효과를 낸다.

P3.9의 Dysta 구현이 결론을 바꿀 만큼 유리하거나 불리하지는 않았다. batch를 준 판(40.8)과 원문에 가까운 판(37.0)이 비슷하고, 둘 다 SlackBatch(9.6)의 4배 안팎이다.

### 4.7 DDR3 대역폭 하한

DDR3 대역폭을 3.015 GB/s에서 0.1 GB/s까지 낮추며 miss 0인 가장 낮은 값을 찾았다. A·한 번에, 시나리오 6 × seed 0~2다. 대역폭마다 조절값은 공통 조정 값을 먼저 쓰고, 실패하면 같은 격자의 다른 값도 시험했다.

| 정책 | L·64 GB/s | XL·256 GB/s |
|---|---:|---:|
| Grouping, Dysta Method, Clockwork Method, Symphony Method, SlackBatch-Lite, SlackBatch | 0.4 | 1.3 |
| Timeout | 0.4 | 1.6 |
| DeepRT Method | 0.65 | 2.4 |
| Shepherd Method | 1.3 | 3.015에서도 miss |

DDR3가 느려져도 SlackBatch가 더 오래 버티지 않는다. 기다리지 않는 정책도 DDR3가 바쁘면 queue가 쌓이고 batch가 저절로 커진다. 0.4 GB/s에서 Grouping의 uniform 시나리오 weight는 9.3 KiB/추론으로, 3.015 GB/s일 때(45.9)의 1/5이다.

하한은 모든 정책에 같은 조건이 정한다. 주기마다 모델 40개를 적어도 한 번 읽어야 하고(5.26 MB), membrane potential 읽기·쓰기 2.89 MB도 있다. 0.3 GB/s에서는 이것만 27.2 ms로 주기의 85 %다. 실패는 편중 시나리오(skewed, skewed-synchronized)에서 먼저 났다. 고정 규칙 정책(Timeout, DeepRT Method, Shepherd Method)은 이 적응이 덜해 하한이 높다.

따라서 SlackBatch의 DDR3 절감은 평균 트래픽을 줄이는 것이다. DDR3 동적 전력과 다른 트래픽에 남기는 대역폭으로 이어진다. worst case 대역폭 요구량은 Grouping과 같다.

### 4.8 L·64 전체 조합

fig20·21과 §4.2는 저장 정책을 A로 고정했다. 저장 6개(A~F) × 연산 2개 × scheduler 6개(Grouping, Dysta Method, Timeout, DeepRT Method, SlackBatch-Lite, SlackBatch) = 72개 설계를 기준 조건과 악조건 4개에서 돌렸다. 조절값은 같은 연산 방식의 A에서 정한 값을 그대로 썼다. 계산은 main, sub1, sub2에 나눠 돌렸고, 세 서버의 결과가 bit 단위로 같은 것을 먼저 확인했다.

B·C는 크기를 정할 때 외부 예약 BRAM(25.5 tile)을 빼지 않아 L·64에서 C가 예산을 넘었다. 예약분을 빼도록 고쳤다(`policies._limit`). 예약이 없는 XL·256의 B·C 크기는 그대로다.

72개 중 58개가 5개 조건 모두 miss 0이었다. 그중 DDR3가 적은 순서다.

| 저장 정책 (SlackBatch) | BRAM에 항상 두는 weight | BRAM에 없는 모델이 오면 | 연산 | DDR3 KiB/추론 | weight | 접근 횟수/추론 요청 (지금 → membrane potential 모델별 배치) | BRAM tile | 악조건 최대 응답 시간 ms |
|---|---|---|---|---:|---:|---|---:|---:|
| C.고정혼합 | 트랙 수 상위 5개 모델은 전체, 그다음 34개 모델은 layer 1만. 바꾸지 않음 | 없는 부분을 그때마다 읽고 버림 | 한 줄씩 | 8.0 | 5.2 | 2.29 → 0.40 | 310.5 | 28.6 |
| F.다음사용 | 모델 전체를 담는 칸 10개 | 다음 추론 요청이 가장 늦게 올 모델을 빼고 새 모델을 넣음 | 한 번에 | 8.1 | 5.3 | 2.04 → 0.15 | 291 | 31.4 |
| E.인기고정 | 칸 10개 중 8칸은 트랙 수 상위 8개 모델로 고정 | 남은 2칸에서 가장 오래 안 쓴 모델을 빼고 새 모델을 넣음 | 한 번에 | 8.2 | 5.4 | 2.04 → 0.15 | 291 | 31.9 |
| B.부분상주 | 40개 모델 모두의 layer 1. 바꾸지 않음 | layer 2~4를 그때마다 읽고 버림 | 한 줄씩 | 8.9 | 6.2 | 2.33 → 0.44 | 195.5 | 28.7 |
| A.전체cache (동결) | 모델 전체를 담는 칸 10개 | 가장 오래 안 쓴 모델을 빼고 새 모델을 넣음(LRU) | 한 번에 | 9.6 | 6.8 | 2.05 → 0.16 | 291 | 31.4 |
| D.스트림 | 없음 | 모델 전체를 그때마다 읽고 버림 | 한 줄씩 | 9.8 | 7.1 | 2.66 → 0.77 | 39.5 | 28.5 |

layer 1은 입력 40 → 뉴런 384 연결의 weight다(15,360 B, 모델의 12 %). layer 1을 두는 정책은 그 모델의 β·vth도 함께 둔다. 한 번에는 모델 weight를 다 읽은 뒤 계산하고, 한 줄씩은 뉴런 64개 단위로 weight가 도착하는 대로 계산한다.

"membrane potential 모델별 배치"는 같은 모델 트랙의 membrane potential을 DDR3에 붙여 두고 batch마다 읽기·쓰기를 한 번씩 한다고 본 계산값(weight 접근 + 2 ÷ 평균 batch)이다. simulation은 지금 추론 요청마다 2회로 센다.

- 저장 정책을 바꾸면 SlackBatch의 DDR3가 더 준다. 동결 구성(A, 9.6)보다 C·한 줄씩이 17 %, F·한 번에가 16 %, E·한 번에가 15 % 적다.
- A와 D의 DDR3가 거의 같다(9.6 대 9.8). SlackBatch와 함께 쓰면 LRU entry 10개(약 260 tile)가 적재를 거의 줄이지 못한다(hit 0.00~0.02).
- B·C·D의 한 번에 방식은 SlackBatch에서도 악조건 miss가 났다(C 5건, B 12건, D 14건). 적재 buffer가 하나라 다음 모델 적재를 연산과 겹치지 못하는데, guard가 이 대기를 계산에 넣지 않는다. 이 세 저장 정책은 한 줄씩과 함께 써야 한다.
- 다른 scheduler 중에서는 DeepRT Method(C·한 줄씩 11.0)가 가장 적었다. 같은 저장 정책끼리 비교해도 SlackBatch가 가장 적다.

전체 표는 `p311L64all_fixed_n1024.md`, `p311L64all_margin_n1024.md`에 있다.

### 4.9 트랙 수와 최대 트랙

최대 트랙은 시나리오마다 miss 0인 가장 큰 트랙 수(seed 3, 16트랙 단위)를 찾고 6개 시나리오 중 가장 작은 값이다.

| 정책 | 한 줄씩 (A~F 모두) | 한 번에 A | E | F | B | C | D |
|---|---:|---:|---:|---:|---:|---:|---:|
| Grouping | 1,360 | 1,360 | 1,360 | 1,360 | 1,296 | 1,312 | 1,280 |
| Dysta Method | 1,360 | 1,360 | 1,360 | 1,360 | 1,088 | 1,280 | 992 |
| Timeout | 1,136 | 1,136 | 1,136 | 1,136 | 1,072 | 1,088 | 1,056 |
| DeepRT Method | 1,216 | 1,216 | 1,216 | 1,216 | 1,168 | 1,184 | 1,168 |
| SlackBatch-Lite, SlackBatch (동결 α 0.2) | 1,360 | 1,360 | 1,360 | 1,360 | 1,296 | 1,312 | 1,280 |
| SlackBatch (공통 조정 α 0) | 1,360 | 1,296 | 1,248 | 1,360 | 1,184 | 1,200 | 1,184 |

- 한 줄씩이면 저장 방식과 상관없이 Grouping, Dysta Method, SlackBatch 계열이 1,360트랙으로 같다. Timeout과 DeepRT Method는 그보다 낮다.
- 한 번에의 B·C·D는 적재 buffer가 하나라 모든 정책의 한계가 내려간다.
- 공통 조정이 고른 α 0에서는 SlackBatch가 한 번에 A·E에서 Grouping보다 낮았다. 공통 조정은 1,024트랙의 DDR3만 보고 α를 골랐기 때문이다. 동결 α 0.2로 다시 돌리면 Grouping과 같아진다. byte 차이는 0.1 KiB/추론이므로 동결 α를 유지한다.

트랙 수를 512~1,424로 바꿔 돌렸다(설계 3개 × scheduler 6개, seed 10, 1,024트랙만 seed 20). A·한 번에 기준이다.

| 정책 | miss가 처음 난 트랙 | DDR3 KiB/추론 (512 → 1,424트랙) | 평균 응답 시간 ms |
|---|---:|---|---|

| Dysta Method | 1,360 | 47.9 → 17.6 | 3.8 → 11.0 |
| Timeout | 1,152 | 32.6 → 15.7 | 7.8 → 11.3 |
| DeepRT Method | 1,152 | 22.9 → 10.6 | 9.4 → 13.9 |

최대 트랙(seed 3)은 1,360인데 seed 10으로 돌린 sweep에서는 1,360트랙에서 miss가 났다. 1,360은 경계값이다.

트랙이 늘면 기다리지 않는 정책도 밀린 추론 요청 때문에 batch가 커져 DDR3가 준다. 그래도 모든 트랙 수에서 SlackBatch가 가장 적다. DDR3 대역폭을 낮출 때도 같은 모양이다(그림 31). 3.015 GB/s에서 Grouping 49 KiB/추론이 0.4 GB/s에서는 약 10 KiB/추론으로 SlackBatch와 만난다.

| 읽기 방식 | 한 줄씩이면 저장 방식의 영향이 사라짐 | 없음 | 없음 | 큼: B·C·D는 한 줄씩이 필요 | 작음 | 중간: 한 줄씩이 약 +0.5회 | 작음: −5~+24 tile |

| 조건 변수 | 영향 |
|---|---|
| 트랙 수 | 1,360트랙 근처에서 대부분 깨진다(Timeout·DeepRT Method는 1,152). 트랙이 늘수록 정책 사이 DDR3 차이가 좁아진다 |
| 시나리오 | 동시 도착(synchronized, skewed-synchronized)에서는 정책 사이 DDR3 차이가 거의 없다. 편중(skewed, skewed-synchronized)이 한계를 정한다 |
| DDR3 대역폭 | 줄수록 정책 사이 DDR3 차이가 좁아져 0.4 GB/s 근처에서 만난다 |

## 5. 우리보다 나은 것

| 대상 | 판정 | 근거 |
|---|---|---|
| cache 교체: RT-Swap Method(F), Ogden Method(E) | **우리보다 낫다** | L·64에서 동결 LRU보다 DDR3가 15~16 % 적고(9.58 → 8.09·8.15 KiB), 악조건 miss 0이다(§4.6) |
| 응답 시간: Clockwork Method, Dysta Method | 지표에 따라 낫다 | L·64 평균 6.2 ms, p99 23.6 ms로 SlackBatch(14.0, 26.4)보다 짧다. 대신 DDR3를 4배 쓴다. 우리 목표(deadline 안 처리 + byte)에서는 이점이 아니다 |
| DDR3 byte: scheduler | 없음 | 가장 가까운 DeepRT Method도 L·64 13.5, XL 60.1 KiB로 SlackBatch(9.6, 31.6)보다 많다. SlackBatch는 하한보다 7 %(L·64), 10 %(XL) 많을 뿐이라 batch 규칙으로 줄일 여지가 작다 |
| DDR3 대역폭 하한 | Grouping 계열과 같음 | 기다리지 않는 정책도 DDR3가 느리면 batch가 커져 같은 하한(L·64 0.4, XL 1.3 GB/s)에 닿는다(§4.7) |
| 견고성 | Dysta Method는 대등 | η를 조정하면 XL 악조건도 miss 0이다. Timeout, DeepRT Method, Shepherd Method는 XL 악조건에서 miss가 난다 |

나은 것으로 고른 것은 scheduler가 아니라 저장 정책이다. SlackBatch는 모델을 deadline 순으로 돌기 때문에 LRU와 맞지 않는다. 교체 규칙을 바꾸면 SlackBatch의 byte가 더 줄어 둘이 함께 간다.

E와 F 중에서는 E가 하드웨어에 쉽다. Host가 트랙 수로 고정할 모델 8개를 정해 entry를 잠그면 된다. F는 모델마다 다음 사용 시각 표가 필요하다. 이득 차이는 0.06 KiB/추론이다. 동결 구성(entry 10개 LRU)을 바꾸려면 PROPOSAL과 ARCH_SPEC을 고쳐야 하므로 사용자 결정으로 남긴다.

## 6. 검증과 한계

확인함:

- 공통 조정: 조절값이 있는 정책 7개 × 설계 3개(L·64, XL·256 각각)와 Dysta Method(추론 요청 단위) 1개(L·64). 조정 seed 100~104 × 시나리오 6 × 조건 5
- 평가: 평가 seed 0~19 × 시나리오 6, 기준과 악조건 4개. L·64 정책 9개 × 설계 3개, XL·256 같은 수
- cache 교체: L·64, Grouping·Timeout·SlackBatch-Lite·SlackBatch × E·F × 한 번에·한 줄씩
- DDR3 대역폭 하한: L·64·XL·256, 정책 9개, A·한 번에, 시나리오 6 × seed 0~2(seed가 적어 경계값은 거칠다)
- L·64 전체 조합: 72개 설계 × 기준과 악조건 4개. main·sub1·sub2의 결과가 같은지 먼저 확인했다(numpy 2.4.6·2.5.4·2.2.6, 실행 4개 bit 일치)
- simulator self-test 51개 통과(P3.11 추가 7개: Symphony Method 미룸, DeepRT Method window·flush, drop, Shepherd Method 선택, F 교체 대상, E 고정)

한계:

- 모든 값은 simulation이다(rev 4, P3.9 비교와 같은 조건). RTL과 board로 확인하지 않았다.
- 비교군은 원문 시스템이 아니라 우리 simulator로 옮긴 정책이다. 선점, sparsity 예측, GPU 여러 대는 없다(§2.3). 결론은 "옮긴 정책보다 낫다"까지다.
- 조정 조건과 평가 조건은 악조건 종류가 같고 seed만 다르다. 모든 정책에 같은 조건이다.
- 공통 조정은 SlackBatch α = 0을 골랐다. 동결 α(51/256)는 바꾸지 않았다(§4.3).
- E·F는 A에서 정한 조절값을 썼다. F는 Host가 트랙 주기와 offset을 알아 다음 사용을 예측한다고 가정했다.
- Dysta Method(추론 요청 단위)는 L·64 A·한 번에만 돌렸다.
- 새 그림은 만들지 않았다. 표만 있다.
- Symphony의 게재 학회는 확인하지 못했다. CD-MSA, AI-MT는 원문을 받지 못했다.

## 7. 재현

```bash
python3 simulation/legacy/sim_develop/run_sim.py --selftest

X="python3 simulation/legacy/sim_develop/target_exp.py --n 1024 --arch L --lanes 64 --reserve 25.5"
S9=final_grouping,p311_dysta,final_timeout,p311_clockwork,p311_symphony,p311_shepherd,p311_deeprt,slackbatch_lite,slackbatch
O="--only A:한번에,A:한줄씩,D:한줄씩"
$X --stage tune2 --sch $S9 $O --prefix p311L64          # 조절값 → p311L64_tuned_n1024.json
$X --stage fixed --seeds 20 --sch $S9 $O --prefix p311L64
$X --stage margin --sch $S9 $O --prefix p311L64

# Dysta Method(추론 요청 단위), 참고
for st in tune2 fixed margin; do $X --stage $st --seeds 20 --sch p311_dysta_req --only A:한번에 --prefix p311L64r; done

# cache 교체: p311L64_tuned_n1024.json의 A 항목을 E·F 이름으로 복사해 p311L64e_tuned_n1024.json을 만든 뒤
E4=final_grouping,final_timeout,slackbatch_lite,slackbatch
for st in fixed margin; do $X --stage $st --seeds 20 --extra-sto --sch $E4 --only E:한번에,E:한줄씩,F:한번에,F:한줄씩 --prefix p311L64e; done

# L·64 전체 조합(§4.8): A에서 정한 조절값을 B~F에 복사한 p311L64all_tuned_n1024.json을 먼저 만든다.
# 악조건 단계는 --only를 저장 정책별로 나눠 main·sub1·sub2에서 돌리고 jsonl을 합친 뒤 --table로 표를 다시 만든다
S6=final_grouping,p311_dysta,final_timeout,p311_deeprt,slackbatch_lite,slackbatch
OA="--only A:한번에,A:한줄씩,B:한번에,B:한줄씩,C:한번에,C:한줄씩,D:한번에,D:한줄씩,E:한번에,E:한줄씩,F:한번에,F:한줄씩"
for st in fixed margin; do $X --stage $st --seeds 20 --extra-sto --sch $S6 $OA --prefix p311L64all; done

# 최대 트랙(§4.9): 같은 prefix로 cap 단계. 동결 α 0.2 비교는 SlackBatch 항목만 51/256으로 바꾼 p311L64a02_tuned로 돈다
$X --stage cap --extra-sto --sch $S6 $OA --prefix p311L64all
$X --stage cap --extra-sto --sch slackbatch_lite,slackbatch $OA --prefix p311L64a02
# 트랙 수 sweep(§4.9): N마다 p311sw_tuned_n{N}.json(= p311L64all_tuned)을 두고 돈다
for N in 512 768 1152 1280 1360 1424; do python3 simulation/legacy/sim_develop/target_exp.py --n $N --arch L --lanes 64 --reserve 25.5 --extra-sto --stage fixed --seeds 10 --sch $S6 --only A:한번에,F:한번에,B:한줄씩 --prefix p311sw; done
python3 simulation/legacy/sim_develop/bw_sweep.py --curve      # 그림 31 → p311_bwcurve_n1024.jsonl
python3 simulation/legacy/sim_develop/plot_p311.py             # 그림 22~31

# XL·256: X 대신 아래를 쓴다. 조정 대상은 S9에서 조절값이 있는 정책
Y="python3 simulation/legacy/sim_develop/target_exp.py --n 1024"
for st in tune2 fixed margin; do $Y --stage $st --seeds 20 --sch $S9 $O --prefix p311XL; done
```
