# P4.2 보고서: membrane storage RTL

작성일: 2026-10-19

트랙마다 membrane potential을 따로 두고 12 bit로 저장하는 경로를 RTL로 만들었다. on-chip 트랙은 `membrane_bank`, 나머지 트랙은 `membrane_buf`를 거쳐 DDR3에 둔다. P4.1 compute array와 붙여 `golden_l64_m12` 82개를 트랙 82개로 돌려 bit 단위로 맞는지, 트랙끼리 섞이지 않는지, `RESET_STATE`이면 DDR3를 읽지 않는지 확인했다. DDR3는 testbench 모델이고 보드 실측이 아니다.

## 1. 요약

### 1.1 환경

| 구분 | 내용 |
|---|---|
| RTL | `hardware/src/`의 `membrane_storage`, `membrane_bank`, `membrane_buf`. P4.1의 `compute_array`, `weight_entry`와 함께 돌렸다 |
| 기준 | `hardware/data/golden_l64_m12/` 82개(실데이터 80, 포화 시험 2). 16 bit로 계산하고 12 bit로 저장한다 |
| 트랙 | vector 하나를 트랙 하나에 둔다. on-chip 60트랙(0, 767 포함), DDR3 22트랙(768, 1,023 포함). 같은 모델의 두 트랙이 둘 다 on-chip인 모델 28개, 둘 다 DDR3 8개, 섞인 모델 4개 |
| 처리 순서 | timestep마다 모델 0~41을 차례로 batch 하나씩 처리한다. batch 안에서는 같은 모델의 트랙 두 개를 번갈아 처리하고, DDR3 트랙은 앞 트랙을 연산하는 동안 준비한다 |
| DDR3 | testbench 모델. 추론 요청 수락, 첫 beat까지 8~47 cycle, beat 사이 빈 cycle, 쓰기 응답 5~34 cycle을 무작위로 준다. 처음 내용은 `0xA5A55A5A`를 반복한 쓰레기 값이다 |
| simulation | xsim 2026.1, Verilator 5.020 |
| 합성 | Vivado 2026.1, `xc7a200tfbg484-2`, out-of-context, clock 10 ns. compute array + entry 4개 + entry 출력 mux + `membrane_storage`(on-chip 768트랙) |

### 1.2 결과

| 질문 | 답 |
|---|---|
| bit 일치 | 추론 2,542개에서 row 불일치 0, 판정용 출력 불일치 0, 끝난 뒤 DDR3 내용 불일치 0(xsim, Verilator 둘 다) |
| `RESET_STATE` | DDR3에서 읽은 beat 22,440개 = 22트랙 × 30 × 34. 첫 timestep은 읽지 않았다. 쓴 beat는 23,188개 = 22트랙 × 31 × 34 |
| 오류를 잡는가 | 일부러 고장 낸 RTL 5개(트랙 번호 무시, reset 때도 읽기, 12 bit 포화 빠짐, 읽기·쓰기 beat 순서 바꿈)가 모두 FAIL |
| DDR3 전송 | 트랙 하나에 32 B beat 34개, 1,088 B. 유효 data는 1,059 B다 |
| timing | 100 MHz 통과. WNS +0.348 ns, WHS +0.100 ns. 가장 느린 경로는 bank 주소가 BRAM 187개로 퍼지는 배선(9.1 ns, 논리 0단)이다 |
| resource | BRAM 301 tile(entry 114 + bank 187), LUT 14,913, FF 4,589, DSP 82. `membrane_storage`는 LUT 5,953(그중 LUTRAM 1,056), FF 744 |

### 1.3 결론

1. 트랙마다 membrane potential을 따로 두고 12 bit로 저장하는 경로가 golden과 bit 단위로 같다. 같은 모델의 트랙을 번갈아 처리해도 섞이지 않고, on-chip 트랙과 DDR3 트랙의 결과도 같다.
2. DDR3에는 뉴런 n의 12 bit를 bit `12n`에 이어 붙인다. row 4개가 beat 3개에 꼭 맞아 변환이 64 bit 단위 선택만으로 끝난다.
3. on-chip 768트랙은 187 tile이다. 04_MEMORY.md §2의 예산 200.5 tile보다 13.5 tile 작다. 첫 합성은 bank를 한 덩어리로 두어 384 tile이 나와 device를 넘었고, 깊이 2,048짜리로 나눠 고쳤다.

## 2. 설계

### 2.1 block

| 파일 | 내용 |
|---|---|
| `membrane_storage.v` | `track_id < N_ONCHIP`이면 bank, 아니면 buffer로 보낸다. 쓸 때 16 bit를 12 bit로 포화하고 읽을 때 부호를 늘린다. `start` 때 트랙을 잡는다 |
| `membrane_bank.v` | on-chip 트랙. row 하나 = 뉴런 16개 × 12 bit = 192 bit, 주소 = `track × 45 + row`. simple dual port BRAM, 읽기 latency 2 |
| `membrane_buf.v` | DDR3 트랙 buffer 2개. 상태는 FREE → FILL(DDR3 읽기) → READY → BUSY(연산) → DRAIN(되쓰기) → FREE. buffer 하나 = 그룹 12개 × 64 bit chunk 12개, LUTRAM |

compute array 쪽 interface는 P4.1 그대로다(row 단위 16 bit 읽기·쓰기, 읽기 latency 2). `RESET_STATE`는 compute array가 읽은 값을 0으로 바꾸므로 bank는 그냥 읽고, DDR3 트랙은 buffer가 DDR3 읽기를 건너뛴다.

### 2.2 DDR3 배치

04_MEMORY.md §5에서 미정이던 12 bit의 byte 배치를 정했다.

```text
트랙 주소   = STATE_BASE + track_id × 0x800
뉴런 n의 값 = 트랙 영역 bit [12n+11 : 12n]   (little-endian으로 이어 붙임, n = 0 ~ 705)
row r       = bit [192r+191 : 192r]          (뉴런 16r ~ 16r+15)
그룹 g      = row 4g ~ 4g+3 = 768 bit = 32 B beat 3개
트랙 하나   = 그룹 11개 + row 44 = beat 34개 = 1,088 B (앞 1,059 B가 유효)
```

buffer는 그룹마다 64 bit chunk 12개로 둔다. row slot s(0~3)는 chunk 3s~3s+2, beat k(0~2)는 chunk 4k~4k+3이다. DDR3에서 beat가 오면 chunk 4개를 쓰고, compute array가 row를 쓰면 chunk 3개를 쓴다. 읽기도 같은 방식으로 고른다.

### 2.3 처리 순서

| 단계 | 하는 일 |
|---|---|
| 준비 | scheduler가 DDR3 트랙을 `pf_*`로 알린다. 빈 buffer가 있으면 받고 DDR3를 읽는다. `RESET_STATE`이면 읽지 않고 바로 준비 완료다. on-chip 트랙은 받기만 하고 무시한다 |
| 시작 | `can_start`(on-chip이거나 준비 완료)일 때 compute array와 같은 cycle에 `start` |
| 연산 | on-chip 트랙은 bank를 바로 읽고 쓴다. DDR3 트랙은 BUSY buffer를 그 자리에서 읽고 쓴다 |
| 되쓰기 | 연산이 끝나면 buffer를 DDR3에 쓰고, 쓰기 응답을 받으면 `wb_done`과 트랙 번호를 낸다. 결과 송신과 request table 칸 비우기는 그 뒤에 한다(03_ARCHITECTURE.md §3) |

buffer 하나로 연산하는 동안 다른 buffer는 앞 트랙을 되쓰고 다음 트랙을 읽는다. 같은 트랙의 다음 추론 요청은 되쓰기 응답 뒤에만 받으므로 DDR3 읽기가 앞 쓰기를 앞지르지 않는다.

`dma`(P4.4)가 맡을 쪽은 아래와 같이 정했다.

| 방향 | 신호 | 규칙 |
|---|---|---|
| 읽기 | `dr_req_valid/ready`, `dr_req_addr` → `dr_valid`, `dr_data` | 추론 요청 하나에 beat 34개를 순서대로 준다. buffer가 자리를 잡아 두었으므로 받는 쪽은 멈추지 않는다 |
| 쓰기 | `dw_req_valid/ready`, `dw_req_addr` → `dw_valid/ready`, `dw_data` → `dw_resp` | beat 34개를 순서대로 받고, 쓰기 응답 뒤 `dw_resp`를 1 cycle 준다 |

## 3. 결과

### 3.1 bit 일치

| 항목 | 값 |
|---|---|
| 추론 | 2,542개(82트랙 × 31) |
| row 불일치 | 0. 전류, 포화 후 membrane potential, spike, 12 bit 저장값 |
| 판정용 출력 불일치 | 0 |
| 끝난 뒤 DDR3 내용 | DDR3 트랙 22개 모두 마지막 timestep의 12 bit 저장값과 같다 |
| DDR3 beat | 읽기 22,440, 쓰기 23,188. 기대값과 같다 |

DDR3의 처음 내용이 쓰레기 값이므로 첫 timestep에 DDR3를 읽어 썼다면 결과가 틀린다. 마지막 대조는 DDR3 배치(§2.2)가 문서대로인지 확인한다. 읽기와 쓰기가 같은 틀린 배치를 쓰면 왕복 대조만으로는 못 잡기 때문이다.

### 3.2 오류를 잡는가

| 고장 | 결과 |
|---|---|
| bank 주소에서 트랙 번호를 뺌 | row 불일치 81,000, 출력 불일치 1,800 |
| `RESET_STATE`여도 DDR3를 읽음 | 읽은 beat 23,188(기대 22,440) |
| 쓸 때 12 bit 포화를 빼먹음 | row 불일치 25,765, DDR3 최종값 불일치 2,128 |
| DDR3에서 읽은 beat 안 chunk 순서를 바꿈 | row 불일치 28,561, DDR3 최종값 불일치 14,007 |
| DDR3에 쓰는 beat의 절반 순서를 바꿈 | row 불일치 28,590, DDR3 최종값 불일치 15,208 |

Verilator로 돌렸다. 다섯 개 모두 FAIL이다.

### 3.3 합성

`hardware/vivado/ooc_timing.tcl`(인자 `p42`), wrapper `p42_timing_top.v`. P4.1 wrapper의 1트랙 RAM을 `membrane_storage`(`N_ONCHIP` 768)로 바꿨다. dma port는 밖으로 냈다.

| 항목 | 첫 합성 | 고친 뒤 |
|---|---:|---:|
| bank BRAM | RAMB36 384 | RAMB36 187 |
| 전체 BRAM tile | 496 (device 365 초과, 배치 안 됨) | 301 |
| WNS ns | — | +0.348 |
| WHS ns | — | +0.100 |

첫 합성에서 Vivado는 34,560 × 192 bit bank를 32K × 1 BRAM 두 단으로 만들었다. 깊이가 32K를 조금 넘었기 때문이다. bank를 깊이 2,048짜리 sub memory 17개로 나누자 sub마다 2K × 18 BRAM 11개(198 bit)가 되어 187개로 줄었다. engine의 `tiles()` 계산값과 같다.

| 대상 | LUT | LUTRAM | FF | RAMB36 | RAMB18 | DSP |
|---|---:|---:|---:|---:|---:|---:|
| `compute_array` | 6,300 | 224 | 2,797 | 0 | 0 | 80 |
| `weight_entry` 1개 | 350 | 342 | 256 | 28 | 1 | 0 |
| `membrane_storage` | 5,953 | 1,056 | 744 | 187 | 0 | 2 |
| ├ `membrane_bank` | 3,460 | 0 | 237 | 187 | 0 | 0 |
| └ `membrane_buf` | 2,491 | 1,056 | 505 | 0 | 0 | 0 |
| wrapper 전체 | 14,913 | 2,802 | 4,589 | 299 | 4 | 82 |

`membrane_bank`의 LUT는 대부분 sub 17개 출력 중 하나를 고르는 192 bit 선택이다. `membrane_buf`의 LUTRAM은 buffer 2개(그룹 16칸 × 64 bit × chunk 12개)다. DSP 2개는 Vivado가 bank 주소 덧셈(`track × 45 + row`)을 넣은 것이다.

가장 느린 경로는 bank 주소 register에서 BRAM 187개의 주소 입력까지 가는 배선이다(여유 0.348 ns). P4.1의 entry BRAM enable 경로(0.311 ns)와 같은 종류다. 전체 설계에서 실패하면 주소 register를 sub마다 복제한다.

## 4. 검증과 한계

- `dma`는 testbench 모델이다. AXI 연결, 우선순위(membrane potential 읽기 > 쓰기 > weight 적재), weight 적재와의 경합은 P4.4에서 본다.
- 준비와 시작 순서는 testbench가 scheduler 대신 정했다. P4.5 `track_scheduler`가 §2.3 규칙을 지켜야 한다.
- buffer가 2개라 앞 트랙의 되쓰기가 늦으면 다음 DDR3 트랙의 준비가 기다린다. testbench 지연에서는 되쓰기와 준비가 연산 시간(평균 5.36 µs)보다 짧았다. 실제 DDR3 지연과 weight 적재가 겹칠 때는 P4.4에서 잰다.
- `N_ONCHIP`은 합성 parameter다. 06_HOST_INTERFACE.md §7의 `N_ONCHIP` register는 만들지 않았다. bank 크기가 합성 때 정해지므로 register로는 더 작은 값만 줄 수 있다.
- DDR3 트랙 하나의 전송은 1,088 B이고 simulation은 1,059 B로 셌다. DDR3 트랙 비율 25 %에서 추론당 약 14.5 B(0.014 KiB) 차이로 DDR3 전송량의 0.2 %다.
- 결과 packet의 포화 flag(bit1)와 `SAT_COUNT`는 만들지 않았다. 16 bit 포화와 12 bit 저장 포화 중 무엇을 셀지 정해지지 않았다.

## 6. 실행

```bash
bash hardware/testbench/run_membrane_storage.sh                                     # vector 생성, lint, xsim, Verilator
vivado -mode batch -nojournal -nolog -source hardware/vivado/ooc_timing.tcl -tclargs p42   # 합성·배치·배선
```

vector는 P4.1과 같은 `hardware/sim/compute_array/vec_m12/`를 쓴다. Vivado report는 `hardware/vivado/build/p42_timing/`에 생긴다.
