# P5.2 보고서: 보드 동작과 RGMII 보정

작성일: 2026-10-25

P4.10에서 만든 `accel_top` bitstream을 AX7A200B 보드에 JTAG로 쓰고, sub1을 임시 Host로 삼아 Ethernet cable로 직결해 시험했다. 처음에는 양방향으로 frame이 깨졌다. 깨진 frame을 분석하니 원인은 FPGA가 PHY로 보내는 송신 clock의 위상이었다. 수신 IDELAY tap과 송신 clock 위상을 실행 중에 바꾸는 register(`LINK_TUNE`)를 넣고, 보드에서 손실을 재어 값을 정했다. 그 값으로 tb_sys와 같은 순서의 보드 시험을 돌려 결과와 membrane potential이 golden과 bit 단위로 같음을 확인했다. 최종 Host(라즈베리파이 5)에서는 아직 시험하지 않았다.

## 1. 요약

### 1.1 환경

| 구분 | 내용 |
|---|---|
| Host | sub1(Xeon W-2255, Ubuntu 24.04). 내장 Ethernet `eno1`(Intel I219-LM)을 보드와 cable로 직결, 192.168.10.1/24 |
| 보드 | AX7A200B. PHY는 MDIO로 설정하지 않고 strap 기본값으로 쓴다. 설명서는 KSZ9031RNX라 하지만 뒤에 MDIO로 읽은 ID는 0x937C·0x4032(JLSemi JL2101 계열)였다([결과 손실 보고서](<P5.3 Result Loss Research Report.md>)). 링크 1000 Mb/s full duplex |
| bitstream | `build_top.tcl`(P4.10 빌드에 `LINK_TUNE`을 더함). sub1에서 JTAG로 쓴다(`program_fpga.tcl`) |
| script | `hardware/board_test/host/p52_link.py`(방향별 frame 손실), `p52_sys.py`(tb_sys 순서의 보드 시험) |
| 입력 | `golden_l64_m12` 80개(모델 40개 × 2), 트랙 80개(on-chip 60, DDR3 20), timestep 31번 |

### 1.2 결과

| 질문 | 답 |
|---|---|
| 처음 상태(송신 90°, 수신 tap 1) | 제어 packet 응답률 58–93%. Host에 CRC 오류가 쌓이고 응답이 없는 요청도 있다 |
| 원인 | 송신 clock이 데이터보다 늦다. 깨진 frame 65개 모두 하강 edge nibble의 bit 5·7(TXD[1]·TXD[3])이 다음 nibble 값으로 바뀌었다 |
| 송신 위상 | 90°에서 −144~−24단계(2.57–0.43 ns 앞)에서 손실 0. 가운데 −80단계(1.43 ns 앞)로 정함 |
| 수신 tap | 송신을 맞춘 뒤 tap 0–28 손실 0(tap 9에서 300개 중 1개), 29부터 늘고 31은 막힘. STA 모델도 만족하는 tap 8로 정함 |
| 오래 확인 | 송신 −80단계에서 tap 15, tap 8 모두 7,500개(1 KiB frame 2,500개 포함) 손실 0 |
| 가속기 결과 | 추론 요청 2,480개의 결과 out0·out1과 필드가 golden과 일치. DDR3 트랙 membrane potential 일치 |
| counter | `CMP_BUSY` 1,331,594 cycle로 tb_sys와 같다. `WEIGHT_BYTES` = `MODEL_LOADS` × 131,648 B, `STATE_BYTES` 1,327,360 B |
| SOFT_RESET·오류 | slot을 둘씩 맞바꿔 쓰고 SOFT_RESET하면 결과 80개 모두 맞고 LATE 80. `ERR_CODE` 3·7, 첫 오류 유지, `ERR_CLEAR` |
| 기본값을 굳힌 bitstream | STA 모든 제약 만족(WNS 0.231 ns, WHS 0.033 ns). `LINK_TUNE`을 쓰지 않고 가속기 시험 PASS, 시험 중 Host CRC 오류 0 |

### 1.3 결론

1. 링크 손실은 보드 불량이 아니라 RTL의 RGMII 송신 clock 위상 설정 때문이었다. 보드 PHY가 TXC를 안에서 늦추는데 FPGA도 90°(2 ns)를 늦춰, PHY가 데이터가 바뀐 뒤에 잡았다.
2. 보정한 뒤 가속기 전체가 보드에서 golden과 bit 단위로 같다. 연산 cycle 합(`CMP_BUSY`)도 simulation과 같다.
3. 찾은 값(수신 tap 8, 송신 −80단계)을 RTL 기본값으로 굳혔다. `LINK_TUNE`은 보드가 바뀔 때 다시 맞추는 손잡이로 남긴다.

## 2. 과정

### 2.1 처음 증상

bitstream을 쓰자 링크는 1000 Mb/s로 올라왔다. 첫 제어 packet부터 응답이 없을 때가 있었다. 응답이 온 packet의 값(ID, VERSION, entry 4, on-chip 768)은 맞았다. 제어 읽기를 보내며 응답 수와 Host NIC의 `rx_crc_errors` 증가분을 셌다.

| 보내는 간격 | 보냄 | 응답 | Host CRC 오류 | 응답 없음 − CRC 오류 |
|---|---:|---:|---:|---:|
| 0 ms | 300 | 279 | 6 | 15 |
| 2 ms | 300 | 200 | 21 | 79 |
| 50 ms | 100 | 66 | 7 | 27 |
| 300 ms | 40 | 32 | 1 | 7 |

Host NIC에는 CRC 오류만 있고 symbol·align 오류는 0이었다. EEE는 링크 상대가 지원을 알리지 않아 꺼져 있었다.

### 2.2 수신 tap부터 의심

빌드 한 번에 25분이 걸려 값마다 다시 빌드할 수 없다. 그래서 수신 IDELAY를 `VAR_LOAD`로 바꾸고, 송신 clock은 MMCM 미세 위상 이동으로 바꿨다. 두 값을 `LINK_TUNE`(0x0318, 06 §7.2)으로 실행 중에 바꾼다.

송신 90° 그대로 수신 tap 0–29를 훑었다. 1 KiB frame을 섞어 tap마다 300개를 보냈고, 응답은 tap과 상관없이 142–202개였다. sampling 시점이 원인이라면 좋은 tap 구간에서는 손실이 0이어야 한다. 그런 구간이 없으므로 수신 timing 문제가 아니었다.

### 2.3 깨진 frame 분석

Host NIC가 FCS가 틀린 frame도 받게(`rx-all`, `rx-fcs`) 하고 1 KiB 읽기 응답을 잡아 기대값과 비교했다. 236개 중 65개가 깨졌다.

| 특징 | 관찰 |
|---|---|
| 틀린 bit | 모두 bit 5(0x20)와 bit 7(0x80). 위 nibble, 곧 TXC 하강 edge에 보내는 TXD[1]·TXD[3] |
| 틀린 값 | 다음 nibble의 값. 예: `00 5a`의 `00`이 `20`으로, 다음 byte 아래 nibble `a`(1010)의 bit 1이 들어왔다 |
| 길이 | 모두 정상 길이(1,082 B). 1–565 byte가 틀렸다 |

PHY가 데이터가 이미 다음 값으로 바뀐 뒤에 잡았다는 뜻이다. 송신 clock이 데이터보다 너무 늦다. PHY 안쪽 TXC 지연과 FPGA의 90°(2 ns)가 더해져 다음 데이터에 너무 가까워진다. 처음에는 설명서의 KSZ9031 값(약 1.2 ns)으로 합을 3.2 ns, 남는 여유를 0.8 ns로 보았지만, 실제 PHY는 다른 칩이라 이 수치는 근거가 없다. 2.1절의 "응답 없음 − CRC 오류"도 대부분 이 송신 오류로 본다. preamble이 깨진 frame은 Host NIC가 frame으로 세지 않기 때문이다.

### 2.4 송신 위상 훑기

수신 tap 1에서 송신 위상을 8단계(0.14 ns)씩 옮겼다. 1단계는 VCO 주기의 1/56인 17.9 ps다.

| 송신 위상(90°에서) | 응답 / 300 | 비고 |
|---|---:|---|
| −224 ~ −184단계 | 0 | 응답 없음 |
| −168단계(−3.00 ns) | 50 | 가장자리 |
| −152단계 | 271 | |
| −144 ~ −24단계(−2.57 ~ −0.43 ns) | 300 | 손실 0 |
| −16단계 | 298 | |
| 0단계(90°, 처음 값) | 190 | |
| +16단계 | 33 | 가장자리 |
| +24 ~ +64단계 | 0 | 응답 없음 |

손실 0 구간은 폭 약 2.1 ns다. 50% 지점(약 −161, +7단계)의 가운데에 가까운 −80단계를 골랐다. 송신을 맞추자 "응답 없음 − CRC 오류"도 0이 되었다.

### 2.5 수신 tap 다시 훑기

송신 −80단계에서 수신 tap을 다시 훑었다. tap 0–28은 300개 모두 응답했다. tap 9에서 1개가 빠졌고, 따로 떨어진 1개다. tap 29는 279개, tap 30은 104개였다. tap 31에서는 FPGA가 다음 `LINK_TUNE` 쓰기를 받지 못해 JTAG로 다시 써서 되돌렸다. 왼쪽 가장자리는 tap 0 아래라 보이지 않는다.

보드만 보면 오른쪽 가장자리(약 tap 30)에서 1.17 ns 떨어진 tap 15가 양쪽 여유가 가장 크다. 그러나 tap 15를 기본값으로 빌드하자 STA가 실패했다(WNS −0.381 ns, RGMII 수신 입력 5개). STA 모델(`ax7a200b_eth.xdc`, 설명서의 KSZ9031 RXC 지연 1.2 ns ± 0.5 ns)에서는 tap 11부터 setup이 음수다. 실제 수신 구간은 모델보다 넓다. 실제 PHY가 다른 칩이라서다. 모델을 보드 하나의 실측으로 고치는 대신, 둘 다 만족하는 tap 8을 골랐다. STA에서 setup 0.232 ns, hold 1.300 ns이고, 보드에서는 오른쪽 가장자리까지 1.68 ns, 왼쪽은 0.62 ns 이상이다. P4.10에서 고른 tap 1도 손실은 0이었지만 왼쪽 여유를 알 수 없다.

### 2.6 최종 빌드

기본값을 수신 tap 8, 송신 −80단계로 굳혀 다시 빌드했다. P4.10 빌드와 비교하면 아래와 같다.

| 항목 | P4.10 빌드 | 최종 빌드 |
|---|---:|---:|
| LUT | 29,417 | 29,403 |
| FF | 20,809 | 20,856 |
| BRAM(tile) | 317.5 | 317.5 |
| DSP | 82 | 82 |
| WNS / WHS(ns) | 0.231 / 0.020 | 0.231 / 0.033 |
| 100 MHz clock 안 WNS(ns) | 0.466 | 0.280 |
| RGMII 수신 setup / hold(ns) | 0.844 / 0.821(tap 1) | 0.232 / 1.300(tap 8) |

100 MHz 여유가 줄어든 것은 배치·배선이 달라진 탓이고, 가장 나쁜 경로는 여전히 RGMII 송신 출력(0.231 ns)이다. `hardware/vivado/build/top/`에는 이 최종 빌드의 report와 bitstream이 있다. sub1의 bitstream은 `~/mmss_jobs/p410_top/accel_top.bit`다.

## 3. 가속기 시험

`p52_sys.py`는 tb_sys와 같은 순서를 Ethernet 너머로 돌린다. 아래 표의 보드 값은 기본값을 굳힌 최종 bitstream(수신 tap 8, 송신 −80단계)에서 `LINK_TUNE`을 쓰지 않고 돌린 결과다. 그 전에 `--link 15,-80`으로 돌린 시험도 PASS였다(`sys_link15_-80.json`). testbench만 볼 수 있는 계층 확인(predictor 표, cache entry)은 뺐다. SOFT_RESET 시험은 cache에 어느 모델이 있는지 모르므로, 모든 slot을 둘씩 맞바꿔 써서 어떤 entry가 남아도 결과가 어긋나게 했다.

| 항목 | 보드 | tb_sys(Verilator) |
|---|---:|---:|
| 모델 40개 적재·다시 읽기 | 2.0 s, 불일치 0 | |
| 제어 packet | 15,600 | 907 |
| 추론 요청·결과 | 2,480 / 2,480 | 2,480 / 2,480 |
| out·필드 불일치 | 0 | 0 |
| batch(구성원 1개 / 2개) | 108 / 1,186 | 10 / 1,235 |
| `MODEL_LOADS` | 1,221 | 1,175 |
| `CMP_BUSY`(cycle) | 1,331,594 | 1,331,594 |
| `CMP_STALL`(cycle) | 4,237,525 | 5,377,700 |
| `STATE_BYTES` | 1,327,360 | 1,327,360 |
| DDR3 트랙 membrane potential 불일치 | 0 | 0 |
| `t_done − t_in` | 6–1,726 µs, 가운데 847 µs | |
| 추론 31 timestep | 0.07 s | 6,850,756 cycle(68.5 ms) |

Batch 구성과 적재 수는 추론 요청이 FPGA에 닿는 시각에 따라 달라서 다르다. `CMP_BUSY`는 연산 cycle의 합이라 데이터로 정해지고, 보드와 simulation이 같다. 이 시험은 timestep마다 모델 40개를 모두 쓰는 cache 최악 부하이고, response time 근거가 아니다.

## 4. 검증과 한계

- Host는 임시로 sub1이다. RGMII 보정은 보드 안 FPGA와 PHY 사이 값이라 Host가 바뀌어도 그대로일 것으로 본다. 라즈베리파이 5에서 다시 확인한다.
- 보드 하나를 실온에서 쟀다. 수신 tap의 왼쪽 가장자리는 보지 못했다.
- `LINK_TUNE`의 송신 위상은 STA가 모른다. STA는 MMCM 정적 위상 90°로 RGMII 출력을 본다. RGMII 입출력은 이 실측을 근거로 하고, `ax7a200b_eth.xdc`의 모델은 고치지 않았다.
- ILA waveform은 보지 않았다. 결과·counter·DDR3 값이 모두 맞아 필요하지 않았다.
- 지연·jitter 측정이 아니다. `t_done − t_in`은 FPGA 안 시각이다. Response time은 P4.9 track generator와 P5.3에서 잰다.
- sub1에서 바꾼 것은 모두 실행 중 설정이라 재부팅하면 사라진다. `eno1`을 192.168.10.1/24로 쓰는 `/run/systemd/network/05-fpga-eno1.network`, FPGA ARP 항목 고정, 옛 PCIe 장치(Xilinx 7022)를 PCI 목록에서 뗀 것이다. netplan의 `eno1` 설정(192.168.0.200, 기본 경로)은 그대로라, 재부팅 뒤 보드를 다시 쓰려면 같은 설정을 다시 넣어야 한다. 그러지 않으면 sub1의 기본 경로가 보드 쪽으로 넘어간다.
- 보드 QSPI에는 옛 PCIe 설계가 남아 있다. 전원을 다시 넣으면 JTAG로 다시 써야 한다.

## 6. 실행

```bash
# sub1(FPGA Host). eno1 = 192.168.10.1/24, 보드 직결
vivado -mode batch -nojournal -nolog -source program_fpga.tcl -tclargs -bit accel_top.bit
python3 p52_link.py tx --rx 1 --lo -224 --hi 64 --step 8       # 송신 위상 훑기
python3 p52_link.py rx --tx -80 --bit accel_top.bit           # 수신 tap 훑기(막히면 JTAG로 되돌림)
python3 p52_link.py check --rx 8 --tx -80 --n 5000            # 오래 확인
python3 p52_sys.py --vec vec_m12 --out result/sys.json         # 가속기 시험(--link "tap,단계"로 값을 덮어쓸 수 있다)
```

결과는 `hardware/board_test/p52_meas/result/`에 있다.
