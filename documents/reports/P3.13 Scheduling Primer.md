## 1. 제안 구성과 실험 조건

제안 구성은 다섯 가지를 함께 쓴다.

| 부분 | 내용 | 바뀌는 곳 |
|---|---|---|
| offset 배정 | 같은 모델의 트랙들이 같은 시각에 추론 요청을 내도록 Host가 frame 경계를 맞춘다(7절) | Host |
| 즉시 입출력 | Host는 frame이 끝나자마자 보내고, FPGA는 연산이 끝나자마자 결과를 보낸다 | Host, FPGA 결과 전송 |
| Grouping | 가장 오래 기다린 추론 요청의 모델을 골라 그 모델의 대기 요청을 모두 처리한다 | 없음(기존 기준선) |
| cache entry 4개, offset-order 교체 | weight 4벌을 BRAM에 두고, 다음에 가장 늦게 쓸 모델을 내보낸다(9절) | FPGA cache 교체 규칙 |
| spike 0 건너뛰기, cycle마다 2개 | spike가 없는 입력은 건너뛰고, L2·L3에서 cycle마다 spike 입력 2개를 더한다(10절) | FPGA compute array |

공통 조건은 L 모델·64 lane, 트랙 1,024개, membrane potential DDR3, 시나리오 6개 × seed 20개다(그림 3은 seed 10, 그림 5는 seed 5). 입출력 지연은 PCIe 실측 표본이다. Ethernet 지연은 아직 재지 않았다. 즉시 입출력과 spike 2개/cycle은 ARCH_SPEC에 아직 없는 가정이다.

## 2. 시스템

| 항목 | 값 |
|---|---|
| 트랙 | 1,024개. 트랙 하나 = 마이크 하나 = 기계 하나 |
| 모델 | 40개. 학습에 쓴 기계 40대(fan·pump·valve 등의 ID)마다 하나. 트랙마다 쓸 모델이 정해져 있다 |
| 모델당 트랙 수 | 정해져 있지 않다. 실험은 트랙마다 모델을 무작위로 정한다. 균등 배정이면 평균 25.6개(1,024 ÷ 40)이고 모델마다 9~45개다. 편중 배정(시나리오 K·SK)이면 가장 많은 모델이 226~258개, 가장 적은 모델이 1~5개다 |
| frame | 추론 요청 하나를 만드는 음성 구간. Host는 64 ms 길이 구간에서 mel 40개를 구하고, 구간을 32 ms씩 앞으로 옮긴다(FFT 1,024 샘플, hop 512 샘플, 16 kHz). 그래서 트랙마다 32 ms에 frame이 하나 끝난다 |
| frame 경계 | frame이 끝나는 시각. 32 ms 간격이다. 첫 경계를 어디에 둘지는 Host가 정한다 |
| 추론 요청 | frame 하나의 mel 40개를 Host가 FPGA로 보낸 것. 트랙마다 32 ms에 하나 |
| 추론 | 추론 요청 하나를 모델에 한 번 통과시키는 것. 추론 요청 1개 = 추론 1번 |
| deadline | 추론 요청이 생긴 시각 + 32 ms. 다음 추론 요청이 오기 전에 끝내야 membrane potential 상태가 이어진다 |
| compute array | 하나. 추론 1번에 dense 22.4 µs, spike 0 건너뛰기 2개/cycle 6.8 µs |
| weight 한 벌 | 모델 하나의 weight와 β·vth. 131,588 B ≈ 128.5 KiB. DDR3에 40벌이 다 있다 |
| entry | BRAM에 weight 한 벌을 두는 자리. 제안은 4개, 비교 구성은 10개 |

## 3. DDR3 전송은 언제 생기나

DDR3 전송은 두 가지다.

| 전송 | 언제 | 크기 |
|---|---|---|
| weight 적재 | 처리할 모델이 BRAM entry에 없을 때(cache miss). 모델을 바꿀 때만 생긴다 | 한 번에 128.5 KiB |
| membrane potential 읽기·쓰기 | 추론마다 트랙의 membrane potential을 DDR3에서 읽고, 끝나면 다시 쓴다 | 추론마다 2.8 KiB |

membrane potential 전송은 어떤 구성이든 같다. 구성마다 달라지는 것은 weight 적재 횟수다.

weight 적재 1번으로 같은 모델의 추론 n개를 이어서 처리하면 추론당 weight는 128.5 KiB ÷ n이다. 이렇게 이어서 처리하는 추론들을 batch라 부른다.

| 처리 방식 | 추론당 weight |
|---|---|
| 추론마다 다른 모델을 적재 | 128.5 KiB |
| 균등 배정에서 주기마다 모델당 1번 적재(batch 크기 평균 25.6) | 5.0 KiB |
| 모델이 entry에 남아 있어 적재하지 않음(cache hit) | 0 |

표의 "KiB/추론"은 측정 구간의 DDR3 전송 byte 전체를 추론 수로 나눈 평균이다. 이 문서의 KiB 값은 따로 적지 않으면 weight와 membrane potential을 합친 값이다. 주기마다 모델당 1번 적재하면 합계는 7.8 KiB/추론이다.

## 4. 응답 시간

추론 요청 하나는 이 순서로 처리된다.

1. 트랙의 frame 하나가 끝난다(frame 경계). Host가 mel을 구한다. 이 시각이 추론 요청 생성 시각이다.
2. Host가 FPGA로 보낸다(입력 지연, 약 0.03 ms).
3. FPGA queue에서 차례를 기다린다(queue 대기).
4. 모델이 BRAM에 없으면 weight를 적재한다(적재 대기, 약 0.04 ms).
5. 연산한다(추론 1번 6.8 µs, batch면 앞 추론들이 끝날 때까지 기다린다).
6. 결과를 Host로 보낸다(출력 지연, 약 0.03 ms).

응답 시간은 1부터 6이 끝날 때까지다. 표의 평균, p99, 최대가 이 값이다. queue 대기와 batch 안에서 기다리는 시간이 대부분이다.

## 5. scheduler가 정하는 것

compute array가 비면 scheduler가 다음을 정한다.

| 결정 | 뜻 | 영향 |
|---|---|---|
| 어느 모델 | 기다리는 추론 요청 중 어느 모델을 처리할지 | weight 적재 횟수, 처리 순서 |
| 몇 개 | 그 모델의 대기 요청을 몇 개 묶을지 | 적재 1번에 처리하는 추론 수 |
| 기다릴지 | 같은 모델의 추론 요청이 더 올 때까지 compute array를 쉬게 할지 | batch가 커져 DDR3 전송량은 줄고 응답 시간은 는다 |

비교한 scheduler는 이렇다.

| scheduler | 고르는 법 | 기다림 |
|---|---|---|
| Grouping | 가장 오래 기다린 요청의 모델, 그 모델의 대기 요청 전부 | 없음 |
| Dysta Method | 적재가 필요 없고 batch가 큰 모델을 먼저 | 없음 |
| Clockwork Method, Shepherd Method | Dysta Method와 비슷하게 적재된 모델·큰 batch 우선 | 없음 |
| Timeout | Grouping과 같음 | 가장 오래된 요청이 정해진 시간(1~8 ms)을 기다릴 때까지 |
| DeepRT Method, Symphony Method | 모델별로 일정 시간 동안 온 요청을 모아서 처리 | 있음 |
| SlackBatch | Grouping과 같음 | deadline을 넘기지 않는 데까지 |

## 6. 기존 scheduler는 왜 둘 중 하나만 줄이나

offset 배정이 없으면 모델 하나의 추론 요청이 32 ms 동안 흩어져 온다. 트랙이 26개인 모델이면 평균 1.2 ms에 하나꼴이다.

- 오자마자 처리하면 응답 시간은 짧다. 하지만 batch가 1~2개라 거의 매번 weight를 다시 적재한다. Dysta Method는 시나리오 U에서 평균 0.25 ms, 85 KiB/추론이다. 추론 3번 중 2번꼴로 적재한다.
- 한 주기의 요청을 다 모아 한 번에 처리하려면 가장 먼저 온 요청이 마지막 요청을 32 ms 가까이 기다려야 한다. deadline도 32 ms라 그렇게는 못 한다. SlackBatch는 deadline을 넘기지 않는 데까지만 기다려 일부를 모은다. 시나리오 U에서 평균 13.4 ms, 8.7 KiB/추론이다.
- Timeout의 기다리는 시간을 1·2·4·8 ms로 바꾸면 두 점 사이에 점들이 생긴다.

기다리는 시간만큼 DDR3 전송량이 줄고 응답 시간이 는다. 그림 2에서 기존 scheduler의 점들이 한 곡선을 따라 늘어서는 이유다. scheduler는 이미 온 요청만 다루므로, 요청이 오는 시각을 바꾸지 않는 한 이 곡선보다 아래로는 못 간다.

## 7. Host offset 배정

offset은 한 주기(32 ms) 안에서 트랙의 frame 경계가 오는 시각이다. 마이크는 쉬지 않고 녹음하므로 frame 경계를 어디에 둘지는 Host가 정한다. 경계를 0, 32, 64 ms에 두어도 3.2, 35.2, 67.2 ms에 두어도 frame 길이와 간격은 같고 모델이 받는 입력의 성질도 같다.

offset 배정은 모델 m의 트랙들이 모두 m × 0.8 ms 근처에 frame 경계를 두게 하는 것이다(32 ms ÷ 40 = 0.8 ms). 모델마다 배정한 이 시각을 offset이라 부른다. 그러면 모델 0의 요청은 0 ms 근처에, 모델 1의 요청은 0.8 ms 근처에 한꺼번에 온다. Grouping은 기다리지 않아도 모델 하나의 요청을 한 batch로 처리한다.

| 시나리오 U | 평균 응답 시간 | KiB/추론 |
|---|---:|---:|
| Dysta Method, offset 배정 없음, entry 10 | 0.25 ms | 85.1 |
| SlackBatch, offset 배정 없음, entry 10 | 13.4 ms | 8.7 |
| 제안(offset 배정, Grouping, entry 4) | 0.06 ms | 7.5 |

Host가 할 일은 트랙마다 첫 frame 경계 시각 하나를 정해 기억하는 것뿐이다. 계산은 늘지 않고 deadline(frame 경계 + 32 ms)도 그대로다. 트랙을 처음 켤 때 frame 몇 개 분량을 버리거나 기다려 경계를 맞추면 된다.

편중 배정(K)에서는 한 모델에 트랙이 240개 안팎 몰린다. 그 모델의 batch 하나가 1.6 ms(240 × 6.8 µs)라 offset 간격 0.8 ms보다 길다. K의 최대 응답 시간이 1.5 ms로 U보다 긴 이유다.

## 8. cache와 jitter

jitter는 같은 모델의 트랙들이 offset 주변으로 흩어지는 폭이다. 기본 실험은 jitter 0.8 ms(offset 간격 하나)다.

모델 0의 트랙 a·b·c, 모델 1의 트랙 d로 예를 들면 이렇다.

| | 도착 시각 | 처리 | weight 적재 |
|---|---|---|---|
| jitter 없음 | a·b·c 0.0 ms, d 0.8 ms | [a b c] 한 batch, 다음 [d] | 모델 0 한 번, 모델 1 한 번 |
| jitter 0.8 ms | a 0.1, b 0.5, c 0.7, d 0.9 ms | a가 오면 바로 [a], b가 오면 [b], c가 오면 [c], 다음 [d] | cache 없음: 모델 0을 a·b·c마다 세 번. cache 있음: 모델 0 한 번(b·c는 cache hit) |
| jitter 3.2 ms | a 0.1, d 0.9, b 1.5, c 2.8 ms | [a], [d], [b], [c] | 모델 0과 1이 섞여 온다. entry가 2개 이상이어야 b·c가 cache hit이다 |

적재와 추론이 0.05 ms 안에 끝나 a를 처리하는 동안 b가 오지 않는다. 그래서 jitter가 있으면 같은 모델의 요청이 따로따로 처리된다. jitter가 offset 간격(0.8 ms)보다 크면 다른 모델의 요청이 사이에 끼어 섞인다.

jitter가 있으면 한 모델의 요청이 두세 번에 나눠 온다. 예를 들어 모델 0의 요청 중 20개가 먼저 오면 Grouping은 그 20개를 바로 처리한다. 나머지 5개는 그 뒤에 와서 따로 처리된다. 그 사이 모델 1의 요청도 처리된다. 이때

- cache가 없으면 5개를 위해 모델 0을 다시 적재한다. offset 배정만 하고 cache를 없애면 50.2 KiB/추론으로 줄지 않는다(표 1).
- cache가 있으면 모델 0이 entry에 남아 있어 다시 적재하지 않는다. 표 1에서 offset 배정과 entry 10을 함께 쓰면 8.9 KiB/추론이다.

"offset 배정 오차를 cache가 흡수한다"는 이 뜻이다. jitter 때문에 나뉘어 온 요청을 cache가 적재 없이 처리한다.

버틸 수 있는 jitter는 entry 수가 정한다. jitter가 3.2 ms면 offset 4개에 걸쳐 모델 4~5개의 요청이 섞여 온다. 섞여 오는 모델을 모두 BRAM에 두려면 entry가 그만큼 있어야 한다. 그림 3에서 entry 2는 jitter 1.6 ms까지 10.4 KiB/추론 이하이고 3.2 ms에서 55로 뛴다. entry 4는 3.2 ms까지 9.3이고 6.4 ms에서 43으로 뛴다. 대략 "entry 수 × 0.8 ms"까지 버틴다. 제안이 entry 4를 쓰는 근거다.

## 9. cache 교체 규칙

entry가 다 찼는데 새 모델을 적재해야 하면 하나를 내보낸다. 무엇을 내보내느냐가 교체 규칙이다.

offset 배정을 하면 모델이 매 주기 0 → 1 → … → 39 → 0 순서로 돈다. 이 순환에서 두 규칙은 크게 다르다(entry 10개 예).

| 규칙 | 내보내는 모델 | 결과 |
|---|---|---|
| LRU | 가장 오래 안 쓴 모델 | 가장 오래 안 쓴 모델이 바로 다음에 다시 쓸 모델이다. 40개 모두 매번 cache miss라 주기마다 40번 적재한다 |
| offset-order 교체 | 다음에 가장 늦게 쓸 모델. 방금 처리한 모델은 한 주기 뒤에야 다시 오므로 가장 늦다. 연산 중인 모델은 내보낼 수 없어 그 직전 모델을 내보낸다 | entry 9개는 같은 모델들(예: 0~8)을 계속 두고, 남은 1개가 나머지 모델을 돌아가며 받는다. 주기마다 9번 hit, 31번 적재한다 |

표 1에서 entry 10은 LRU 8.9, offset-order 교체 7.6 KiB/추론이다. entry 4면 3개를 계속 두고 1개가 돈다. 주기마다 38번 안팎 적재해 8.6 KiB/추론이다.

다음에 쓸 순서가 offset 번호 순서와 같으므로, 하드웨어에서는 "지금 offset 번호에서 각 entry 모델의 offset 번호까지 거리"를 비교하면 된다. 역할은 나뉜다. Host가 모델마다 offset 번호를 정해 시작할 때 한 번 FPGA에 써 준다(40개 표). FPGA는 적재할 때마다 이 표로 내보낼 entry를 고른다. 추론 요청마다 Host와 주고받는 정보는 없다. simulation은 트랙 offset으로 다음 사용 시각을 계산했는데, offset 배정 상태에서는 이 표와 같은 결과다.

## 10. spike 0 건너뛰기와 트랙 한계

SNN의 L2·L3는 앞 layer에서 spike가 난 입력의 weight만 더한다. spike가 없는 입력을 건너뛰면 연산이 준다.

compute array는 64 lane이다. lane 하나가 출력 뉴런 하나를 맡는다. cycle마다 입력 하나의 weight 64개(word 하나)를 읽어 64 lane이 각자 더한다. 그래서 cycle 수 = 처리하는 입력 수다.

| layer | 입력 | dense | spike 0 건너뛰기 1개/cycle | 2개/cycle |
|---|---|---:|---:|---:|
| L1 (384뉴런 = 6 그룹) | mel 40개, spike가 아니라 숫자 | 6 × 40 = 240 | 240 | 240 |
| L2 (256뉴런 = 4 그룹) | L1 spike 384개 중 1인 것 n1개(평균 85) | 4 × 384 = 1,536 | 4 × n1 ≈ 340 | 4 × ⌈n1/2⌉ ≈ 170 |
| L3 (64뉴런 = 1 그룹) | L2 spike 256개 중 1인 것 n2개(평균 109) | 256 | n2 ≈ 109 | ⌈n2/2⌉ ≈ 55 |
| L4 (출력 2개) | | 2 | 2 | 2 |
| 제어 비용(가정) | | 203 | 203 | 203 |
| 합계 cycle(100 MHz) | | 2,237 = 22.4 µs | 903 = 9.0 µs | 676 = 6.8 µs |

dense는 spike가 0인 입력도 cycle을 쓴다. spike 0 건너뛰기는 1인 입력만 처리한다. "2개/cycle"은 cycle마다 1인 입력 두 개의 weight를 읽어 함께 더한다는 뜻이다. BRAM port가 2개라 cycle마다 weight word를 2개까지 읽을 수 있다. n1·n2는 golden vector(SW 정수 모델)에서 추론마다 센 값이다.

| 연산 | 추론 1번 | compute array만 따진 트랙 한계(32 ms ÷ 추론 1번) |
|---|---:|---:|
| dense(모든 입력 계산) | 22.4 µs | 약 1,430 |
| spike 0 건너뛰기, cycle마다 1개 | 9.0 µs | 약 3,540 |
| spike 0 건너뛰기, cycle마다 2개(실험 기본) | 6.8 µs | 약 4,730 |

cycle마다 2개를 더하려면 BRAM의 두 번째 port로 weight를 하나 더 읽고 DSP의 pre-adder로 두 값을 함께 더해야 한다. RTL로 확인하지 않은 가정이다.

spike 0 건너뛰기는 DDR3 전송량을 바꾸지 않는다. 어느 입력에 spike가 날지 미리 모르므로 weight는 다 적재한다. 바뀌는 것은 응답 시간과 트랙 한계다. 그림 5에서 dense는 1,408트랙이 한계이고 1,536트랙에서 과부하가 된다. spike 0 건너뛰기는 1,536트랙에서도 14 ms 이하다.

## 11. deadline 보장

가장 나쁜 경우는 추론 요청 1,024개가 한꺼번에 오는 것이다(시나리오 S). 마지막 요청의 응답 시간은 1,024 × 추론 1번 + weight 적재 1번 + 입출력이다. dense로 계산해도 23 ms라 deadline 32 ms 안이다. compute array를 쉬게 하지 않는 scheduler면 무엇을 써도 같으므로, 1,024트랙의 deadline 보장은 scheduler가 아니라 이 계산에서 나온다.

guard는 deadline을 넘길 것 같으면 처리 순서를 바꾸는 장치다. 제안 구성은 처리 순서를 바꾸지 않고 위 계산으로 deadline이 보장되므로 guard를 쓰지 않는다. 1,024트랙에서는 guard가 있는 scheduler로 재 봐도 한 번도 작동하지 않았다. 동작, 구현, 측정은 GUARD.md에 따로 남겼다.

## 12. 표·그림 읽는 법

비교군(Dysta Method 등)은 그림 2에만 나온다. 나머지는 제안 구성에서 한 가지씩 바꾼 결과다. 표의 값은 시나리오 6개를 합친 값이다.

| 항목 | 무엇을 바꿨나 | 볼 곳 |
|---|---|---|
| 표 1 | offset 배정 끔/켬 × cache(없음, LRU, offset-order) × entry 수 | offset 배정만(50.2 KiB/추론)이나 cache만(52.0)으로는 안 줄고, 둘 다 있어야 8.9로 준다. offset-order 교체를 쓰면 7.6. 평균 응답 시간은 offset 배정이 정한다(1.63 → 0.18 ms) |
| 그림 2 | offset 배정 없이 scheduler 11개, 제안 점 하나 | 기존 scheduler는 DDR3 전송량과 응답 시간을 맞바꾸는 한 곡선 위에 있다. 제안 점만 그 곡선 아래 왼쪽에 있다 |
| 부록 표 | offset 배정을 켜고 scheduler 8개 | 기다리지 않는 4개(Grouping, Dysta Method, Clockwork Method, Shepherd Method)는 같다. 기다리는 4개는 응답 시간만 는다. scheduler는 가장 단순한 Grouping이면 된다 |
| 표 3 | 악조건 5개 × offset 배정 켬/끔 | 둘 다 deadline miss 0. 최대 응답 시간은 offset 배정 켬 9.2 ms, 끔 23.1 ms(가장 나쁜 dense 조건) |
| 그림 3 | jitter × entry 수 | entry 수가 버티는 jitter 폭(8절). entry 4를 고른 근거 |
| 그림 4 | 도착 패턴 7개 | 고르게 나눈 offset(모델과 무관하게 offset을 고르게 나눔)은 무작위와 같다(81.6, 80.6). 모델별로 모아야 7.5로 준다. 교대·지연에도 8.6~12.8 |
| 그림 5 | 트랙 수 × 연산 × offset 배정 | 한계는 compute array다(10절). offset 배정은 한계를 바꾸지 않는다 |

그림 4의 지연 패턴에서 최대 응답 시간 17~18 ms는 늦게 도착한 요청 자체가 최대 16 ms 늦은 탓이다. 가속기 안에서 처리하는 시간은 1 ms 안이다.

## 13. simulator가 흉내 내는 것

[engine.py](../../simulation/engine/engine.py)의 event 단위 simulator다. 시각을 µs로 진행하며 요청 도착, 적재, 연산, 결과 전송을 하나씩 처리한다.

| 대상 | 흉내 내는 방법 | 근거 |
|---|---|---|
| 추론 요청 도착 | 트랙마다 offset + 32 ms × k에 생성. 시나리오가 offset·모델 배정·요청을 빠뜨리는 비율을 정한다. 생성 뒤 입력 지연을 더해 도착 | 입력 지연은 PCIe 64 B 전송 실측 표본(P3.2) |
| 결과 전송 | 연산이 끝나면 출력 지연을 더해 Host 도착 | PCIe 실측 표본 |
| DDR3 전송 | DMA 하나가 순서대로 처리. 전송 한 번 = 0.244 µs + byte ÷ 3,015 MB/s. weight 적재 131,588 B, membrane potential 추론마다 2,824 B(쓰기는 2,768 MB/s) | DDR3 보드 실측 회귀(P3.1) |
| prefetch | 지금 batch를 연산하는 동안 다음 batch의 weight를 비어 있는 entry로 받는다. 한 batch 앞만 본다 | ARCH_SPEC |
| 연산 | 추론마다 10절의 cycle 수 ÷ 100 MHz. batch 안의 추론은 차례로 처리 | ARCH_SPEC §5.2 구조, spike 수는 golden vector |
| cache | entry 수와 교체 규칙(LRU, offset-order)을 그대로 따라간다 | |
| scheduler | compute array가 빌 때마다 정책 코드가 모델과 batch를 고른다 | policies.py |
| 측정 | 16주기를 버리고 다음 64주기(2.048 s)를 잰다 | |

흉내 내지 않는 것: DDR3 refresh와 bank 충돌(회귀식에 평균으로만 들어감), RTL pipeline의 세부 정지(제어 비용 203 cycle로 뭉뚱그림), Host CPU 시간, Ethernet 지연, 전력.

## 14. 용어 모음

| 용어 | 뜻 |
|---|---|
| 추론 요청 | Host가 FPGA로 보낸 입력 하나. 트랙마다 32 ms에 하나 |
| DDR3 전송 | weight 적재와 membrane potential 읽기·쓰기. "요청"이라는 말은 쓰지 않는다 |
| batch | weight 적재 1번으로 이어서 처리하는 같은 모델의 추론들. PROPOSAL의 Channel Window와 같은 것이다 |
| cache hit / cache miss | 처리할 모델이 BRAM entry에 있음 / 없어서 weight를 적재해야 함 |
| deadline miss | 응답 시간이 32 ms를 넘은 추론 요청. 표의 "miss" 열이 이 수다. cache miss와 다르다 |
| offset | 한 주기 안에서 트랙의 frame 경계가 오는 시각(0~32 ms) |
| offset 배정 | Host가 같은 모델 트랙의 frame 경계를 한 시각 근처로 모으는 것. 크기순으로 늘어놓는 sort와 다르다. 표·그림의 "offset 배정 켬/끔" |
| offset | offset 배정 때 모델마다 배정한 시각(0.8 ms 간격). ARCH_SPEC의 DDR3 모델 slot(256 KiB 칸)과 다르다 |
| jitter | 같은 모델 트랙이 offset 주변으로 흩어지는 폭 |
| KiB/추론 | 측정 구간의 DDR3 전송 byte ÷ 추론 수. 평균값이라 추론마다 그만큼 전송한다는 뜻이 아니다 |
| DDR3 MB/s | 측정 구간의 DDR3 전송 byte ÷ 시간. 추론 요청이 최대(초당 32,000개)인 시나리오에서는 KiB/추론 × 32,000이다 |
| 하한 | 주기마다 모델당 weight를 1번만 적재할 때의 값. 시나리오 U에서 weight 5.0, membrane potential 포함 7.8 KiB/추론. offset-order 교체는 cache 재사용으로 이보다 낮아질 수 있다 |
| p99 | 응답 시간을 작은 것부터 늘어놓았을 때 99 % 지점의 값 |
| dense | spike 0 건너뛰기를 끈 연산. 악조건 "dense"는 모든 입력에 spike가 나는 경우라 연산 시간이 같다 |
| 시나리오 | U offset 무작위·균등 배정, K offset 무작위·편중 배정, S 동시 도착, SK 동시 도착·편중, I 주기마다 25 %만 요청, R 주기마다 켜진 트랙 비율 25~100 % 무작위 |
