# P5.3 결과 손실 조사 보고서

작성일: 2026-10-26

P5.3과 P2.9의 보드 실행마다 결과 38–66개(100만 개당 약 8개)가 Host에 오지 않았다. 원인은 sub1의 Host NIC(Intel I219, 칩셋 내장)의 절전이다. 링크가 50 µs 넘게 조용하다가 frame이 다시 오면, NIC가 드물게 약 15 µs 분량의 frame을 오류 표시 없이 잃는다. FPGA RTL, `verilog-ethernet`, 보드 PHY, RGMII timing, 케이블, DDR3 동작, CPU 절전은 원인이 아니다. 최종 Host인 라즈베리파이 5는 NIC가 다른 칩이라 이 문제가 없을 것으로 보지만, 아직 재지 않았다.

## 1. 요약

### 1.1 환경

| 구분 | 내용 |
|---|---|
| 보드 | P5.2 bitstream에 진단 counter와 MDIO master를 더한 것(§4). 수신 tap 8, 송신 −80단계 |
| Host | sub1(Xeon W-2255 workstation). 내장 NIC `eno1`(Intel I219-LM, e1000e)을 보드와 직결 |
| 입력 | P5.3과 같다. 평가 파일 12,671개, 1,024트랙 실시간 166.7 s, 추론 5,330,965개 |
| 관찰 | Host tcpdump(양방향 모든 frame의 앞 96 B), Host NIC·커널 counter, FPGA 진단 counter, 보드 PHY·Host PHY register |

### 1.2 결과

| 조건 | 손실 결과 |
|---|---:|
| 기준(P5.3, P2.9 세 번, 이번 두 번) | 38–66 |
| 송신 위상 −40단계 / −120단계(0.7 ns씩 옮김) | 56 / 65 |
| 보드 PHY를 1000BASE-T master로 고정 | 51 |
| DDR3를 거의 쓰지 않음(모델 4개, 트랙 768개, 추론 3,998,400개) | 31 |
| Host CPU 한 core를 계속 바쁘게 | 44 |
| 링크 100 Mb/s | 0 |
| Host가 쓰지 않는 port로 작은 packet을 쉬지 않고 보냄(초당 약 38만 개) | 0 |

### 1.3 결론

1. 빠진 결과도 FPGA 안에서는 정상 frame으로 MAC 송신 FIFO까지 들어갔다. Host 쪽에서는 tcpdump에도 오류 counter에도 흔적이 없다. Host NIC가 frame을 받기 전 단계에서 소리 없이 잃는다.
2. 손실은 링크가 50 µs 넘게 조용한 뒤 다시 온 frame에서 시작한다. Host가 계속 송신해 NIC를 쉬지 못하게 하면 손실이 0이 된다. 그래서 Host NIC의 절전이 원인이다.
3. sub1에서 1 Gb/s로 시험할 때는 Host가 작은 packet을 계속 보내거나 100 Mb/s로 쓴다. 라즈베리파이 5에서는 같은 시험으로 손실이 없는지 확인한다.

## 2. 조사

### 2.1 손실의 모양

실행 6번에서 손실 사건 111개, 손실 결과 302개다. 사건마다 같은 frame에서 이어진 트랙 1–3개의 결과가 빠진다. 3개를 넘은 적은 없다. 빠진 결과 앞뒤의 결과는 순서대로 오고 중복도 없다. FPGA 시각(`t_done`)으로 보면 결과는 약 5 µs 간격으로 나가므로, 사건 하나는 15–22 µs 동안 FPGA → Host 방향의 frame이 사라진 것이다. Host → FPGA 추론 요청은 모든 실행에서 하나도 빠지지 않았다.

### 2.2 FPGA 안

진단 counter(§4)로 결과가 거치는 단계를 셌다(진단 bitstream 실행).

| 단계 | 수 |
|---|---:|
| frontend `RES_OUT` | 5,330,965 |
| eth_link가 받은 결과 | 5,330,965 |
| UDP 머리 | 5,331,807(결과 + 제어 응답 842) |
| MAC 송신 FIFO good frame | 5,331,808(+ ARP 1) |
| MAC FIFO bad·overflow, 송신 underflow, IP·UDP payload 조기 종료, ARP 실패, 링크 속도 바뀜, 수신 FCS 오류·FIFO overflow | 모두 0 |
| Host가 받은 결과 | 5,330,921(44개 빠짐) |

FIFO 뒤 MAC 송신 경로(`axis_gmii_tx`, `rgmii_phy_if`)에는 frame을 버리는 로직이 없다.

### 2.3 Host 쪽

| 확인 | 결과 |
|---|---|
| tcpdump가 잡은 FPGA 결과 frame | Host program이 받은 수와 같다. 머리가 바뀐 frame, 목적지 MAC이 다른 frame도 없다 |
| NIC counter | 실행 중 CRC·symbol·length 오류, buffer 부족(`rx_no_buffer_count`), 놓침(`rx_missed_errors`), DMA 오류 모두 0 |
| 커널 | UDP 수신 buffer 오류, `rx_dropped` 0 |
| Host PHY reg 10 | 실행 내내 수신 상태 local·remote OK, idle 오류 0 |

P5.3 보고서에 적은 `rx_errors` 17은 bitstream을 쓸 때 링크가 다시 올라오며 생긴 것이고, 실행 중에는 늘지 않는다.

### 2.4 쉰 시간과 손실

결과마다 바로 앞 결과와의 간격(FPGA가 송신을 쉰 시간)으로 나눠 손실을 셌다(`p53_loss_gap.py`, 실행 6번).

| 앞 결과와 간격 | 결과 | 손실 | 100만 개당 |
|---|---:|---:|---:|
| 10 µs 미만 | 30,776,646 | 217 | 7.1 |
| 10~50 µs | 95,918 | 0 | 0 |
| 50~100 µs | 264,957 | 17 | 64 |
| 100 µs 이상 | 848,137 | 68 | 80 |

50 µs 이상 쉰 뒤의 결과는 전체의 3.5%지만 사건 111개 중 85개(77%)가 여기서 시작한다. 10 µs 미만 칸의 손실 217개는 대부분 같은 사건의 둘째·셋째 결과다. 모델 batch 안 위치로 보면 사건 30개가 batch의 첫 결과에서 시작한다. 무작위라면 4–5개다.

### 2.5 원인 가르기

| 가설 | 시험 | 결과 |
|---|---|---|
| RGMII 송신 timing | 송신 위상을 ±0.7 ns 옮김 | 손실 수가 같은 범위, CRC 오류 0. 아니다 |
| 1000BASE-T master/slave(보드 PHY가 slave) | MDIO로 보드 PHY를 master로 고정(Host가 slave) | 51. 아니다 |
| DDR3 동시 switching·전원 | weight 적재 4번, membrane potential DDR3 전송 0 | 100만 개당 7.8(같다). 아니다 |
| Host CPU 절전(C-state) | CPU 한 core를 계속 바쁘게 | 44. 아니다. Response time은 줄었다(§3) |
| 1 Gb/s 물리 계층 | 100 Mb/s | 0 |
| Host NIC 절전 | Host가 쉬지 않고 송신 | 0 |

Host의 송신은 Host NIC의 송신과 FPGA의 수신만 바꾸고, FPGA가 결과를 보내다 쉬는 방식은 그대로다. 그런데도 손실이 사라진다. 그러니 원인은 보드 쪽이 아니라 Host NIC다. NIC가 자기 송수신이 모두 조용할 때 들어가는 절전에서 깨어나는 동안 frame을 잃는다. I219에는 MAC과 PHY 사이 연결이 쉬면 들어가는 저전력 상태(K1)가 있고, e1000e driver에도 1 Gb/s에서 이 상태를 따로 다루는 code가 있다. 다만 NIC 안을 직접 볼 수 없어 K1이라는 것은 추정이다. e1000e에는 이 절전을 끄는 parameter가 없다. ethtool의 EEE는 꺼져 있었다(링크 상대가 알리지 않아 inactive).

## 3. 함께 드러난 것

| 항목 | 내용 |
|---|---|
| 보드 PHY | 설명서는 KSZ9031RNX(주소 011)라 하지만 MDIO로 읽으면 주소 1에서 ID 0x937C·0x4032(JLSemi JL2101 계열)로 응답한다. 주소 0은 broadcast로 같이 응답한다 |
| 바로잡은 문서 | 01 §2, 06 §3의 PHY 이름, P4.10·P5.2 보고서의 KSZ9031 지연 서술, P5.3·P2.9 보고서의 손실 원인, `ax7a200b_eth.xdc`·`accel_top.v` 주석. XDC의 수신 STA 모델은 KSZ9031 값 그대로라 실측보다 좁다 |
| Host response time | Host를 계속 바쁘게 하면(배경 packet 또는 바쁜 core) response time이 평균 4.8 → 2.9 ms, 최대 13.5 → 6.8 ms로 줄었다. P5.3·P2.9의 response time에는 Host 절전에서 깨어나는 시간이 들어 있다. sub1 CPU C-state는 C1 2 µs, C1E 10 µs, C6 133 µs다 |

## 4. 진단 RTL

조사용으로 넣었고 RTL에 남겨 둔다. design_references 주소표에는 넣지 않았다.

| 주소 | 이름 | 내용 |
|---|---|---|
| `0x0108` | MDIO | 쓰기: bit[31:30] op(01 쓰기, 10 읽기), [25:21] PHY 주소, [20:16] reg, [15:0] 데이터. 읽기: bit31 busy, [15:0] 읽은 값. 언제나 쓸 수 있다 |
| `0x0440` | 결과 받음 | eth_link가 frontend에서 받은 결과 |
| `0x0444` | UDP 머리 | udp_complete가 받은 송신 머리(결과 + 제어 응답) |
| `0x0448` | MAC good frame | MAC 송신 FIFO에 정상으로 들어간 frame(UDP + ARP) |
| `0x044C`~`0x0454` | bad·overflow·underflow | MAC 송신 FIFO bad frame, overflow, 송신 underflow |
| `0x0458`~`0x0460` | 조기 종료·ARP | IP payload 조기 종료, ARP 실패, UDP payload 조기 종료 |
| `0x0464`~`0x046C` | 링크·수신 | 링크 속도 바뀜, 수신 FCS 오류, 수신 FIFO overflow |

counter는 32 bit이고 `CNT_CLEAR`와 SOFT_RESET으로 0이 된다. MDIO master(`mdio_master.v`)는 Clause 22 frame을 MDC 1.56 MHz로 보내고, 쉬는 동안 MDC 0·MDIO Z다. MDIO 핀에 pull-up을 걸었다. 자원은 LUT 416개, FF 544개 늘고 timing은 만족한다(WNS 0.095 ns). `tb_mdio`(PHY register 모델), `tb_regs`, `tb_eth`, `tb_sys`(진단 counter 값 확인 포함)가 PASS다. sub1 `~/mmss_jobs/p410_top/accel_top.bit`은 진단 RTL이 없는 P5.2 최종본이고, 진단 bitstream은 `~/mmss_jobs/p410_build/out_mdio/`에 있다.

## 5. 한계

- K1이라는 것은 정황 추정이다. 확인한 것은 "Host NIC가 쉬지 못하게 하면 사라진다"까지다.
- 라즈베리파이 5에서 재지 않았다. 도착하면 같은 입력으로 손실을 잰다. 라즈베리파이의 PHY가 EEE를 켜면 링크가 저전력 idle(LPI)에 들어갈 수 있는데, `verilog-ethernet` MAC은 LPI를 다루지 않는다. EEE 상태도 함께 본다.
- 모든 시험은 보드 한 대, sub1 한 대, 케이블 한 개로 했다.

## 6. 실행

```bash
# sub1. 작업 폴더는 p52_acc_run.sh와 같은 꼴, PT에 p52_sys.py·p53_mdio.py·program_fpga.tcl
BIT=out_mdio/accel_top.bit bash p53_loss_run.sh <작업 폴더> <이름>     # 기준
#   TX=-40(송신 위상) MS=master(보드 PHY) MAP=data/map768.txt BG=1(배경 packet) BUSY=1(바쁜 core)
python3 p53_loss_gap.py data/map.txt <이름>/board_result.csv ...       # 쉰 시간별 손실, batch 안 위치
python3 p53_mdio.py dump                                                # 보드 PHY register
sudo python3 p53_hostphy.py eno1                                        # Host PHY register
```

실행별 요약(`run.log`, `stop.log`, `link.log`, PHY register)과 쉰 시간 분석(`gap.txt`)은 `hardware/board_test/p53_meas/result/loss/`에 있다. 결과 CSV와 pcap은 sub1 `~/mmss_jobs/p52_acc/run_*`에 있다.
