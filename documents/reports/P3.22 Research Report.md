# P3.22 보고서: deadline을 mic 수음 시각부터 재기

작성일: 2026-10-16

deadline의 시작을 "Host가 추론 요청을 만든 시각"에서 "frame 마지막 소리를 mic가 받은 시각"으로 바꿨다(사용자 결정, 2026-10-16). 옛 정의는 mic에서 Host까지 걸린 시간을 어디에도 세지 않아, 소리가 늦게 들어와도 deadline miss로 잡히지 않았다. 이 보고서는 바뀐 정의에서 외부 지연을 0~20 ms로 늘려 가며 방법별 deadline miss와 DDR3 전송량을 다시 본 결과다. 값은 모두 simulation이다.

## 1. 요약

### 1.1 환경

| 구분 | 내용 |
|---|---|
| deadline | frame 마지막 소리의 mic 수음 시각 + 32 ms, Host 결과 수신 기준. 오디오 지연, Host 전처리, 전송, FPGA 처리가 모두 들어간다 |
| 외부 지연 | 새 환경 키 `pre_us`. 모든 추론 요청의 FPGA 도착에 더하고 생성 시각(deadline 기준)은 그대로 둔다. 그래서 deadline을 계산하는 scheduler도 줄어든 여유를 본다 |
| 구성 | L·64 lane, 1,024트랙, entry 4, 남는 BRAM에 12 bit membrane potential, jitter 0.8 ms. 같은 BRAM·trace |
| 방법 | Grouping, Dysta Method, SlackBatch(offset 배정 없음, LRU), 제안(offset 배정, offset-order cache, Grouping) |
| 조건 | 기준, 악조건 겹침(모든 입력 spike + control overhead 20 % 증가 + DDR3 2.0 GB/s) × 외부 지연 0·5·10·15·20 ms |
| 평가 | 시나리오 6 × seed 10, 점 40개, 실행 2,400번. 환경 파일 `p322_e2e_deadline` |

### 1.2 결과

| 질문 | 답 |
|---|---|
| 평상시 deadline miss | 외부 지연 20 ms까지 네 방법 모두 0 |
| 악조건 겹침 deadline miss | 기존 셋은 10 ms에서 5.1 %, 15 ms에서 13.3 %, 20 ms에서 21.5 %. 제안은 20 ms까지 0 |
| SlackBatch의 DDR3 | deadline 여유가 줄어 덜 기다리므로 늘어난다. 0 / 10 / 20 ms에서 7.20 / 9.71 / 17.54 KiB/추론. 제안 6.36과의 차이가 12 %에서 34 %, 64 %로 커진다 |
| worst case 계산의 여유 | FPGA 쪽 보수적 worst case 약 25 ms. 오디오·전처리·링크 지연에 보장하는 몫은 약 7 ms |
| simulator 수정 | offset-order cache가 일정한 도착 지연을 못 따라가 제안의 DDR3를 6.69로 부풀렸다. 고친 뒤 지연과 무관하게 6.36 |

### 1.3 결론

1. mic 기준 deadline에서 제안과 기존 방법의 차이는 줄지 않고 커진다. 기다리지 않는 방법의 DDR3 전송량과 평균 응답 시간 차이는 그대로이고, 악조건에서 deadline miss 차이가 새로 생긴다.
2. 기다려 묶는 방법은 외부 지연이 커질수록 기다릴 여유를 잃어 DDR3 이득이 사라진다.
3. worst case 계산으로 보장하려면 오디오·전처리·링크 지연의 합이 약 7 ms 안이어야 한다. 저지연 오디오 설정(1~4 ms)은 들어가고 기본 설정(10~20 ms)은 들어가지 않는다. 그 범위는 simulation의 실제 응답 시간(제안, 악조건 겹침에서 FPGA 쪽 10.5 ms)에 기댄다.

## 2. 정의

```text
deadline  = t_gen + 32 ms,   t_gen = frame 마지막 샘플을 mic가 받은 시각
응답 시간 = t_done_host − t_gen
          = 수음 → Host 송신(오디오 buffer + 전처리) + Host → FPGA → Host 왕복
```

Host는 block이 들어온 시각과 block 안의 샘플 위치로 `t_gen`을 거꾸로 계산한다. 장치 안의 ADC·USB 지연은 loopback으로 따로 잰다(미정). offset 배정은 frame마다 지연을 더하지 않는다. 자르는 위치만 정하고 소리가 끝난 뒤 기다리지 않기 때문이다. 트랙을 처음 켤 때만 최대 32 ms를 버린다.

## 3. 결과

### 3.1 평상시

| 외부 지연 ms | Grouping 최대 ms | Dysta Method 최대 ms | SlackBatch DDR3 KiB/추론 · 최대 ms | 제안 DDR3 KiB/추론 · 최대 ms |
|---:|---:|---:|---|---|
| 0 | 7.23 | 7.19 | 7.20 · 26.84 | 6.36 · 1.08 |
| 5 | 12.23 | 12.19 | 8.22 · 26.84 | 6.36 · 6.08 |
| 10 | 17.23 | 17.19 | 9.71 · 26.85 | 6.36 · 11.08 |
| 15 | 22.23 | 22.19 | 12.17 · 26.88 | 6.36 · 16.08 |
| 20 | 27.23 | 27.19 | 17.54 · 27.26 | 6.36 · 21.08 |

모든 점에서 deadline miss는 0이다. 기다리지 않는 방법은 응답 시간이 외부 지연만큼 그대로 밀리고 DDR3 전송량은 같다(Grouping 58.92, Dysta Method 56.84 KiB/추론). SlackBatch는 최대 응답 시간을 deadline 직전(약 27 ms)에 맞춰 두고 기다리는 시간을 줄인다. 그래서 batch가 평균 19.2개에서 7.6개로 작아지고 DDR3 전송량이 2.4배가 된다.

### 3.2 악조건 겹침

칸은 deadline miss 비율 / 최대 응답 시간 ms다.

| 외부 지연 ms | Grouping | Dysta Method | SlackBatch | 제안 |
|---:|---:|---:|---:|---:|
| 0 | 0 / 25.2 | 0 / 25.2 | 0 / 28.6 | 0 / 10.5 |
| 5 | 0 / 30.2 | 0 / 30.2 | 0 / 30.2 | 0 / 15.5 |
| 10 | 5.1 % / 35.2 | 5.1 % / 35.2 | 5.1 % / 35.2 | 0 / 20.5 |
| 15 | 13.3 % / 40.2 | 13.3 % / 40.2 | 13.3 % / 40.2 | 0 / 25.5 |
| 20 | 21.5 % / 45.2 | 21.5 % / 45.2 | 21.5 % / 45.2 | 0 / 30.5 |

기존 셋은 모든 입력이 spike이고 DDR3가 느려지면 FPGA 안에서 약 25 ms를 쓴다. offset이 모델별로 모이지 않아 weight 적재를 자주 기다리기 때문이다. 이때는 기다려 묶는 SlackBatch도 기다릴 여유가 없어 Grouping과 같아진다. 제안은 FPGA 안에서 10.5 ms를 써서 외부 지연에 약 21 ms가 남는다.

### 3.3 simulator 수정과 옛 결과

offset-order cache(G)는 다음 사용 시각을 생성 시각의 offset으로 예측했다. 모든 추론 요청의 도착이 일정하게 늦어지면 예측이 그만큼 어긋나, 곧 올 모델을 내보냈다. 하드웨어의 offset 순서 표는 offset 번호의 차이만 보므로 일정한 지연과 무관하다. 그래서 simulator도 일정한 지연(`pre_us`, `tail_us`)만큼 예측을 도착 시각 쪽으로 옮겼다.

| 실험 | 바뀐 점 |
|---|---|
| `p322_e2e_deadline` | 고치기 전 제안 DDR3 6.69 → 고친 뒤 6.36 KiB/추론(외부 지연 5~20 ms). deadline miss·응답 시간은 같음 |
| `p321_adverse` | 외부 지연 행의 제안 DDR3 6.67~6.69 → 6.36. 최대 응답 시간·deadline miss는 같음. P3.21 보고서는 이 DDR3 값을 쓰지 않아 고칠 곳이 없다 |
| `p313_adverse` | 다시 돌렸고 값이 같다(꼬리 700 µs) |
| `p312_latency_adverse`, `p312r_replicate_adverse` | 다시 돌리지 않았다. 꼬리 700 µs 행만 해당하며 `p313_adverse`와 같은 조건이라 바뀌지 않을 것으로 본다 |

## 4. 한계

- 외부 지연은 모든 추론 요청에 같은 값으로 넣었다. 실제로는 mic마다, 주기마다 다르다. 그 jitter는 지금 jitter(생성 offset의 퍼짐)로 따로 넣고 있다.
- jitter를 "자르는 시각의 jitter"로 모델링한다. mic 기준 deadline에서는 실제 jitter가 "Host에 넘어오는 시각"에 있으므로, offset 단위 모아 보내기의 응답 시간 증가를 실제보다 크게 잡는다. 바꾸려면 추론 요청마다 다른 외부 지연을 넣어야 한다(다음 작업).
- 오디오 지연, Host 전처리, Ethernet 지연은 재지 않았다.
