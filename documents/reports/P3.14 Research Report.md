# P3.14 보고서: 폴더 정리와 engine 결과 재생성

작성일: 2026-10-15

2026-10-15에 저장소 폴더를 다시 나눴다. Simulation은 실험마다 따로 짠 옛 스크립트 대신, 환경 파일(변수 값)을 읽는 engine 하나로 돌린다. 이 보고서는 옛 실험을 engine으로 다시 돌려 CSV로 저장하고, 그 값이 옛 결과와 같은지 확인한 결과다. 값은 모두 simulation이다.

## 1. 요약

### 1.3 결론

1. engine은 옛 실험 결과를 재현한다. 다른 곳은 옛 스크립트와 일부러 다르게 둔 두 군데뿐이다.
2. P3.13의 Offset Assignment 없음 점은 offset 난수만 달라 실행별 값이 다르다. 합산 값은 DDR3 0.01 KiB/추론, 평균 0.003 ms, 최대 0.07 ms 안에서 같고 결론은 그대로다.
3. P3.11 bandwidth 하한은 조절값을 고정하면 Dysta Method·Clockwork Method가 1.0 GB/s, Timeout이 0.65 GB/s를 요구한다. 옛 결과의 0.4 GB/s는 bandwidth마다 조절값을 다시 고른 값이다. hardware는 조절값 한 벌로 돌므로 이번 값을 쓴다.
4. 같은 실행을 두 번 하던 환경 2개(`p311L64_fixed`, `p39L64_fixed`)를 지웠다. 1,024트랙 기본 지표는 `…_margin`의 cond 기준 행이 맡는다.
5. engine을 `engine.py` 한 파일로 합쳤다(옛 `sim_core.py`·`policies.py`·`bram_plan.py`와 실행기). 합치기 전과 후 engine으로 모든 환경 파일의 점 981개에서 실행을 하나씩 돌렸고, 출력(response time 배열, BRAM tile 포함)이 모두 같았다. search·tune 환경은 512트랙으로 줄여 돌렸다. 환경 5개(`template`, `p313_jitter`, `p35_combos`, `p312r_replicate_rthr`, `p39L64_cap`)는 결과 CSV도 다시 만들어 같았다.

### 1.4 한계

- engine 요약의 p99는 response time 히스토그램 칸(0.05 ms)의 위 경계다. 옛 표는 아래 경계(P3.13)나 response time 전체의 percentile(P3.8~P3.11)을 써서 p99는 비교하지 않았다.
- 설계별 합산만 남은 옛 결과(P3.8~P3.11)는 합산 지표(추론 요청 수, deadline miss, 평균, 최대, DDR3 KiB, MB/s, batch, hit rate)로만 비교했다.
- 환경 파일이 없는 옛 실험(P3.5 bandwidth sweep, DSE 검증·민감도, XL 비교, p38f·p38s·p38t, p311 전체 조합·XL 등)은 다시 돌리지 않았다. 옛 스크립트와 결과는 비교 뒤 지웠다(§5). 이 실험들의 값은 각 보고서 표에만 남는다.

## 2. P3.13 Offset Assignment 없음 점

옛 `paper_exp.py`는 트랙 offset을 직접 뽑아 넘겼고, engine은 offset을 배정하지 않을 때 offset을 `make_workload`에 맡긴다. 다른 옛 스크립트와 같은 난수 순서를 쓰기 위해서다. 그래서 Offset Assignment 없음 점만 실행별 값이 다르다. 합산하면 아래와 같다.

| 실험 | 점 | 옛 → 새 DDR3 KiB/추론 | 평균 ms | 최대 ms | deadline miss |
|---|---|---|---|---|---|
| 그림 2 | Grouping | 52.04 → 52.03 | 1.629 → 1.629 | 7.31 → 7.25 | 0 → 0 |
| 그림 2 | Dysta Method | 49.47 → 49.47 | 1.559 → 1.560 | 7.25 → 7.22 | 0 → 0 |
| 그림 2 | SlackBatch | 9.47 → 9.47 | 12.434 → 12.433 | 26.87 → 26.89 | 0 → 0 |
| 표 3 | Offset Assignment 없음 · dense | 51.16 → 51.16 | 4.976 → 4.976 | 23.11 → 23.05 | 0 → 0 |
| 그림 4 | 무작위 offset | 80.59 → 80.59 | 0.286 → 0.286 | 1.07 → 1.07 | 0 → 0 |
| 그림 5 | 1,408트랙 dense, synchronized | 6.30 → 6.30 | 15.852 → 15.851 | 31.61 → 31.60 | 0 → 0 |
| 그림 5 | 1,536트랙 dense, synchronized | 3.29 → 3.29 | 129.50 → 129.50 | 368.1 → 367.3 | 430,348 → 430,690 |

표에 없는 Offset Assignment 없음 점(표 1의 3개, 그림 2의 나머지 8개, 표 3의 나머지 4개, 그림 4의 동시 도착, 그림 5의 나머지)도 차이가 이 범위 안이다. Deadline miss 수가 달라진 곳은 이미 과부하였던 dense 1,536트랙뿐이다. P3.13 보고서의 결론과 표 값은 바뀌지 않는다.

## 3. P3.11 bandwidth 하한

시나리오 6 × seed 3, L·64 lane, A·한 번에. Deadline miss 0인 가장 낮은 DDR3 bandwidth(GB/s)이다.

| scheduler | 옛 결과(조절값) | 새 결과(조절값 고정) |
|---|---|---:|
| Grouping | 0.4 | 0.4 |
| Dysta Method | 0.4 (η 0.01) | 1.0 (η 0.0001) |
| Clockwork Method | 0.4 (B) | 1.0 (A) |
| Timeout | 0.4 (W 1 ms) | 0.65 (W 5 ms) |
| Symphony Method | 0.4 | 0.4 |
| Shepherd Method | 1.3 | 1.3 |
| DeepRT Method | 0.65 | 0.65 |
| SlackBatch-Lite | 0.4 | 0.4 |
| SlackBatch | 0.4 | 0.4 |

새 결과는 P3.11 공통 조정 값(1,024트랙 기준 한 벌)을 모든 bandwidth에 그대로 쓴다. 옛 결과는 bandwidth마다 그 정책에 유리한 조절값을 다시 골랐다. 조절값 한 벌로 도는 hardware에는 새 결과가 맞다. P3.11 보고서의 bandwidth 하한 표는 당시 방법의 결과로 남긴다.
