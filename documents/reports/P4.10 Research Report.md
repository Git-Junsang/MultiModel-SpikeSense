# P4.10 보고서: 통합 test와 전체 배치·배선

작성일: 2026-10-25

P4.1~P4.7에서 만든 블록을 `accel_sys`(100 MHz 쪽 전체)와 `accel_top`(MIG, clock, 보드 핀)으로 묶었다. testbench는 Host를 `verilog-ethernet`으로 만들어 RGMII 선으로 잇고, DDR3는 AXI4 slave 모델로 둔다. 06 §6의 시작 순서대로 모델 적재, 설정, 추론, 종료, 오류 처리를 거치며 결과와 membrane potential을 `golden_l64_m12`와 bit 단위로 맞췄다. `accel_top` 전체는 sub1에서 합성·배치·배선해 bitstream까지 만들었다. 보드에는 쓰지 않았고, 보드와 Host(라즈베리파이 5)에서는 아직 재지 않았다.

## 1. 요약

### 1.1 환경

| 구분 | 내용 |
|---|---|
| RTL | `hardware/src/accel_sys.v`(eth_link, ctrl, regs, frontend, accel_core, MIG 입구 선택), `accel_top.v`(MIG, MMCM, IDELAYCTRL, 핀) |
| testbench | `tb_sys.sv`. Host = `verilog-ethernet`(TARGET GENERIC, 125 MHz + 250 ppm), RGMII 선 연결. DDR3 = AXI4 256 bit slave 모델(무작위 ready·지연·beat 간격, ID가 다른 읽기 burst끼리 beat 섞기) |
| 입력 | `golden_l64_m12` 80개(모델 40개 × 2)를 트랙 80개(on-chip 60, DDR3 20)에 두고 timestep 31번 |
| simulation | xsim 2026.1, Verilator 5.020 |
| 빌드 | Vivado 2026.1, `xc7a200tfbg484-2`, sub1, `build_top.tcl`(MIG 포함 전체, RX IDELAY tap 1) |

### 1.2 결과

| 질문 | 답 |
|---|---|
| 결과가 맞는가 | 추론 요청 2,480개의 결과 out0·out1이 golden과 bit 일치(xsim, Verilator). track·seq·model·flag·batch_n·시각 순서도 맞다 |
| DDR3 트랙 membrane potential | 끝난 뒤 DDR3 트랙 20개를 DDR3 창으로 읽어 golden의 마지막 12 bit 저장값과 일치 |
| 시작 순서(06 §6) | MIG 보정 전 DDR3 창 status 2, Ethernet으로 모델 적재 후 다시 읽어 비교, 설정·PNU 표 쓰기, SOFT_RESET, RUN 중 설정·DDR3 쓰기 무시 |
| SOFT_RESET | cache에 있는 두 모델의 slot을 맞바꿔 쓰고 SOFT_RESET하면 entry·counter·`NOW_US`가 비워져 새 weight로 결과가 맞다 |
| counter | `REQ_IN`·`RES_OUT` 2,480, `WEIGHT_BYTES`·`STATE_BYTES`가 DDR3 모델이 센 beat × 32 B와 같다 |
| 오류 | model_id 45 → `ERR_CODE` 3, 첫 오류 유지, `ERR_CLEAR` 뒤 100 B datagram → `ERR_CODE` 7 |

| 자원 | LUT 29,417(21.9 %), FF 20,809(7.7 %), BRAM 317.5 tile(87.0 %), DSP 82. MIG를 뺀 `accel_sys`는 LUT 22,916, FF 15,106 |
| timing | 모든 제약 만족. WNS 0.231 ns(RGMII 송신 출력), WHS 0.020 ns. 100 MHz clock 안 WNS 0.466 ns |
| RGMII 수신 | IDELAY tap 1에서 setup 0.844 ns, hold 0.821 ns |

### 1.3 결론

1. 전체 가속기가 Ethernet 입력부터 결과 송신, DDR3 membrane potential 되쓰기까지 golden과 bit 일치한다. 블록 testbench에서 stub로 두었던 연결(frontend ↔ accel_core, ctrl ↔ MIG, regs ↔ predictor)도 이 시험에서 실제로 돈다.
2. MIG, Ethernet MAC, scheduler를 포함한 전체 설계가 100 MHz에서 배치·배선 timing을 만족한다. 03 §5의 timing 기준을 배치·배선 단계에서 채웠고, 보드 동작은 P5에서 본다.
3. BRAM은 317.5 / 365 tile이다. 04 §2가 링크·request table·준비 buffer에 잡은 50 tile 중 15.5 tile만 쓰여 47.5 tile이 남는다.
4. xsim 2026.1에서만 보이는 X 두 가지를 RTL에서 고쳤다(§4). Verilator는 X를 다루지 않아 두 문제 모두 보지 못했다.

## 2. 통합 구성

### 2.1 accel_sys와 accel_top

| 항목 | 구성 |
|---|---|
| 추론 요청 길 | Ethernet → `eth_link` → frontend → `accel_core` → frontend(result) → `eth_link` → Ethernet |
| 제어 길 | Ethernet → `eth_link` → `ctrl` → `regs`(AXI4-Lite) 또는 DDR3 창(AXI4) |
| reset | `rst`(전원·MIG reset)는 eth_link, ctrl, regs의 설정만 받는다. frontend, accel_core, 시각, counter는 `regs`가 내는 `core_rst`(`rst` 또는 SOFT_RESET)를 받는다 |
| MIG 입구 | `run` = 1이면 dma, 0이면 ctrl의 DDR3 master. `run`은 IDLE에서만 바꾼다(06 §6). ctrl의 run 입력은 `run || !mig_calib`라 MIG 보정 전 DDR3 창 접근은 status 2 |
| clock | sys_clk 200 MHz → MIG → ui_clk 100 MHz(`accel_sys` 전체). ui_clk → MMCM → gtx_clk 125 MHz, 90° 125 MHz, IDELAYCTRL용 200 MHz |
| RGMII 수신 | KSZ9031이 RXC를 약 1.2 ns 늦춰 낸다는 모델로 제약을 둔다(`ax7a200b_eth.xdc`). data 쪽 IDELAYE2 tap으로 맞춘다 |

### 2.2 tb_sys 순서

| 단계 | 내용 |
|---|---|
| 1 | MIG 보정 전: 정보 register(ID, VERSION, N_ENTRY, N_ONCHIP), `STATUS.MIG_CALIB` 0, DDR3 창 읽기·쓰기 status 2 |
| 2 | MIG 보정 뒤 모델 0·1을 1 KiB 제어 쓰기로 DDR3 창에 적재하고 다시 읽어 비교. 나머지 38개는 DDR3 모델에 직접 넣는다. `+FULL=1`이면 40개 모두 Ethernet으로 적재 |
| 3 | 설정 쓰기·읽기, PNU 표(주소마다 다른 값, 그다음 시나리오 값)를 쓰고 predictor 안 값을 계층 이름으로 확인, SOFT_RESET, `STATUS.IDLE`, RUN = 1, RUN 중 설정·DDR3 쓰기 무시 |
| 4 | timestep마다 `NOW_US`를 읽어 `t_host`로 쓰고 추론 요청 80개를 datagram(최대 23개)으로 보낸 뒤 결과 80개를 다 받는다. 31번 |
| 5 | IDLE 뒤 RUN = 0. counter와 DDR3 모델이 센 beat 비교, DDR3 트랙 membrane potential을 DDR3 창으로 읽어 비교 |
| 5b | 두 모델의 slot을 맞바꿔 쓰고 SOFT_RESET, `DEADLINE_US` 1로 timestep 한 번. 옛 entry가 남으면 out이 어긋난다. 결과마다 LATE |
| 6 | model_id 45 → `ERR_CODE` 3·`ERR_INFO` 트랙, 100 B datagram은 첫 오류를 바꾸지 않음, `ERR_CLEAR`, 다시 100 B → `ERR_CODE` 7·`ERR_INFO` 100 |

모든 단계에서 AXI 규칙(valid 유지, 4 KiB 경계, 주소 범위, 주소 전 쓰기 data 없음, wlast)을 본다. RUN이 바뀔 때 DDR3 거래가 없어야 하고, DDR3 트랙 결과는 되쓰기 B 응답 뒤에 나와야 한다. 결과와 DDR3 쓰기 data에 X가 하나라도 있으면 오류다.

## 3. 결과

### 3.1 tb_sys

| 항목 | xsim | Verilator | Verilator `+FULL=1` |
|---|---:|---:|---:|
| 추론 요청·결과 | 2,480 | 2,480 | 2,480 |
| out·필드 불일치 | 0 | 0 | 0 |
| batch(구성원 1개 / 2개) | 14 / 1,233 | 10 / 1,235 | 14 / 1,233 |
| `MODEL_LOADS` | 1,179 | 1,175 | 1,178 |
| `WEIGHT_BYTES` | 155,212,992 | 154,686,400 | 155,081,344 |
| `STATE_BYTES` | 1,327,360 | 1,327,360 | 1,327,360 |
| `CMP_BUSY` / `CMP_STALL`(cycle) | 1,331,594 / 5,224,534 | 1,331,594 / 5,377,700 | 1,331,594 / 5,392,038 |
| 제어 packet | 907 | 907 | 10,711 |
| AXI 위반, 오류 | 0, 0 | 0, 0 | 0, 0 |
| 전체 cycle(100 MHz) | 10,714,344 | 10,873,987 | 55,372,772 |

`STATE_BYTES`는 DDR3 트랙 20개의 읽기 20,400 beat(t0는 `RESET_STATE`라 읽지 않음)와 쓰기 21,080 beat를 더한 값 × 32 B다. 무작위 지연이 simulator마다 달라 batch 수와 적재 수가 조금 다르다.

이 시험은 timestep마다 모델 40개를 모두 쓴다. entry가 4개라 batch 1,245개 중 1,175개가 적재로 시작하고(Verilator), 연산 정지(`CMP_STALL`)가 연산 cycle의 4배다. 적재·정지 경로를 많이 돌리려는 시험이고 성능 근거가 아니다.

### 3.2 오류를 잡는가

Verilator로 돌렸고 9개 모두 FAIL이다.

| 고장 | 들어간 곳 |
|---|---|
| MIG 읽기 ready 선택을 run과 반대로 | `accel_sys` |
| RUN 중 DDR3 창 쓰기 거부 빠짐 | `ctrl` |
| 결과 out0·out1 자리 바꿈 | `result` |
| DDR3 트랙 결과를 되쓰기 완료 전에 보냄 | `result` |
| 1,472 B(추론 요청 23개) datagram을 길이 오류로 | `eth_link` |
| frontend·accel_core가 SOFT_RESET을 받지 않음 | `accel_sys` |
| PNU 표 쓰기가 predictor에 0으로 감 | `accel_sys` |
| LATE와 SAT counter 사건 바꿈 | `accel_sys` |
| `CMP_STALL` 0 | `accel_sys` |

뒤 4개는 독립 검토자가 "지금 testbench로는 못 잡는다"고 낸 것이다. 각각을 잡는 검사(5b SOFT_RESET, PNU 표 계층 확인, 5b LATE 80개, `CMP_STALL`과 DDR3 모델 비교)를 넣은 뒤 FAIL을 확인했다.

### 3.5 timing

| clock | setup WNS(ns) | hold WHS(ns) |
|---|---:|---:|
| ui_clk 100 MHz(`clk_pll_i`) | 0.466 | 0.020 |
| gtx_clk 125 MHz | 1.331 | 0.076 |
| RGMII 수신 125 MHz | 0.844 | 0.118 |
| gtx_clk → RGMII 송신 출력 | 0.231 | 0.235 |
| gtx_clk → 90° clock | 0.426 | |

100 MHz 안에서 가장 나쁜 경로는 req_table의 모델별 대기 수(`cnt`)에서 weight cache 교체 순위(`rank`)로 가는 길이다. logic 17단, 지연 9.45 ns 중 배선이 69 %다. PNU-count가 대기 수로 다음 쓰임을 예측하는 경로다. DRC와 methodology에는 error와 critical warning이 없다.

RGMII 수신 tap은 배선을 그대로 두고 IDELAY 값만 0~31로 바꿔 STA로 쟀다(`rx_idelay_sweep.txt`). IDELAYE2가 없으면 setup 1.24 ns, hold 0.10 ns로 hold 쪽이 좁다. IDELAYE2를 넣으면 tap 0도 지연이 생겨 setup 0.932 ns, hold 0.752 ns가 된다. tap 1에서 setup 0.844 ns, hold 0.821 ns로 가장 고르고, tap 11부터 setup이 음수다. 기본값을 tap 1로 정했다(`accel_top.v`, `build_top.tcl`).

## 4. 고친 것

| 문제 | 원인 | 수정 |
|---|---|---|
| xsim에서 t0 결과가 X | `compute_array`의 부호 확장 함수(`sx12`, `sx15`)를 `accel_sys` 안에서 부르면 xsim 2026.1이 X를 낸다. 블록 testbench에서는 생기지 않았다 | 함수를 지우고 부호 확장을 식 안에 풀어 썼다 |
| DDR3 트랙 되쓰기 data에 X | 트랙의 마지막 beat(row 44)의 위 64 bit는 없는 row 45 자리다. `RESET_STATE`로 DDR3 읽기를 건너뛴 트랙에서는 이 칸이 한 번도 쓰이지 않아 X로 나갔다. X가 제어 응답 frame에 실리면 xsim에서 FCS가 깨져 Host가 frame을 버린다 | `membrane_buf`가 마지막 beat의 위 64 bit를 0으로 낸다 |
| RGMII 수신 제약 | 처음 제약은 RXC 지연이 없는 모델이었다 | KSZ9031이 RXC를 약 1.2 ns 늦춘다는 모델로 바꿨다(`-max 3.3`, `-min 2.3`) |

이 밖에 testbench의 Verilator `-j` 값을 모두 4 이하로 낮췄다(main 메모리).

## 5. 검증과 한계

- 보드와 라즈베리파이에서는 재지 않았다. bitstream은 sub1 `~/mmss_jobs/p410_top/`에 두었고 보드에 쓰지 않았다. RGMII 수신 tap, PHY reset 시간, Linux가 UDP checksum 0을 받는지는 보드에서 본다(P5.2).
- RGMII 수신 timing은 KSZ9031 RXC 지연 1.2 ns라는 data sheet 값의 모델이다. 실제 지연은 보드에서 frame 오류를 보며 tap으로 맞춘다. 보드에서는 송신 90° 설정이 맞지 않아 frame이 깨졌고, 송신 위상 −80단계·수신 tap 8로 다시 정했다([P5.2 보고서](<P5.2 Research Report.md>)).
- 100 MHz 여유가 0.466 ns다. 줄일 곳은 위 `cnt` → `rank` 경로, dma `wr_paddr`(fanout 652), membrane_bank 17:1 선택 회로다. 지금은 만족하므로 고치지 않았다.
- DDR3는 AXI slave 모델이다. MIG의 실제 지연과 refresh는 보드에서 본다.
- 이 시험의 부하는 cache에 가장 나쁜 경우(timestep마다 모델 40개)다. 목표 trace로 RTL 응답 시간을 재는 것은 load generator(P4.9)와 보드에서 한다.
- `+FULL=1`은 Verilator로만 돌렸다(기본 실행에서 xsim 203 s, Verilator 51 s). §4 수정 전후 결과가 같다.
- xsim은 X를 전파하고 Verilator는 하지 않는다. X가 걸린 문제는 xsim에서만 보인다. 두 도구를 함께 쓰는 이유다.

## 7. 실행

```bash
bash hardware/testbench/run_sys.sh                         # lint, Verilator·xsim. PASS가 없으면 0이 아닌 값으로 끝난다
PLUS=+FULL=1 SIMS=verilator bash hardware/testbench/run_sys.sh   # 모델 40개를 모두 Ethernet으로 적재
# sub1에서(공백 없는 경로). 보드에 쓰지 않는다

```

산출물은 `hardware/vivado/build/top/`(timing·utilization·IO·DRC report, `rx_idelay_sweep.txt`, `worst_paths.txt`, bitstream)이다.
