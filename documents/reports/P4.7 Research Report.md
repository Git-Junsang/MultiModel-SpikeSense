# P4.7 보고서: Ethernet 경로와 제어 packet

작성일: 2026-10-24

Host와 FPGA 사이 Gigabit Ethernet 경로(`eth_link`)와 제어 packet 처리기(`ctrl`)를 RTL로 만들었다. MAC과 IP·UDP·ARP는 무료 공개 core `verilog-ethernet`을 고치지 않고 가져다 썼다. testbench의 Host도 같은 core로 만들어 RGMII 선으로 맞대고, 추론 요청·결과·제어 packet을 주고받아 확인했다. RTL simulation과 out-of-context 합성 결과이고, 보드와 Host(라즈베리파이 5)에서는 아직 재지 않았다.

## 1. 요약

### 1.1 환경

| 구분 | 내용 |
|---|---|
| RTL | `hardware/src/eth_link.v`, `ctrl.v`. `hardware/ip/verilog-ethernet/`(commit `77320a9`, MIT, 42개 파일, 원본과 byte 단위로 같음) |
| 규칙 | 06 §4(UDP framing), §7(주소 공간), §7.6(제어 packet) |
| testbench | Host = 같은 core(TARGET GENERIC), RGMII 선으로 연결, Host clock 250 ppm 어긋남. eth_link 뒤에 ctrl, register 모델, 무작위 ready·지연 DDR3 AXI4 모델, frontend 대신 추론 요청을 무작위 지연 뒤 결과로 바꾸는 loopback |
| simulation | xsim 2026.1, Verilator 5.020 |
| 합성 | Vivado 2026.1, `xc7a200tfbg484-2`, out-of-context, 가져온 core의 clock 경계·RGMII 제약 적용 |

### 1.2 결과

| 질문 | 답 |
|---|---|
| 추론 요청이 빠짐없이 순서대로 오는가 | 추론 요청·결과 795개(xsim), 825개(Verilator)가 bit 단위로 같다. 23개짜리 datagram 11개를 선로 속도로 이어 보내도 빠짐이 없다 |
| 길이 오류 | payload 0·1·63·100·1,480 B, 24개(1,536 B), IP 첫 조각(192 B)은 datagram 전체를 버리고 `len_err`에 길이를 낸다. 다른 port의 길이 0, 뒤 IP 조각은 조용히 버린다 |
| 결과·응답 받는 곳 | 결과는 가장 최근 정상 추론 요청의 IP·port로, 제어 응답은 그 요청을 보낸 IP·port로 간다. 결과와 응답이 함께 기다리면 결과가 먼저 나간다(20~25번 확인) |
| 제어 | register·DDR3 창 읽기·쓰기, tag와 머리 되돌림, status 1·2·3, DDR3 1 KiB가 4 KiB 경계를 넘으면 burst를 나눔, 길이가 틀린 쓰기는 하나도 쓰지 않음, AXI 오류 응답이면 status 1 |
| 틀린 frame·ARP | FCS가 틀린 frame(RGMII 선 bit 뒤집기)은 버린다. ARP는 Host → FPGA, FPGA → Host 양쪽 |
| 오류를 잡는가 | 일부러 고장 낸 RTL 20개가 모두 FAIL |
| 자원 | `eth_link` LUT 1,798, FF 3,414, BRAM 4 tile(RAMB36 3 + RAMB18 2). `ctrl` LUT 877, FF 566 |
| timing(합성) | clock 안 WNS: 100 MHz 4.390, 125 MHz 송신 4.183, 수신 3.452 ns. clock 사이는 모두 양수이고 가장 작은 것은 송신 clock 90° 경로 0.131 ns |

### 1.3 결론

1. 공개 core를 고치지 않고 06 §4의 UDP 규칙과 §7.6 제어 packet을 구현했다. MAC 안쪽만 125 MHz이고 IP·UDP·제어는 가속기와 같은 100 MHz다.
2. 가져온 core의 UDP checksum 생성기에 결함이 있어 껐다. header FIFO가 찬 때 들어온 header를 버려 payload와 짝이 어긋난다. FPGA가 보내는 UDP checksum은 0이고 Ethernet FCS는 그대로다(06 §4).
3. 제어 응답이 ARP를 기다리는 동안 다음 제어 datagram이 오면 받는 경로 전체가 멈추는 교착이 검토에서 나왔다. 응답을 기다리는 동안 온 제어 datagram은 버리게 바꿨다. Host는 응답을 받은 뒤 다음 제어 요청을 보낸다(06 §7.6).
4. 링크 BRAM은 4 tile로 04 §2의 링크 예약(PCIe 근거 20.5 tile)보다 작다.

## 2. 설계

### 2.1 eth_link

| 항목 | 구성 |
|---|---|
| MAC | `eth_mac_1g_rgmii_fifo`. 수신 FIFO 8 KiB(FCS가 틀린 frame은 버림), 송신 FIFO 4 KiB(frame 단위). logic clock 100 MHz |
| IP·UDP·ARP | `udp_complete`. 받는 IP가 FPGA IP(192.168.10.2)인 datagram만 받는다. ARP cache 16개, 다시 묻기 2 s, 만료 30 s |
| port 5000 | UDP 머리의 길이를 먼저 보고 0, 64의 배수 아님, 1,472 B 초과면 datagram을 버리고 `len_err`. 맞으면 64 B마다 512 bit word 하나로 frontend에 낸다(빈 cycle 없음) |
| IP 조각 | 조각 offset ≠ 0이면 port와 상관없이 버린다. port 5000의 첫 조각(MF)은 `len_err` |
| port 5001 | payload를 8 bit stream으로 ctrl에 넘기고, ctrl 응답을 그 요청의 IP·port로 보낸다 |
| 송신 | 결과와 제어 응답이 함께 기다리면 결과 먼저. UDP checksum 0 |
| PHY | `phy_reset_n`은 reset 뒤 11 ms 동안 0. MDC 0, MDIO Z(쓰지 않음). 수신 IDELAYE2는 parameter(`RX_IDELAY`, 0이면 없음) |

수신 FIFO를 4 KiB로 두면 23개짜리 datagram 11개(모델 묶음 약 250트랙)를 선로 속도로 받을 때 frame을 잃었다. 그래서 8 KiB다.

### 2.2 ctrl

```text
받기    요청 전체(최대 12 B + 1 KiB)를 buffer에 받은 뒤 실행한다. 길이가 틀린 쓰기는 하나도 쓰지 않는다
검사    형식 오류(머리 12 B 미만, magic, op, count 1~256, 길이) → status 3
        4 B 정렬, regs와 DDR3 창을 넘는 범위 → 1, DDR3 창에서 run = 1 → 2, DDR3 32 B 정렬 → 1, count % 8 → 3
실행    register: AXI4-Lite로 word 하나씩. DDR3 창: 4 KiB 경계에서 나눈 AXI4 burst
응답    요청마다 하나. 머리가 5 B뿐인 요청에도 status 3 응답을 낸다
```

`accel_sys`는 ctrl의 run 입력에 `run || !mig_calib`를 넣는다. MIG 보정 전에 DDR3 창에 접근하면 응답 없이 멈추는 대신 status 2를 낸다.

## 3. 결과

### 3.1 testbench

| 항목 | xsim | Verilator |
|---|---|---|
| 추론 요청·결과 bit 일치 | 795 | 825 |
| 길이 오류 datagram | 8 | 8 |
| 제어 요청 | 35 | 35 |
| 결과·응답 동시 대기에서 결과 먼저 | 20 | 25 |
| cycle(100 MHz) | 172,791 | 174,270 |

무작위 지연이 simulator마다 달라 개수가 조금 다르다. AXI 규칙(valid 유지, 4 KiB 경계, 주소 전 쓰기 data 없음, wlast, run = 1일 때 DDR3 접근 없음), `phy_reset_n` 시간, MDC·MDIO도 본다.

### 3.2 오류를 잡는가

Verilator로 돌렸고 20개 모두 FAIL이다. 길이 상한 1,536 B, 길이 오류 datagram이 결과 받는 곳을 바꿈, 추론 요청 byte 순서 반대, 길이 0 감지 빠짐, 4 KiB 나눔 빠짐, run 거부 빠짐, tag 안 되돌림, ctrl 길이 검사 빠짐, 응답을 결과 port로, 수신 FIFO 4 KiB, 응답을 기다리는 동안 제어 머리를 붙잡음(교착), DDR3 bresp 무시, 바쁠 때도 제어 datagram을 넘김, 뒤 IP 조각 받음, MF 첫 조각 받음, 응답을 결과 IP로, 응답이 결과보다 먼저, AXI4-Lite rresp·bresp 무시, 모든 port의 길이 0에 `len_err`.

### 3.3 검토

독립 검토자 3명의 지적 10개 중 9개를 RTL·testbench에서 고쳤다. 나머지 하나(MIG 보정 전 ctrl 멈춤)는 `accel_sys` 연결로 고쳤다. 첫 합성 보고의 WNS +0.122 ns, WHS −0.553 ns는 clock 경계 제약을 넣지 않은 값이어서, 가져온 core의 제약을 넣고 다시 쟀다(§1.2).

## 4. 검증과 한계

- 보드와 라즈베리파이에서는 재지 않았다. Linux가 UDP checksum 0을 받는지, RGMII 수신 delay(IDELAY tap), PHY reset 시간은 보드에서 확인한다(P5.2).
- 배치·배선과 RGMII 입출력 timing은 P4.10 전체 설계에서 본다([P4.10 보고서](<P4.10 Research Report.md>) §3.5). 합성에서 송신 clock 90° 경로의 여유가 0.131 ns다.
- UDP 머리 길이보다 실제 payload가 짧은 datagram(조각이 아닌데 잘린 경우)은 이미 낸 추론 요청 word를 되돌리지 못한다(코드에 shortcut 주석). Host가 잘못 만든 datagram일 때만 생긴다.
- ctrl이 제어 요청을 처리하는 동안(1 KiB DDR3면 수십 µs) 받는 경로가 멈추고 수신 FIFO 8 KiB가 받는다. Host가 응답 전에 제어 요청을 이어 보내면서 추론 요청도 많이 보내면 넘칠 수 있다. 06 §7.6의 "응답 뒤 다음 요청" 규칙을 지키면 생기지 않는다.
- ARP cache가 빈 상태(FPGA만 reset)에서 결과를 보내는 경우는 시험하지 않았다.
- 도구 문제: Verilator 5.020은 `else if` 조건 안의 queue `pop_front`를 앞 조건과 상관없이 실행했고, xsim 2026.1은 넓은 vector의 part-select를 queue 원소와 `!==`로 바로 비교하면 같은 값도 다르다고 냈다. testbench에서 임시 변수로 피했다.
