# P4.5·P4.6 보고서: Grouping scheduler, request table, register

작성일: 2026-10-24

추론 요청을 받아 batch로 묶고 결과를 내는 쪽(frontend)과 register block을 RTL로 만들었다. frontend는 ingest, req_table, track_scheduler, result로 이루어진다. simulator(Grouping + PNU-count) 실행 6개를 사건 순서대로 RTL에 넣어 교체 계획, batch 구성원, 결과가 simulator와 같은지 확인했다. register block은 06 §7 주소표를 구현한다. 모두 RTL simulation 결과이고, 자원과 timing은 P4.10 전체 배치·배선에서 본다.

## 1. 요약

### 1.1 환경

| 구분 | 내용 |
|---|---|
| RTL | `hardware/src/`의 `ingest`, `req_table`, `track_scheduler`, `result`, `frontend`(P4.5·P4.6), `regs`(P4.6). `compute_array`·`accel_core`에 16 bit 포화 출력 `sat16`과 membrane potential 전송 수 `ev_state_xfer`를 더했다 |
| 기준 | simulator의 `simulate`·`Grouping`·`Queue`(drop 규칙 포함). p326_final_compare 제안 구성(Model-Grouped Offset Assignment, Grouping, PNU-count, entry 4, Xeon CPU 고정·부하 없음 묶음 지연)에서 J, 시나리오, seed, offset 배정만 바꿨다 |
| 대조 방법 | simulator의 사건(연산 완료, 도착, 연산 시작)을 시각 순서로 넣는다. 같은 시각이면 완료 → 도착 → 시작 순서다. accel_core 자리의 stub이 사건 시각에 연산 시작(`go_ready`)과 완료(`done`)를 준다. 사건 사이에는 RTL이 결정할 cycle(96)을 준다 |
| 지정 시험 | 검사 오류, drop, backpressure, 같은 cycle 사건, DDR3 결과 순서 |
| simulation | xsim 2026.1, Verilator 5.020 |

| 출력 사건 | `ev_req_in`·`ev_res_out`·`ev_late`·`ev_sat`·`ev_load`·`ev_batch` 수와 `pending_n`이 testbench가 센 값과 같다 |

| 오류를 잡는가 | 일부러 고장 낸 frontend 17개, regs 20개가 모두 FAIL |
| 포화 flag | 16 bit 연산 포화가 golden의 31 추론과 모두 맞다 |
| 이전 RTL | `compute_array`·`accel_core`를 고친 뒤 P4.1·P4.2·P4.4 testbench가 모두 PASS |

### 1.3 결론

1. Grouping RTL은 같은 queue 상태에서 simulator와 같은 모델을 고르고 같은 구성원을 같은 순서로 batch에 넣는다. 계획은 앞 batch의 첫 추론이 시작된 뒤에 하고, batch 구성원은 첫 추론이 시작되는 cycle에 정한다. simulator의 "batch 시작 시각 s에 다음 batch를 고르고 s까지 도착한 추론 요청을 넣는다"와 같다.
2. RTL은 결과를 보낸 뒤 request table 칸을 비운다. DDR3 트랙은 되쓰기 응답 뒤에 결과를 보내므로 membrane potential 읽기가 앞 쓰기를 앞지르지 않는다. simulator는 연산 완료 시각으로 drop을 판정해 수 µs 차이가 난다. 주기가 32 ms라 정상 동작에서는 차이가 생기지 않는다.
3. 결과 flag의 포화와 `SAT_COUNT`는 16 bit 연산 포화로 정했다. 12 bit 저장 포화는 실데이터 추론의 95 %에서 나서 이상을 알리지 못한다.
4. register는 용도별 블록(06 §7)으로 두었다. PNU 표 창은 predictor 설정 주소에 4를 곱한 자리라 주소 변환 회로가 없다.

## 2. 설계

### 2.1 block

| 파일 | 내용 |
|---|---|
| `ingest.v` | 64 B 추론 요청 검사, req_table 등록, predictor 도착 알림. 2 cycle에 하나 |
| `req_table.v` | 트랙 칸(BRAM), 결과 전 표시(`pend`), 모델별 대기 목록(linked list) |
| `track_scheduler.v` | 가장 오래된 추론 요청 찾기, 교체 계획, 다음 추론 준비(입력 읽기 → `pf` → `go`), batch 시작 때 목록 떼어 내기 |
| `result.v` | 완료 FIFO, 결과 32 B 만들기, 칸 비우기, LATE 판정 |
| `frontend.v` | 넷을 묶는다 |
| `regs.v` | AXI4-Lite slave, 06 §7 주소표, 시각, counter, 오류 |

### 2.2 req_table

| 항목 | 구성 |
|---|---|
| 트랙 칸 | `{RESET_STATE, x}` 321 bit(연산 입력), `{t_in, t_host, seq, model, RESET_STATE}` 87 bit(결과용). BRAM, 읽기 latency 2 |
| `pend[트랙]` | 1,024 bit. ingest가 켜고 결과를 보낸 뒤 끈다. 켜져 있으면 같은 트랙 추론 요청은 drop(ERR_CODE 5) |
| 대기 목록 | 모델마다 head, tail, 수, head의 도착 순번. 트랙마다 다음 트랙 번호 `next[트랙]`(LUTRAM) |

트랙마다 대기 추론 요청은 하나뿐이라 linked list 하나로 충분하다. batch를 시작할 때 그 모델 목록 전체를 떼어 내고 목록을 비운다. 그래서 "시작 뒤 도착한 같은 모델 추론 요청은 다음 batch"가 따로 회로 없이 맞는다. 같은 cycle에 같은 모델을 떼어 내고 추가하면 추가한 추론 요청은 새 목록의 첫 항목이 된다.

### 2.3 track_scheduler

```text
계획    계획된 batch가 없고 대기 추론 요청이 있으면 모델 0~39의 head 도착 순번을 한 cycle에 하나씩 비교해(40 cycle)
        가장 오래된 추론 요청의 모델을 고르고 pl로 알린다. 순번은 32 bit이고 차이로 비교해 돌아도 된다
준비    다음에 시작할 추론 요청 = 지금 batch의 다음 구성원, 다 시작했으면 계획된 batch의 head
        입력을 읽고(2 cycle) pf로 membrane potential을 준비한 뒤 go를 올린다
시작    계획된 batch의 head가 시작되는 cycle에 목록을 떼어 낸다. batch 크기 = 그때 목록 수
완료    done마다 {트랙, 시작·완료 시각, batch 크기, 출력, 16 bit 포화, DDR3 트랙}을 result로 넘긴다
```

계획은 앞 batch의 첫 추론이 시작된 뒤에만 한다. 그래야 weight_cache가 가장 최근 계획의 entry를 연산 중으로 보고 victim에서 뺀다(P4.4 §2.4). 결과 FIFO에 자리가 없으면 `go`를 내리지 않는다.

### 2.4 result와 ingest

| 항목 | 규칙 |
|---|---|
| 결과 순서 | 완료 순서. on-chip 트랙은 바로, DDR3 트랙은 `wb_done` 뒤. membrane_buf가 되쓰기를 완료 순서대로 하므로 `wb_done` 수만 센다 |
| LATE | `t_done > t_host + DEADLINE_US − MARGIN_US`(µs, 차이로 비교) |
| 결과 FIFO | 4개. 3개가 차면 새 추론을 시작하지 않는다 |
| ingest 검사 순서 | magic(1, 정보 = 받은 순번) → track_id(2) → model_id(3) → x > 127(4) → 결과 전 같은 트랙(5). 2~5의 정보는 track_id. `run = 0`이면 오류 없이 버린다 |
| `n_expect` | 4 B를 11 bit로 포화해 predictor에 넘긴다 |

### 2.5 regs

06 §7 주소표 그대로다. 정해지지 않았던 부분은 아래와 같이 정했다.

| 항목 | 정한 것 |
|---|---|
| 시각 | `NOW_US`는 100 cycle마다, `phase_us`는 0~31,999를 돌고 넘칠 때 `epoch` +1. SOFT_RESET(`core_rst`)에서 모두 0. Host는 SOFT_RESET 뒤 clock 차이를 다시 구한다 |
| `first_epoch` | core_rst 뒤 1, 첫 phase 넘김에서 0. 16 bit `epoch`가 돌아(약 35분) 0이 돼도 다시 1이 되지 않는다 |
| SOFT_RESET | `core_rst`를 4 cycle 내고 RUN을 0으로. 제어 경로(eth_link, ctrl, regs 설정)는 지우지 않는다. SOFT_RESET이 제어 packet으로 오기 때문이다 |
| 64 bit 값 | 값마다 HI 그림자를 두고 LO를 읽을 때 잡는다 |
| 쓰기 | `wstrb`가 4'hF일 때만. 범위 밖 설정 값은 무시 |
| 오류 | 같은 cycle이면 ingest(1~5) > dma(6) > Ethernet 길이(7). 첫 오류만 남는다 |

### 2.6 포화 flag

| 포화 | golden_l64_m12 실데이터 2,400 추론 | 포화 시험 vector |
|---|---|---|
| 12 bit 저장(±2,048) | 추론 2,276개(95 %). 저장값 중 layer 2 5.8 %, layer 3 43.5 % | — |
| 16 bit 연산(`sat16`) | 0 | positive 30 추론 모두 |

12 bit 저장 포화는 P3.19에서 정한 양자화의 일부라 늘 난다. 16 bit 연산 포화는 실데이터에서 0이라, 입력이 학습 분포를 벗어났는지 알리는 지표가 된다. `plift_core`가 lane마다 포화 bit를 내고 `compute_array`가 추론마다 OR한다(row 44는 lane 0·1만).

## 3. 결과

### 3.1 simulator 대조

| 기록 | offset 배정 | J ms | 시나리오 | 추론 요청 | batch(평균 / 최대) | miss 계획 | 여러 모델 대기 계획 |
|---|---|---:|---|---:|---|---:|---:|
| t0 | 모델별 | 0.8 | uniform | 24,576 | 22,249 (1.1 / 8) | 911 | 0 |
| t1 | 모델별 | 3.2 | skewed | 24,576 | 19,380 (1.3 / 26) | 1,678 | 1,445 |
| t2 | 모델별 | 0 | skewed-synchronized | 24,576 | 1,010 (24.3 / 243) | 910 | 0 |
| t3 | 모델별 | 1.6 | fluctuating | 15,242 | 14,660 (1.0 / 5) | 939 | 60 |
| t4 | 모두 같음 | 0.8 | uniform | 24,576 | 1,800 (13.7 / 39) | 1,346 | 1,495 |
| t5 | 없음 | 0.8 | uniform | 24,576 | 18,997 (1.3 / 6) | 16,993 | 18,232 |

1,024트랙, 앞 8 + 뒤 16주기. 모든 기록에서 불일치는 0이고 drop은 0이다. 모델별 offset 배정에서는 모델끼리 0.8 ms씩 떨어져 도착해 계획할 때 대기 모델이 대개 하나다. 그래서 가장 오래된 추론 요청 고르기는 t1·t4·t5가 시험한다.

처음 대조에서 계획할 때 queue 상태가 47번 달랐다. testbench가 시각을 µs로 내린 값으로 "같은 시각 도착"을 판단해 실제로는 다른 시각인 도착을 이어서 넣었기 때문이다. 기록에 "다음 사건과 시각이 정확히 같음" bit를 더해 고쳤다.

### 3.2 지정 시험

| 시험 | 확인 |
|---|---|
| 검사 오류 | magic(받은 순번 0과 8), track_id 1,000(N_TRACKS 1,000)과 0x8005, model_id 40과 0x45, x byte 0·8·39가 128 이상, 각 code와 정보 |
| run = 0 | 오류 없이 버리고 REQ_DROP만 |
| drop | 연산 중, 연산 뒤 결과 전(on-chip·DDR3) 같은 트랙은 ERR_CODE 5. 결과를 보낸 뒤에는 받는다 |
| `n_expect` | 5,000·2,048 → 2,047, 2,047 → 2,047, 100 → 100 |
| backpressure | 결과 출력을 막으면 시작한 추론 3개, 풀면 6개 결과가 batch 크기 6으로 순서대로 |
| 같은 cycle | batch 시작 cycle에 같은 모델 추론 요청이 req_table에 들어오면 다음 batch(크기 1)로 간다 |
| DDR3 결과 대기 | DDR3 완료 → on-chip 완료 → 60 cycle 뒤 `wb_done`. `wb_done` 전에는 결과가 없고, 뒤에 두 결과가 완료 순서대로 |

### 3.3 regs

xsim·Verilator 모두 3,235,019 cycle에서 쓰기 92, 읽기 223, 검사 310개와 cycle마다 시각 대조를 했다. phase는 실제로 한 번(3.2 M cycle) 넘겼고 `epoch` 0xFFFF → 0은 hierarchy로 값을 넣어 시험했다. AXI4-Lite는 주소·data 같은 cycle 21, 주소 먼저 37, data 먼저 36번, 응답 대기(bready·rready)를 섞었다.

### 3.4 오류를 잡는가

Verilator(regs는 xsim도)로 돌렸다. 모두 FAIL이다.

| 대상 | 고장 |
|---|---|
| frontend 17개 | 가장 최근 추론 요청 고름, 목록 연결 안 함, 같은 cycle 추가가 이번 batch에 듦, drop 검사 빠짐, LATE 부호 반대, pf 건너뜀, 출력 필드 뒤바뀜, 결과 FIFO 한계 하나 틀림, 계획을 batch 시작 전에 함, batch 크기 하나 틀림, DDR3 결과가 wb_done을 안 기다림, hit에도 ev_load, pending_n 0, magic 정보 0, n_expect 자르기, track_id 위 bit 무시, x byte 39 검사 빠짐 |
| regs 20개 | phase 32,000에서 넘김, HI 그림자 없음·공유, 오류 우선순위·첫 오류, PNU 창 RUN gating, wstrb 무시, core_rst 3 cycle, STATE_BYTES 계산, cfg 주소, N_TRACKS 1,025, NOW_US 101 cycle, bvalid·arready handshake, SOFT_RESET 뒤 RUN, MAX_PENDING clear, `first_epoch` 정의 |

frontend 고장 중 7개(DDR3 결과 대기, ev 출력, pending_n, magic 정보, n_expect, 위 bit, x 마지막 byte)는 처음 testbench가 통과시켰다. 독립 검토가 찾은 빈틈이고 시험을 더해 잡았다. "가장 최근 추론 요청을 고름"도 모델별 offset 기록만으로는 통과해서 t4·t5를 더했다.

## 4. 검증과 한계

- accel_core는 stub이다. 실제 weight 적재·membrane potential 준비 시간과 함께 도는 것은 P4.10 통합 test에서 본다. 대조는 사건 사이에 RTL이 결정할 cycle을 주므로, RTL이 결정하는 데 걸리는 시간(가장 오래된 추론 요청 찾기 40 cycle, 입력 읽기·pf)이 응답 시간에 더하는 몫은 여기서 재지 않았다.
- drop은 결과를 보낸 뒤 칸을 비울 때까지 유지된다(§1.3). simulator와 다른 경우는 같은 트랙의 다음 추론 요청이 연산 완료 뒤 결과 송신 전(수 µs)에 올 때뿐이다.
- `MAX_PENDING`은 batch에 아직 들지 않은 대기 추론 요청 수의 최대다.
- regs에서 시험하지 않은 것: `NOW_US`·32 bit counter가 도는 경우, 4 B 정렬이 아닌 주소(아래 2 bit를 무시한다), clear와 같은 cycle의 사건(버린다).
- 자원과 timing은 P4.10 전체 배치·배선 결과로 적는다([P4.10 보고서](<P4.10 Research Report.md>) §3.4, §3.5). 1,024 bit `pend`와 모델 40개 목록의 선택 회로가 가장 클 것으로 본다.
