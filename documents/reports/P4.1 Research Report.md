# P4.1 보고서: compute_array와 plift_core RTL

작성일: 2026-10-17

추론 하나(`40→384→256→64→2`)를 처리하는 64 lane compute array를 RTL로 만들었다. golden_l64 82개와 bit 단위로 맞는지, 추론 하나에 몇 cycle이 드는지, 100 MHz에서 timing이 맞는지 확인했다. cycle은 simulation, timing은 out-of-context 배치·배선 결과다. 보드 실측은 아니다.

## 1. 요약

### 1.1 환경

| 구분 | 내용 |
|---|---|
| RTL | `hardware/src/`의 `plift_core`, `plif_array`, `mac_unit`, `spike_list`, `weight_entry`, `compute_array` |
| 기준 | `hardware/data/golden_l64/`(16 bit 저장)와 `golden_l64_m12/`(12 bit 저장) 각 82개(실데이터 80, 포화 시험 2), [snn_int8.py](../../software/model/snn_int8.py) |
| simulation | xsim 2026.1, Verilator 5.020. vector마다 31 timestep, 첫 timestep은 `RESET_STATE` |
| membrane potential | testbench가 golden의 저장 bit(16 또는 12)로 포화해 들고 있다. RTL 저장은 P4.2 `membrane_bank`에서 한다 |
| 합성 | Vivado 2026.1, `xc7a200tfbg484-2`, out-of-context, clock 10 ns. `compute_array` + entry 4개 + entry 출력 4:1 mux + membrane potential RAM 1트랙 |

### 1.2 결과

| 질문 | 답 |
|---|---|
| bit 일치 | 16 bit·12 bit golden 각각 추론 2,542개, row 114,390개에서 전류, 포화 후 membrane potential, spike, 저장한 membrane potential, 판정용 출력이 모두 일치했다(xsim, Verilator 둘 다) |
| 연산 cycle | 실데이터 평균 535.9 cycle(5.36 µs), 최대 621. 모든 spike가 1인 포화 시험이 1,205로 가장 길다. 기준 2,237 이하 |
| control overhead | 67(실데이터 전부). 설계 가정은 203이었다 |
| spike 2개/cycle | entry BRAM 두 번째 port와 DSP pre-adder로 구현했다. DSP 64개가 모두 D port를 쓴다 |
| timing | 100 MHz 통과. WNS +0.311 ns, WHS +0.059 ns. 가장 느린 경로는 FF 1개가 entry BRAM 출력 register enable 전체로 가는 배선(8.9 ns)이다 |
| resource | `compute_array` LUT 5,027, FF 2,783, DSP 80. entry 1개 28.5 tile(RAMB36 28 + RAMB18 1), 4개 114 tile |

### 1.3 결론

1. 정수 연산은 SW reference와 같다. layer 2·3 전류를 넓은 폭으로 더한 뒤 16 bit로 포화하는 규칙도 포화 시험으로 확인했다.
2. control overhead는 가정의 1/3이다. 실데이터 평균 추론 시간이 6.8 µs(가정)에서 5.36 µs로 준다. simulation의 control overhead 203을 67로 바꾸면 평균 응답 시간과 트랙 한계가 달라진다. design_references 수치는 아직 바꾸지 않았다.
3. 첫 배선에서 PLIF 한 cycle 경로가 10.8 ns로 실패했다. 누설 곱 뒤에 register를 넣어 고쳤고 control overhead가 63에서 67로 늘었다. 우려했던 entry 출력 mux와 adder tree는 첫 배선부터 통과했다.

## 2. 설계

### 2.1 block

| 파일 | 내용 |
|---|---|
| `plift_core.v` | 뉴런 1개. 선행 `plift_core.v`에서 전류 폭을 17 bit로 넓히고, 되감기를 포화로 바꾸고, 누설 곱 뒤에 register를 넣었다 |
| `plif_array.v` | `plift_core` 16개. cycle마다 row 하나(뉴런 16개), latency 2 |
| `mac_unit.v` | lane 1개. `p = clr ? m : p + m`, `m = (a + d) × b`. DSP48E1 하나에 들어간다 |
| `spike_list.v` | spike가 1인 뉴런 번호 목록. 16 bank에 돌아가며 넣어 cycle마다 16개 쓰기, 2개 읽기 |
| `weight_entry.v` | entry 1개. word RAM 2,048 × 512 bit(true dual port, 읽기 latency 2), params RAM 64 × 256 bit |
| `compute_array.v` | 명령 생성 FSM, 64 lane, shadow register, layer 4 adder tree, PLIF row 처리 |

lane 입력은 layer마다 다음과 같다.

| layer | a | d | b |
|---|---|---|---|
| 1 | W1 (port A) | 0 | mel 입력 x_q |
| 2·3 | spike 1번째 input의 weight (port A) | 2번째 input의 weight (port B), 없으면 0 | 1, 빈 cycle은 0 |
| 4 | W4[k][j] (port A) | 0 | s3[j] |

dma는 연산 중이 아닌 entry에만 쓴다. 그래서 연산 중인 entry의 port B는 두 번째 word 읽기에 쓸 수 있다. 03_ARCHITECTURE.md §6의 "두 번째 port를 DMA 쓰기와 나눠 쓰는 방법"은 이 규칙으로 정했다.

### 2.2 단계

```text
cycle 0   명령 register (FSM)
cycle 1   목록 읽기 결과 → word 주소 → entry
cycle 3   entry 출력 → mac_unit 입력
cycle 6   누산 enable·clear
cycle 7   누산 결과 → shadow register (layer 4는 adder tree, 3 cycle)
P0        row마다 membrane potential·params 읽기 주소
P2        plif_array 입력
P4        membrane potential 쓰기, spike 목록 쓰기
```

그룹 누산이 끝나면 64개 값을 shadow register에 잡는다. PLIF는 4 cycle에 row 4개를 처리하고, 그동안 다음 그룹을 누산한다. spike 0 건너뛰기 그룹이 4 cycle보다 짧으면 shadow를 비우기 전에 덮으므로 최소 4 cycle로 채운다. 채운 cycle은 b = 0이다. 실데이터는 n1이 22 이상, n2가 72 이상이라 채울 일이 없었다.

### 2.3 control overhead

layer 경계마다 앞 layer의 PLIF가 끝나야 다음 layer를 시작한다. 다음 layer의 input 목록이 그때 완성되기 때문이다. 경계 한 곳에서 기다리는 시간은 누산 단계(7 cycle), row 4개 처리, PLIF 단계, FSM 전환을 합쳐 약 17 cycle이다.

| 구간 | cycle |
|---|---:|
| layer 1→2, 2→3, 3→4 경계 | 각 약 17 |
| layer 4 adder tree와 마지막 PLIF | 약 16 |
| 합계(측정) | 67 |

spike가 하나도 없는 포화 시험(negative)은 빈 cycle 20개가 더해져 87이다.

## 3. 결과

### 3.1 bit 일치

| 항목 | 값 |
|---|---|
| vector | 82개(모델 40개 × 정상·이상 + 포화 시험 2개) |
| 추론 | 2,542개(82 × 31) |
| 대조 row | 114,390개(추론마다 45 row) |
| 불일치 | 16 bit·12 bit 저장 모두 layer 1~4 0. `out_mem0`·`out_mem1`도 일치 |

testbench는 모델 image(`model.slot.bin`)를 entry port로 써 넣는다. slot에서 만든 word는 실데이터 모델 40개의 `entry.hex`와 같았다. vector가 바뀌어도 membrane potential을 지우지 않으므로 `RESET_STATE`가 동작하지 않으면 다음 vector의 첫 timestep이 틀린다.

### 3.2 연산 cycle

| 입력 | cycle 평균 | 최소 | 최대 |
|---|---:|---:|---:|
| 실데이터 2,480 추론 | 535.9 | 389 | 621 |
| 포화 시험 positive (spike 전부 1) | 1,205 | 1,205 | 1,205 |
| 포화 시험 negative (spike 없음) | 329 | 329 | 329 |

실데이터 평균 spike 수는 n1 85.6, n2 108.9다. 계산식 `240 + 4⌈n1/2⌉ + ⌈n2/2⌉ + 2`의 평균은 468.9 cycle이고 측정값과의 차이 67 cycle이 control overhead다. 같은 입력에 가정 203을 넣으면 671.9 cycle이다.

### 3.3 합성

`hardware/vivado/ooc_timing.tcl`(인자 `p41`), wrapper `p41_timing_top.v`. out-of-context, clock 10 ns, `opt_design` → `place_design` → `phys_opt_design` → `route_design`.

| 항목 | 첫 배선 | 고친 뒤 |
|---|---:|---:|
| WNS ns | −0.758 | +0.311 |
| 실패 endpoint | 256 | 0 |
| WHS ns | +0.068 | +0.059 |
| control overhead | 63 | 67 |

첫 배선의 실패 256개는 모두 `plif_array` 출력이었다(16 lane × 16 bit). 누설 곱(DSP, register 없음 3.2 ns) → 적분 → 포화 → 발화 → soft reset이 한 cycle에 묶여 10.8 ns였다. 곱 뒤에 register를 넣었다.

| 대상 | LUT | LUTRAM | FF | RAMB36 | RAMB18 | DSP |
|---|---:|---:|---:|---:|---:|---:|
| `compute_array` | 5,027 | 224 | 2,783 | 0 | 0 | 80 |
| ├ `plif_array` | 1,701 | 0 | 672 | 0 | 0 | 16 |
| ├ `spike_list` 2개 | 898 | 224 | 61 | 0 | 0 | 0 |
| └ 64 lane, FSM, adder tree 등 | 2,428 | 0 | 2,050 | 0 | 0 | 64 |
| `weight_entry` 1개 | 351 | 342 | 0 | 28 | 1 | 0 |
| wrapper 전체 | 8,446 | 1,745 | 3,831 | 116 | 4 | 80 |

wrapper 전체에는 entry 4개, 출력 mux, membrane potential RAM 1트랙(RAMB36 4)이 들어 있다. entry 1개는 28.5 tile로 P3.4 계산과 같고 04_MEMORY.md의 29 tile보다 작다. params RAM은 LUTRAM(342 LUT)으로 갔다. DSP 80개는 lane 64개와 PLIF 16개이고 lane 64개가 모두 pre-adder(D port)를 쓴다.

가장 느린 경로(여유 0.311 ns)는 연산 단계 2의 FF 1개(`c_bv`)가 entry 4개 BRAM 116개의 출력 register enable로 가는 배선이다. 논리는 0단이고 배선만 8.9 ns다. 전체 설계에서 배치가 달라지면 여기부터 실패할 수 있다. 그때는 이 신호를 entry마다 복제한다.

## 4. 검증과 한계

- 12 bit 저장은 testbench가 흉내 냈다. `compute_array`는 16 bit 결과를 내고 저장할 때만 포화한다는 interface가 `golden_l64_m12`의 규칙(판정용 출력은 저장 전 값)과 맞는지까지 확인했다. 12 bit로 저장하면 다음 추론으로 넘기는 값 가운데 ±2,048을 넘는 것이 layer 2에서 7 %, layer 3에서 45 %라 실데이터 80개가 모두 golden_l64와 값이 다르다. 판정은 같다(P3.13). RTL 저장 포화는 P4.2에서 `golden_l64_m12`로 확인한다.
- entry는 testbench가 직접 쓴다. dma(P4.4), cache 교체와 연산 중 entry 보호(P4.3), 적재가 늦을 때 연산 정지는 아직 없다. `compute_array`는 entry가 준비된 뒤 `start`를 받는다고 가정한다.
- timing은 out-of-context 결과다. MIG·Ethernet MAC·scheduler와 함께 배치하면 달라질 수 있다. I/O 경로는 보지 않았다. 여유가 0.311 ns로 작다(§3.3).
- layer 경계 대기(약 17 cycle × 4)는 다음 layer가 목록이 다 차기 전에 시작하면 줄일 수 있다. 지금 값으로도 가정보다 작아 하지 않았다.
