# P4.4 보고서: DMA와 prefetch RTL

작성일: 2026-10-24

DDR3와 on-chip memory 사이 전송을 맡는 `dma`를 RTL로 만들었다. weight 적재와 DDR3 트랙의 membrane potential 읽기·쓰기를 AXI4 master 하나로 처리한다. compute array, weight cache, membrane storage, dma를 `accel_core`로 묶고, 적재가 늦으면 연산을 멈추는 조건과 정지 cycle counter를 넣었다. golden 82개를 DDR3 모델과 함께 돌려 bit 일치, 전송 완료, AXI backpressure를 확인했다. DDR3는 testbench의 AXI slave 모델이고 보드 실측이 아니다. timing은 out-of-context 배치·배선 결과다.

## 1. 요약

### 1.1 환경

| 기준 | `golden_l64_m12` 82개(실데이터 80, 포화 시험 2), 모델 42개. DDR3 모델의 slot 0~39는 `models.ddr.bin`의 slot 0~39와 byte 단위로 같다 |

### 1.3 결론

1. dma가 slot 앞 131,648 B를 entry에 옮기는 배치(beat 0~45는 params row, 그다음 beat 2개가 word 하나)가 export 형식과 같다. 연산이 읽지 않는 word까지 entry 전체가 slot과 같다.
2. 다음 batch의 모델을 지금 batch 연산 중에 적재하므로 batch가 적재보다 길면 weight를 기다리지 않는다. batch가 짧으면 적재가 끝날 때까지 연산이 멈추고 그 cycle을 `stall_cyc`(06 §7 `CMP_STALL`)로 센다.
3. 읽기 data를 ID로 나눈다. slave가 ID가 다른 burst끼리 순서를 바꾸거나 beat를 섞어도 결과가 같다.
4. dma를 넣어도 100 MHz를 지킨다. 여유는 P4.3의 0.365 ns에서 0.295 ns로 줄었고 가장 느린 경로는 dma가 아니다.

## 2. 설계

### 2.1 block

| 파일 | 내용 |
|---|---|
| `dma.v` | AXI4 master 256 bit. weight 적재, membrane potential 읽기·쓰기, 우선순위, 오류 응답 |
| `accel_core.v` | `compute_array`, `weight_cache`, `membrane_storage`, `dma`를 묶는다. 추론 시작 조건과 `stall_cyc`를 둔다. scheduler(P4.5)가 붙을 port는 교체 계획 `pl_*`, 준비 `pf_*`, 추론 시작 `go_*`다 |

`accel_core`는 P4.3의 timing wrapper가 하던 연결을 RTL로 옮긴 것이다. P4.4부터 testbench와 timing 확인이 같은 module을 쓴다.

### 2.2 weight 적재

weight_cache가 miss로 `ld_busy`를 올리면 dma가 slot 주소 `model_base + ld_model × 0x4_0000`부터 4,114 beat를 읽는다.

| 항목 | 값 |
|---|---|
| burst | 16 beat(512 B), 동시에 4개까지. 모든 burst가 512 B 경계에서 시작해 4 KiB 경계를 넘지 않는다 |
| 근거 | P3.1 보드 측정에서 16 beat burst를 동시에 4개 내면 순차 읽기가 3.015 GB/s였다. burst를 더 길게 잡거나 더 많이 내면 membrane potential 읽기가 그 뒤에서 더 오래 기다린다 |
| 끝 | 마지막 word를 쓰는 cycle에 `ld_done`. weight_cache는 다음 cycle에 `ld_busy`를 내리고 다음 계획을 받는다 |

```text
slot beat 0 ~ 45        params row 0~45(뉴런 16개 × {vth, β})   → entry params RAM
slot beat 46 + 2w       word w의 bit [255:0]                     → register에 둔다
slot beat 47 + 2w       word w의 bit [511:256]                   → word w를 쓴다 (w = 0 ~ 2,033)
```

04_MEMORY.md §3의 "word 주소 = beat 번호 ÷ 2"는 weight section 안의 beat 번호다. slot 전체로 세면 (beat − 46) ÷ 2다.

### 2.3 membrane potential 전송과 우선순위

| 방향 | 하는 일 |
|---|---|
| 읽기 | membrane_buf의 전송 하나를 burst 하나(34 beat)로 낸다. 받은 beat는 바로 buffer로 넘긴다 |
| 쓰기 | 주소 handshake 뒤에만 data를 낸다. 34번째 beat에 `wlast`, 쓰기 응답을 `dw_resp`로 넘긴다 |
| 우선순위 | 읽기 주소 채널에 membrane potential 읽기를 먼저 올린다. membrane potential 쓰기가 기다리거나 진행 중이면 weight burst를 새로 내지 않는다 |

04 §5의 순서(membrane potential 읽기 > 쓰기 > weight 적재)를 이렇게 옮겼다. 쓰기와 weight 읽기는 AXI 채널이 달라 동시에 낼 수 있다. 그러나 보드 MIG는 읽기를 먼저 처리하도록 설정했다(`RD_PRI_REG`). weight 읽기가 이어지면 쓰기가 밀리고, 쓰기가 끝나야 buffer가 비어 다음 DDR3 트랙을 준비할 수 있다. 그래서 쓰기 동안에는 weight burst를 멈춘다.

읽기 data는 AXI ID로 나눈다(weight 0, membrane potential 1). AXI는 ID가 다른 burst끼리 응답 순서를 바꾸거나 beat를 섞는 것을 허용한다. 나간 순서로 나누면 그런 slave에서 data가 섞인다(§3.5).

오류 응답(SLVERR·DECERR)이 오면 `err`를 1 cycle 올리고 그 전송의 시작 주소를 `err_addr`에 낸다. weight는 slot 주소다. 06 §4.3의 `ERR_CODE` 6에 쓸 값이다. 같은 cycle에 읽기와 쓰기 오류가 함께 나면 쓰기 쪽만 낸다. `ERR_CODE`는 첫 오류만 남기므로 이것으로 충분하다고 봤다.

### 2.4 추론 시작과 정지 cycle

```text
go_ready   = compute array가 빔 && go_entry가 적재 중이 아님 && membrane potential 준비됨(can_start)
시작        = go_valid && go_ready
stall_cyc += go_valid && compute array가 빔 && !go_ready
```

`stall_cyc`는 scheduler가 추론 시작을 냈는데 compute array가 빈 채로 적재나 membrane potential 준비를 기다린 cycle이다. scheduler가 결정하는 동안의 cycle은 세지 않는다. 06 §7 `CMP_STALL`("추론 요청이 있는데 DMA를 기다린 cycle")을 RTL에서 이렇게 정했다.

scheduler(P4.5)가 지켜야 할 순서는 아래와 같다.

| 규칙 | 이유 |
|---|---|
| batch i+1의 계획(`pl_valid`)은 batch i의 첫 추론이 시작된 뒤에 낸다 | weight_cache는 가장 최근 계획의 entry를 연산 중으로 보고 victim에서 뺀다 |
| DDR3 트랙은 `go` 전에 `pf`로 준비한다 | 준비하지 않은 DDR3 트랙의 `go`는 받지 않는다 |
| `go_entry`는 그 batch의 `pl_entry`다 | 적재 중인지 이 entry로 판단한다 |

## 3. 결과

### 3.1 bit 일치와 전송 완료

| 항목 | MODE 0 | MODE 1 | MODE 2 |
|---|---:|---:|---:|
| 추론 | 2,542 | 2,542 | 2,542 |
| row·출력·DDR3 최종값 불일치 | 0 | 0 | 0 |
| 적재 / miss / 교체 계획 | 672 / 672 / 1,272 | 672 / 672 / 1,272 | 672 / 672 / 1,272 |
| entry 내용 불일치(적재마다 word 2,034 + params 46) | 0 | 0 | 0 |
| weight beat | 2,764,608 | 2,764,608 | 2,764,608 |
| membrane potential beat 읽기 / 쓰기 | 22,440 / 23,188 | 22,440 / 23,188 | 22,440 / 23,188 |
| AXI 규칙 위반 / 우선순위 위반 | 0 / 0 | 0 / 0 | 0 / 0 |

xsim과 Verilator 둘 다 PASS다. MODE 0은 두 simulator의 값이 같다. 끝난 시각만 1 cycle 다른데, 마지막 되쓰기를 기다리는 testbench 순서 차이다. MODE 1·2는 `$urandom` 난수열이 simulator마다 달라 cycle 수가 다르다.

entry 내용 대조는 spike 0 건너뛰기 때문에 필요하다. layer 2·3 word는 spike가 난 input의 것만 읽으므로 golden 대조만으로는 읽지 않은 word의 적재 오류를 못 잡는다.

testbench가 본 AXI 규칙은 다음과 같다. valid가 ready 전에 내려가거나 주소·data가 바뀌지 않는다. burst가 4 KiB 경계를 넘지 않고 길이와 주소가 slot 유효 범위·DDR3 트랙 영역 안이다. 주소 handshake 전에 쓰기 data가 없고 `wlast`가 34번째 beat에만 있다. 나가 있는 weight burst가 4개 이하다. 우선순위는 앞 cycle에 membrane potential 쓰기가 진행 중이거나 읽기가 기다렸으면 이번 cycle에 새 weight burst가 나오지 않는지로 봤다.

### 3.2 전송 시간 (MODE 0)

| 항목 | cycle |
|---|---|
| 적재 4,114 beat (`ld_busy` → `ld_done`) | 최소 4,145, 평균 4,168.4, 최대 4,688 |
| membrane potential 읽기 34 beat (전송 수락 → 마지막 beat) | 평균 68.3, 최대 92 |
| membrane potential 쓰기 34 beat (전송 수락 → 쓰기 응답) | 41 |

- 최소 4,145 cycle은 4,114 beat에 slave의 첫 beat 지연 26 cycle과 dma 안 register 단을 더한 값이다. beat 사이 빈 cycle이 없다.
- 적재가 최대 4,688 cycle로 길어진 것은 같은 시간에 membrane potential 읽기·쓰기를 먼저 처리했기 때문이다.
- 이 slave는 cycle마다 beat 하나(3.2 GB/s)를 준다. 보드 DDR3는 순차 읽기 3.015 GB/s라 적재 한 번이 43.91 µs(04 §3)로 예상된다. 보드에서는 재지 않았다.
- membrane potential 읽기는 가장 오래 걸린 것이 92 cycle이다. 앞 트랙 되쓰기 41 cycle을 더해도 가장 짧은 추론 309 cycle(spike 0개)보다 짧다. 다음 DDR3 트랙 준비는 앞 추론 연산 중에 끝나고, timestep 16~30에서 membrane potential 대기는 0이었다.

### 3.3 prefetch와 연산 정지 (MODE 0)

| 구간 | batch | weight 대기 cycle | membrane potential 대기 cycle |
|---|---:|---:|---:|
| 첫 적재(앞에 겹칠 연산 없음) | 1 | 4,143 | 0 |
| timestep 0~15, 첫 batch 뒤 | 41 | 0 | 2,250 |
| timestep 16~30 | 1,230 | 2,283,612 | 0 |
| 합 | 1,272 | 2,287,755 | 2,250 |

- 합 2,290,005 cycle이 `stall_cyc`와 같다.
- timestep 0~15의 batch는 추론 16~32개라 적재보다 길다. 다음 모델 적재가 batch 연산 중에 끝나 weight를 기다리지 않았다.
- membrane potential 대기 2,250 cycle은 트랙이 하나뿐인 포화 시험 모델 2개에서 났다. 같은 DDR3 트랙의 다음 timestep을 바로 이어 처리해 앞 추론의 되쓰기와 다음 읽기를 기다렸다(전환 30번 × 75 cycle). 실제로는 같은 트랙의 다음 추론 요청이 32 ms 뒤에 온다.
- timestep 16~30의 miss 629번이 평균 3,631 cycle씩 멈췄다. 적재(평균 4,168 cycle)에서 앞 batch 추론 하나의 연산 시간을 뺀 만큼이다. timestep 16의 첫 batch(모델 0)는 앞 batch(모델 41의 timestep 0~15) 동안 적재가 끝나 멈추지 않았다.

### 3.5 오류를 잡는가

RTL 사본에 고장을 하나씩 넣고 Verilator로 돌렸다. 오류 주소 고장만 MODE 2, 나머지는 MODE 1이다.

| 고장 | 결과 |
|---|---|
| 적재 중인 entry로도 시작(`go_ready`에서 적재 조건을 뺌) | row 불일치 16,938, 출력 불일치 640 |
| word의 두 beat 순서를 바꿈 | 적재 640번에서 entry 불일치, row 불일치 111,600 |
| params row를 하나씩 밀어 씀 | 적재 672번 모두 entry 불일치, row 불일치 111,536 |
| 마지막 word를 쓰기 전에 `ld_done` | 적재 672번 모두 entry 불일치(마지막 word), 출력 불일치 2,493 |
| 읽기 data를 ID 대신 "membrane potential 읽기가 나가 있는가"로 나눔 | row 불일치, 그 뒤 적재가 끝나지 않아 시간 초과 |
| membrane potential 쓰기 중에도 weight burst를 냄 | 우선순위 위반 1,726 |
| weight burst를 membrane potential 읽기보다 먼저 냄 | 우선순위 위반 770 |
| 주소 handshake 전에 쓰기 data를 냄 | AXI 규칙 위반(주소 전 쓰기 data), 시간 초과 |
| `wlast`를 33번째 beat에 | AXI 규칙 위반(`wlast`), 시간 초과 |
| weight burst를 동시에 5개까지 냄 | AXI 규칙 위반 169,758 |
| 연산 중인 cycle도 정지로 셈 | `stall_cyc` 4,482,944, testbench 3,174,547 |
| weight 오류 주소를 slot 주소 대신 다음 burst 주소로 | 주소 불일치 5,816 / 5,850 |

- word 순서 고장이 적재 672번 중 640번에서만 드러난 것은 포화 시험 모델 2개(적재 32번)의 word가 앞뒤 반쪽이 같기 때문이다. 실데이터 모델 40개에서는 모두 잡았다.
- 우선순위 고장 2개는 결과 bit가 같다. 우선순위는 정확도가 아니라 전송 시간에 관한 규칙이라 AXI 쪽 관찰로만 잡힌다.
- "연산 중인 cycle도 정지로 셈"은 처음 testbench로는 통과했다. testbench가 앞 추론이 끝난 뒤에만 `go`를 냈기 때문이다. 실제 scheduler처럼 앞 추론 연산 중에 `go`를 미리 올리도록 고친 뒤 잡혔고, §3.1~§3.4는 고친 testbench의 결과다.

### 3.6 합성

`hardware/vivado/ooc_timing.tcl`(인자 `p44 accel_core`). wrapper 없이 `accel_core`를 top으로 둔다. AXI port, scheduler port, predictor 설정은 밖으로 냈다.

| 항목 | P4.3 | P4.4 |
|---|---:|---:|
| WNS ns | +0.365 | +0.295 |
| WHS ns | +0.055 | +0.059 |
| 실패 endpoint | 0 | 0 |

| 대상 | LUT | LUTRAM | FF | RAMB36 | RAMB18 | DSP |
|---|---:|---:|---:|---:|---:|---:|
| `compute_array` | 6,293 | 224 | 2,793 | 0 | 0 | 80 |
| `weight_cache` | 3,636 | 1,550 | 1,602 | 112 | 6 | 1 |
| └ `next_use_predictor` | 814 | 182 | 481 | 0 | 2 | 1 |
| `membrane_storage` | 6,189 | 1,056 | 1,032 | 187 | 0 | 1 |
| `dma` | 120 | 0 | 1,555 | 0 | 0 | 0 |
| `accel_core` 전체 | 16,232 | 2,830 | 7,070 | 299 | 6 | 82 |

- `dma`의 FF는 대부분 data register다. AXI 읽기 data 256 bit, word 앞 beat 256 bit, entry 쓰기 data 512 bit, params 쓰기 256 bit를 한 단씩 둔다. entry BRAM 입력이 register에서 바로 나가게 하려고 넣었다.
- 가장 느린 경로는 compute array의 register 하나가 entry BRAM의 출력 register enable로 퍼지는 배선이다(9.34 ns, 논리 0단). P4.1에서 본 경로와 같은 종류다. dma 경로는 상위 10개에 없다.
- BRAM은 P4.3과 같은 302 tile이다. dma는 BRAM을 쓰지 않는다.

## 4. 검증과 한계

- DDR3는 testbench의 AXI slave 모델이다. MIG와 붙인 시험과 보드 적재 시간(예상 43.91 µs)은 P5.3에서 잰다. MIG의 AXI ID는 4 bit이고 dma는 1 bit만 쓴다. top에서 위 bit를 0으로 둔다. size 32 B, INCR, `wstrb` 전부 1, `awid` 0도 top에서 묶는다.
- scheduler는 testbench가 대신했다. batch 순서(모델 번호 순, 같은 트랙 timestep 이어 처리)는 simulator와 다르다. simulator와 같은 순서는 P4.5에서 넣는다.
- predictor 설정을 비워(`N_REG` 0) victim은 가장 오래된 entry다. PNU 결정은 P4.3에서 확인했다.
- `rst`는 dma가 쉬고 있을 때(`dma_idle`)만 준다. 나가 있는 burst의 응답을 버리는 처리는 없다. 06 §6의 종료 순서(IDLE을 기다린 뒤 RUN = 0)를 따르면 문제가 없다.
- simulator의 DMA는 batch의 weight 전송 뒤에 membrane potential 전송을 붙인다. RTL은 batch i 구성원의 membrane potential 전송을 batch i+1 적재 사이에 먼저 끼워 넣는다. 전송량이 같아 적재가 늦어지는 양은 비슷하겠지만 cycle 단위로 대조하지 않았다.
- `MODEL_LOADS`, `WEIGHT_BYTES`, `STATE_BYTES` counter는 만들지 않았다. `pl_done`·`pl_hit`와 membrane potential 전송 handshake로 셀 수 있어 P4.6에서 다른 counter와 함께 만든다.
- timing은 out-of-context 결과다. MIG, Ethernet MAC, scheduler를 넣은 전체 배치는 P5.1에서 본다.

## 6. 실행

```bash
bash hardware/testbench/run_dma.sh                                                  # vector 생성, lint, xsim·Verilator MODE 0·1·2
MODES=1 bash hardware/testbench/run_dma.sh                                          # MODE 하나만
vivado -mode batch -nojournal -nolog -source hardware/vivado/ooc_timing.tcl -tclargs p44 accel_core   # 합성·배치·배선
```

log는 `hardware/sim/dma/`, Vivado report는 `hardware/vivado/build/p44_timing/`에 생긴다. Verilator는 MODE마다 약 10초, xsim은 MODE 0 약 70초 걸렸다.
