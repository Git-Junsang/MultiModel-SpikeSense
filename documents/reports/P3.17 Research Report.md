# P3.17 보고서: 라즈베리파이 5 측정값을 넣은 entry 수 실험과 최종 비교

작성일: 2026-11-13

[07_SIMULATION.md](../design_references/07_SIMULATION.md) §6에 남은 측정값 세 가지를 simulator에 넣었다. 모델 그룹 지연 표, 추론 요청별 퍼짐, Ethernet 링크 지연이다. 값은 모두 [P3.16 보고서](<P3.16 Research Report.md>)의 라즈베리파이 5–보드 직결 측정에서 왔다. 그 뒤 entry 수 실험과 최종 방법 비교를 다시 했다. 수치는 따로 적지 않으면 simulation 결과다.

## 1. 요약

**환경.**

| 항목 | 값 |
|---|---|
| 가속기 | L·64-lane @100 MHz, 1,024트랙, 모델 40개, rtl67, DDR3 3,015 MB/s, 남는 BRAM에 12 bit membrane potential |
| Host·전송 | Model-Grouped Offset Assignment, Grouping, 즉시 송신, drop 규칙 |
| Host 처리 지연 | 라즈베리파이 5에서 잰 모델 그룹 지연을 넣음. 추론 요청별 지연은 넣지 않음(§2.2) |
| 링크 지연 | 라즈베리파이 5–보드 직결 Ethernet 표본(§2.3) |
| Host 조건 | CPU 고정·performance·부하 없음(기본), CPU 고정·performance·busy loop 3개, CPU 고정 없음·ondemand·부하 없음 |
| 실행 | 시나리오 6개 × seed 30 |

**실험과 결과.**

- entry 수 실험(§3.1): 세 Host 조건 모두 entry 2–10에서 miss·drop이 0이었다. 제안 구성은 모델·주기마다 weight를 한 번만 읽었다. DDR3 traffic은 entry 2에서 6.24 KiB/추론으로 가장 적고 entry 4에서 6.37 KiB/추론이다. entry가 늘면 on-chip membrane potential 트랙이 줄어 DDR3가 조금씩 는다. PNU-Count, PNU-Count RTL, Oracle MIN의 차이는 0.01 KiB/추론 이하다.
- 최종 비교(§3.2): 제안은 Dysta Method보다 DDR3 traffic이 88.8% 적다. 최대 response time은 5.9–9.2% 짧고 준비 완료 뒤 최대 response time은 70.5–77.5% 짧다. Xeon·PCIe 조건의 P3.26 값(88.7%, 9.6%, 71.5%)과 거의 같다.

| Host 조건 | 방법 | DDR3 KiB/추론 | 최대 response time ms | 준비 완료 뒤 최대 ms |
|---|---|---:|---:|---:|
| CPU 고정·부하 없음 | Dysta Method | 57.07 | 6.33 | 5.83 |
| CPU 고정·부하 없음 | 제안 | 6.37 (−88.8%) | 5.75 (−9.2%) | 1.72 (−70.5%) |
| CPU 고정·busy loop 3개 | Dysta Method | 57.05 | 16.93 | 8.10 |
| CPU 고정·busy loop 3개 | 제안 | 6.37 (−88.8%) | 15.92 (−5.9%) | 1.82 (−77.5%) |

**결론.**

1. 라즈베리파이 5 Host에서도 Offset Assignment의 DDR3 이득은 Xeon 측정 때와 같다. 추론 요청별 퍼짐이 17 µs(p99) 정도라 모델 그룹이 한 batch로 들어온다.
2. 즉시 송신에서도 단일 적재가 성립한다. 제안 구성의 모델·주기당 적재는 최대 1번이었다. P3.26에서 단일 적재가 깨진 것은 J = 0.8–3.2 ms를 넣었을 때다.
3. entry 수는 이 조건에서 DDR3를 거의 바꾸지 않는다. 미리 정한 규칙대로라면 entry 2지만 지금 bitstream의 entry 4를 유지하자고 제안한다(§4).
4. PNU 표는 CPU 고정·performance·부하 없음의 모델 그룹 지연 표와 J = 0으로 만들자고 제안한다(§4). 이 조건의 PNU-Count RTL은 Oracle MIN과 같은 DDR3 traffic을 냈다.
5. 최대 response time은 여전히 Host 처리 지연 꼬리가 정한다. busy loop 3개에서는 15.9 ms로 커진다. 방법 비교는 준비 완료 뒤 response time으로 한다.

**한계.** 부하 조건에서 드물게 잰 추론 요청별 퍼짐(최대 2.2–5.5 ms)은 넣지 않았다. Ethernet 표본은 tcpdump를 켠 한 조건에서만 쟀다. 모델 그룹 지연 표는 모델당 25.6트랙·Offset Assignment Host에서 쟀으므로 비교군과 편중 시나리오의 실제 Host 처리 지연과는 다를 수 있다(§5).

## 2. 바꾼 것

### 2.1 모델 그룹 지연 표

P3.16의 `analyze_p316.py`가 만든 `pi_group_<조건>.csv.gz`를 그대로 넣었다. 열(period, model_id, delay_us)이 Xeon 표(P3.25 `m3_group_*`)와 같아서 engine을 고치지 않았다. 앞 16주기는 이미 빠져 있다.

| Host 조건 | 표 | 모델 그룹 지연 p99 ms | 최대 ms | simulation 재현 구간 최대 ms |
|---|---|---:|---:|---:|
| CPU 고정·performance·부하 없음 | `pi_group_pin3_performance_load0` | 2.04 | 6.22 | 5.45 |
| CPU 고정·performance·busy loop 3개 | `pi_group_pin3_performance_load3` | 2.28 | 19.72 | 15.61 |
| CPU 고정 없음·ondemand·부하 없음 | `pi_group_pin-none_ondemand_load0` | 2.64 | 3.15 | 3.15 |

Simulator는 표의 앞 절반을 PNU가 아는 분포로 쓰고 뒤 절반을 seed마다 다른 구간부터 넣는다(P3.26 §2.1). 그래서 simulation 안의 최대는 표 전체의 최대보다 작을 수 있다.

### 2.2 추론 요청별 퍼짐

P3.16에서 잰 j는 같은 모델·주기 추론 요청의 FPGA 도착 시각(`t_in_us`)에서 그 그룹의 첫 도착을 뺀 값이다. UDP 송신, datagram 2개 사이 간격, Ethernet 전송이 모두 들어 있다. 부하가 없는 조건에서 p50은 8 µs, p99는 17 µs, 최대는 19–40 µs였다.

Simulator에 넣는 방법 세 가지를 같은 Host 조건(CPU 고정·부하 없음, 시나리오 uniform, seed 3개)에서 실측과 비교했다.

| 넣는 방법 | j p50 µs | j p99 µs | 그룹 안 퍼짐 p99 µs | 최대 µs |
|---|---:|---:|---:|---:|
| 실측(P3.16) | 8 | 17 | 17 | 19–40 |
| 추론 요청별 지연 없음 + Ethernet 입력 표본 | 6.5 | 15.0 | 18.5 | 35.5 |
| 위 + packet 간격 9.6 µs | 7.5 | 22.9 | 25.6 | 44.4 |
| Uniform(0, 17 µs) + Ethernet 입력 표본 | 11.8 | 26.6 | 30.6 | 44.6 |

Ethernet 입력 표본은 추론 요청마다 잰 값이라 datagram 안 위치가 이미 들어 있다. 그래서 표본을 추론 요청마다 따로 뽑는 것만으로 실측 퍼짐이 나온다. 추론 요청별 지연은 `host_jitter_dist = "none"`, `host_jitter_ms = 0`으로 두었다. Packet 간격을 더 넣으면 퍼짐을 부풀린다. `host_packet_gap_us`는 이전처럼 모아 보내기에서만 쓴다.

### 2.3 Ethernet 링크 지연

환경 키 `host_link`를 더했다. 값이 `pcie`면 이전처럼 PCIe 64 B 표본(P3.3)을 쓰고 `ethernet`이면 P3.16 Ethernet 표본(`hardware/board_test/p316_meas/result/eth_up_ns.txt`, `eth_down_ns.txt`)을 쓴다. 두 파일은 분위수 20,000개(ns)로 PCIe 표본과 형식이 같다.

| 표본 | p50 µs | p99 µs | 최대 µs |
|---|---:|---:|---:|
| Ethernet 입력(Host → FPGA) | 22.0 | 30.0 | 50.3 |
| Ethernet 결과(FPGA → Host) | 37.5 | 70.8 | 126.0 |

- 링크 표본은 입력 지연, 결과 지연, Dysta Method의 결과 회수 여유(결과 최대 + 20 µs = 146 µs), 조건부 response time에 쓰인다. 네 곳 모두 `Hardware.link`에서 고른다.
- 기존 환경 파일 11개와 template에는 `host_link = "pcie"`를 넣었다. 옛 결과가 그대로 나오는 것은 `test_engine.py`의 p325 재현 검사로 확인했다.
- 입력과 결과는 대칭 시각 차이(1초 창마다 θ)를 가정해 나눈 값이다(P3.16 §2.3).

## 3. 결과

### 3.1 entry 수 실험

환경은 `simulation/environment/p317_entry.toml`이다. Entry 선택 규칙은 P3.25·P3.26과 같고 실험 전에 정했다. 규칙은 miss 0, 최소 deadline 여유 > 0, DDR3 traffic이 entry 2–10 중 최솟값의 110% 이내인 가장 작은 entry를 고르는 것이다.

CPU 고정·performance·부하 없음, PNU-Count:

| entry | on-chip 트랙 | DDR3 KiB/추론 | Belady 하한 KiB/추론 | 모델·주기당 적재 평균 | 한 모델·주기 적재 최대 | 최대 response time ms |
|---:|---:|---:|---:|---:|---:|---:|
| 2 | 992 | 6.24 | 6.24 | 1.000 | 1 | 5.75 |
| 3 | 880 | 6.31 | 6.30 | 0.974 | 1 | 5.75 |
| 4 | 768 | 6.37 | 6.36 | 0.948 | 1 | 5.75 |
| 5 | 656 | 6.44 | 6.43 | 0.921 | 1 | 5.75 |
| 6 | 544 | 6.50 | 6.49 | 0.895 | 1 | 5.75 |
| 8 | 320 | 6.63 | 6.61 | 0.843 | 1 | 5.75 |
| 10 | 96 | 6.76 | 6.74 | 0.791 | 1 | 5.70 |

- 모든 점에서 miss와 drop이 0이었다. 규칙이 고르는 entry는 세 Host 조건과 세 정책에서 모두 2다.
- entry를 늘리면 다음 주기까지 남는 모델이 생겨 적재는 줄지만(entry 10에서 모델·주기당 0.79번) DDR3에 두는 membrane potential 트랙이 늘어 전체 DDR3 traffic은 는다.
- PNU-Count, PNU-Count RTL, Oracle MIN은 모든 entry에서 0.01 KiB/추론 안이다. Belady 하한과의 차도 0.02 KiB/추론 이하다.
- 다른 두 Host 조건의 DDR3 traffic은 기본 조건과 0.01 KiB/추론 안이다. 최대 response time은 busy loop 3개에서 15.88–15.92 ms, CPU 고정 없음·ondemand에서 4.54 ms였다. Entry 수에 따라 거의 바뀌지 않는다.

### 3.2 최종 비교

환경은 `simulation/environment/p317_final_compare.toml`이다. P3.26 최종 비교와 방법 8개가 같고 entry는 4다.

| 방법 | DDR3 KiB/추론 | 평균 ms | p99 ms | 최대 ms | 준비 완료 뒤 최대 ms | 한 모델·주기 적재 최대 |
|---|---:|---:|---:|---:|---:|---:|
| Dysta Method (unaligned, LRU) | 57.07 | 2.24 | 5.95 | 6.33 | 5.83 | 75 |
| DeepRT Method (unaligned, LRU) | 11.28 | 9.00 | 16.75 | 20.39 | 16.59 | 4 |
| global alignment + Grouping (LRU) | 6.70 | 3.13 | 6.10 | 6.36 | 4.32 | 1 |
| global alignment + Dysta Method (LRU) | 6.65 | 3.09 | 6.05 | 6.32 | 5.84 | 1 |
| global alignment + DeepRT Method (LRU) | 6.70 | 9.12 | 16.95 | 19.97 | 16.57 | 2 |
| 제안 (Offset Assignment + Grouping + PNU-Count) | 6.37 | 1.52 | 3.25 | 5.75 | 1.72 | 1 |
| Offset Assignment + Dysta Method + PNU-Count | 6.37 | 1.52 | 3.25 | 5.75 | 1.72 | 1 |
| Offset Assignment + DeepRT Method + PNU-Count | 6.38 | 9.08 | 16.75 | 18.26 | 16.56 | 1 |

위 표는 CPU 고정·performance·부하 없음이다. Busy loop 3개 조건에서 제안은 6.37 KiB/추론, 최대 15.92 ms, 준비 완료 뒤 최대 1.82 ms였다. Dysta Method는 57.05 KiB/추론, 16.93 ms, 8.10 ms였다. 모든 점에서 miss와 drop은 0이다.

P3.26(Xeon 모델 그룹 지연, PCIe 표본, J = 0)과 비교하면 아래와 같다.

| 값 | P3.26 Xeon | 라즈베리파이 5 |
|---|---:|---:|
| 제안 DDR3 KiB/추론 | 6.37 | 6.37 |
| Dysta Method 대비 DDR3 감소 | 88.7% | 88.8% |
| 제안 최대 response time ms | 9.27 | 5.75 |
| Dysta Method 대비 최대 감소 | 9.6% | 9.2% |
| 제안 준비 완료 뒤 최대 ms | 1.75 | 1.72 |
| Dysta Method 대비 준비 완료 뒤 최대 감소 | 71.5% | 70.5% |

최대 response time이 Xeon보다 짧은 것은 라즈베리파이 5의 부하 없는 모델 그룹 지연 꼬리(최대 6.2 ms)가 Xeon(8.75 ms)보다 짧기 때문이다. 준비 완료 뒤 최대는 링크와 모델 그룹 지연을 함께 바꿨는데도 1.75 ms에서 1.72 ms로 거의 같다.

## 4. 제안

이 절의 값은 제안이다. 확정은 design_references에 반영할 때 한다.

| 항목 | 제안 | 근거 |
|---|---|---|
| entry 수 | 4 유지(지금 bitstream) | 규칙은 entry 2(6.24 KiB/추론)를 고른다. Entry 4는 6.37 KiB/추론으로 2.1% 많지만 bitstream을 다시 만들지 않는다. 부하 조건에서 잰 추론 요청별 퍼짐 꼬리(최대 2.2–5.5 ms)는 이 실험에 넣지 않았다. P3.24에서 entry 4는 J = 3.2 ms까지 DDR3가 두 배로 늘지 않았다 |
| PNU 표의 모델 그룹 지연 표 | `hardware/board_test/p316_meas/result/pi_group_pin3_performance_load0.csv.gz` | 실행 조건(계산 thread CPU 3 고정, performance)과 같다. 열이 `setup --model-group-delay-trace` 입력 형식과 같다 |
| PNU 표의 J | 0 µs (`setup --jitter-us 0`) | 추론 요청별 퍼짐 p99.9가 17 µs라 LUT 칸 256 µs보다 작다. 이 조건에서 PNU-Count RTL은 Oracle MIN과 같은 DDR3 traffic을 냈다 |

Entry 2로 바꾸면 on-chip 트랙이 768개에서 992개로 늘고 DDR3 traffic이 2.1% 준다. 이 차이로 RTL을 다시 합성할 만한지는 사용자가 정한다.

## 5. 한계

- 추론 요청별 지연을 넣지 않았다. 부하 조건에서 드물게 생긴 2.2–5.5 ms 퍼짐(원인 미확인, P3.16)은 빠져 있다.
- Ethernet 표본은 tcpdump를 켠 CPU 고정·performance·부하 없음 조건 하나에서 쟀다. busy loop 조건의 링크 지연은 재지 않았고 같은 표본을 썼다.
- 모델 그룹 지연 표는 Offset Assignment Host에서 모델당 25.6트랙으로 쟀다. 비교군(unaligned, global alignment)과 편중 시나리오에도 같은 (모델, 주기) 지연을 넣었다(P3.26과 같은 한계).
- mic 입력(resampler 계산, sample clock drift 보정)은 Host 처리 지연에 들어 있지 않다. P4.8이 끝나면 다시 잰다.
- 실험은 sub2(numpy 2.2.6)에서 돌렸다. 개발 서버는 numpy 2.4.6이다. `test_engine.py`는 두 서버 모두 통과했다(sub2는 core·p326·env, 개발 서버는 전체).

## 6. 실행 방법

```bash
python3 simulation/engine/test_engine.py
python3 simulation/engine/engine.py simulation/environment/p317_entry.toml --jobs 18          # 11,340 run, sub2 405 s
python3 simulation/engine/engine.py simulation/environment/p317_final_compare.toml --jobs 18  # 2,880 run, sub2 195 s
```

결과는 `simulation/result/p317_entry.csv`, `p317_final_compare.csv`와 각 `_runs.csv.gz`다.
