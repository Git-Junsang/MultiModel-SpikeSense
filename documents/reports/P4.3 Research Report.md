# P4.3 보고서: weight cache와 PNU-Count RTL

작성일: 2026-10-20

Weight cache entry를 관리하고 PNU-Count로 victim을 고르는 RTL을 만들었다. RTL이 쓰는 정수 µs와 지연 예측 표를 같은 식으로 simulator에 넣었다. 그 simulator 실행의 도착·교체 기록을 RTL에 다시 넣어 결정이 모두 같은지 봤다. 표로 근사한 탓에 DDR3 traffic이 얼마나 달라지는지도 쟀다. 결정 대조는 RTL simulation, 표 근사는 simulation, timing은 out-of-context 배치·배선 결과다. 보드 실측은 아니다.

## 1. 요약

### 1.1 환경

| 구분 | 내용 |
|---|---|
| RTL | `hardware/src/`의 `weight_cache`(entry E개, 교체 FSM), `next_use_predictor`(PNU-Count). Entry는 P4.1 `weight_entry` |
| 기준 | `engine.PNURTL`. RTL과 같은 정수 µs·표 식을 넣은 PNU-Count다. 정확한 식은 `engine.PNU`(P3.26) |
| 결정 대조 | simulator 실행 3개의 도착과 교체 계획을 기록해 RTL에 시각 순서로 넣었다. Host 처리 지연은 M3 CPU 고정·부하 없음 모델 그룹 지연 + Uniform(0, J), 1,024트랙, Model-Grouped Offset Assignment, Grouping |
| 표 근사 실험 | `p43_pnu_rtl`. `p326_cache_policy`와 같은 조건에서 정확한 식과 RTL 식을 비교했다. Entry 4·6 × J 0·0.8·1.6·3.2 ms × 시나리오 6 × seed 30 |
| simulation | xsim 2026.1, Verilator 5.020 |
| 합성 | Vivado 2026.1, `xc7a200tfbg484-2`, out-of-context, clock 10 ns. Compute array + `weight_cache`(entry 4) + Membrane Storage(on-chip 768트랙) |

### 1.2 결과

| 질문 | 답 |
|---|---|
| RTL 결정이 simulator와 같은가 | 교체 계획 187,090개(victim을 고른 교체 14,138개)가 모두 같다(xsim, Verilator) |
| 연산 중 entry 보호 | 연산 중 entry를 내보낸 경우 0. 적재가 끝날 때까지 다음 계획을 받지 않는다 |
| 오류를 잡는가 | 일부러 고장 낸 RTL 6개 중 5개가 FAIL. 남은 하나는 simulator로는 구별할 수 없는 고장이다(§3.2) |
| 표 근사 | J ≤ 1.6 ms에서는 정확한 식과 DDR3 traffic이 같다. J = 3.2 ms에서 entry 4는 +0.67%(12.37 → 12.45 KiB/추론), entry 6은 +0.03%. 최대 response time은 같고 deadline miss는 0 |
| 결정 시간 | 후보 하나에 6 cycle, entry 4면 약 20 cycle(0.2 µs). 적재 한 번(43.91 µs)보다 훨씬 짧다 |
| timing | 100 MHz 통과. WNS +0.365 ns, WHS +0.055 ns |
| predictor 자원 | LUT 812(LUTRAM 182), FF 481, RAMB18 2개(1 tile), DSP 1 |
| 전체 자원 | BRAM 302 tile(entry 114 + bank 187 + predictor 1), LUT 16,056, FF 5,453, DSP 82 |

### 1.3 결론

1. RTL weight cache는 simulator의 PNU-Count와 같은 victim을 고른다. 다음 batch의 모델이 entry에 있는지, 빈 entry가 있는지, 어느 entry를 내보낼지가 기록 3개에서 모두 같았다.
2. 지연 예측을 256 µs 칸 표와 정수 µs로 계산해도 DDR3 traffic 차이는 0.7% 이하다. 04_MEMORY.md §3.1에서 확인하지 않았던 "예측 표의 근사 오차"는 이 범위다.
3. predictor는 BRAM 1 tile을 쓴다. Simulation이 예약한 0.5 tile보다 0.5 tile 크다. BRAM 합은 302 tile로 링크·request table 예약(50 tile)을 더해도 365 안이다.
4. 첫 배선은 100 MHz를 놓쳤다(WNS −1.793 ns). predictor 도착 처리를 3단으로 나누고 membrane bank 주소를 sub 메모리마다 복제해 고쳤다.

## 2. 설계

### 2.1 block

| 파일 | 내용 |
|---|---|
| `weight_cache.v` | entry E개(parameter, 기본 4), entry마다 모델 번호·LRU 순위, 교체 FSM, compute array 읽기 mux, DMA 쓰기 길 |
| `next_use_predictor.v` | 모델마다 다음 사용까지 남은 시간 Δ를 낸다. 모델별 기록(가장 최근 주기 하나), Host가 쓰는 설정과 표 |

### 2.2 교체 순서

Scheduler가 지금 batch를 연산하는 동안 다음 batch의 모델을 알린다(`pl_valid`, `pl_model`).

| 경우 | 하는 일 |
|---|---|
| hit | 그 모델이 entry에 있다(적재 중 포함). 그 entry를 가장 최근으로 올린다 |
| 빈 entry | 가장 번호가 작은 빈 entry에 적재한다 |
| 내보냄 | 가장 최근 entry(지금 연산 중인 batch)를 뺀 entry를 오래된 순서로 predictor에 묻는다. `{Δ, queue가 빔}`이 가장 큰 entry를 내보낸다. 같으면 오래된 entry |

적재할 때는 그 entry를 적재 중으로 두고 `ld_entry`·`ld_model`을 DMA에 낸다. DMA는 `wr_*`로 그 entry에 쓰고 `ld_done`을 준다. 적재가 끝날 때까지 다음 계획을 받지 않으므로 적재 대상과 연산 중 entry는 후보가 되지 않는다. 이 순서는 simulator의 `NextUse.plan`과 같다.

### 2.3 예측 식

04_MEMORY.md §3.1의 식을 정수 µs로 계산한다. 모델 m의 nominal offset은 `OFFSET_NUM[m] × 800 µs`다.

```text
kn, el  = 지금 주기와 그 주기 nominal offset 뒤 경과
est     = 가장 최근 주기의 예상 추론 요청 수(packet n_expect). 아직 없으면 N_REG[m]
r       = est − (주기 kn의 도착 수)
Δ_nxt   = (32,000 − el) + EG + LUT_U[0][rb(max(1, est))]
Δ       = 0                       queue에 추론 요청이 있음
          ∞                       N_REG[m] = 0
          Δ_nxt                   첫 주기 시작 전
          LUT_G[el / 256]         주기 kn 첫 추론 요청 전, r > 0, el < TAU_G
          LUT_U[x / 256][rb(r)]   첫 추론 요청 뒤(x = 지금 − 첫 도착), r > 0, x < TAU_U
          Δ_nxt                   그 밖
rb      = 남은 수 칸 1, 2, 3~4, 5~8, 9~16, 17 이상 → 0~5
```

모델마다 가장 최근 주기 하나의 (주기 번호, 예상 수, 도착 수, 첫 도착 시각)만 둔다. 지금 주기 kn의 기록만 예측에 쓰므로 이것으로 충분하다. Simulator는 모든 주기를 세지만 결과는 같다.

추론 요청이 몇 번째 주기의 것인지는 도착할 때 정한다. `t_host − (지금 주기의 nominal 시작)`이 −16,000 µs보다 작으면 앞 주기다. Simulator에서는 t_host가 nominal 시각과 정확히 같아 지금 주기로 세는 것과 결과가 같다. Host와 FPGA의 clock 차이로 t_host가 nominal보다 조금 앞서도 주기를 잘못 세지 않게 둔 규칙이다.

### 2.4 Host가 쓰는 설정

| 주소 | 이름 | 값 |
|---|---|---|
| `0x000 + m` | `OFFSET_NUM[m]` | 모델 m의 offset 번호(0–39) |
| `0x040 + m` | `N_REG[m]` | 모델 m의 등록 트랙 수. 0이면 그 모델은 다음 사용 없음 |
| `0x080`, `0x081`, `0x082` | `TAU_G`, `TAU_U`, `EG` | 모델 그룹 지연 G의 최대, 추론 요청별 지연 j의 최대, G의 평균(µs, 올림·반올림) |
| `0x100 + i` | `LUT_G[i]` | i = 0~127. `δ_G((i + 0.5) × 256 µs)` |
| `0x400 + 8i + rb` | `LUT_U[i][rb]` | i = 0–127, rb = 0–5. `δ_j((i + 0.5) × 256 µs, 칸 대표값)`, 대표값 1, 2, 3.5, 6.5, 12.5, 24 |

값은 16 bit µs다. 표를 만드는 식은 `engine.rtl_tables()`이고 Host runtime이 같은 식을 써야 한다. 이 주소는 predictor 안의 주소다. Ethernet 위 register 주소는 아직 정하지 않았다(06_HOST_INTERFACE.md §7, P4.6·P4.7).

### 2.5 pipeline

| 경로 | 단계 |
|---|---|
| 도착 | A 주기 위치(el, kn), B 추론 요청 주기, C 모델 기록 고치기. 도착 3 cycle 뒤에 기록된다 |
| 질의 | 0 받기, 1 모델 기록 읽기, 2 판정·표 읽기, 3 결과. 질의 뒤 4 cycle에 Δ가 나온다 |

## 3. 결과

### 3.1 결정 대조

| 기록 | 조건 | 도착 | 교체 계획 | hit | 빈 entry | 내보냄 | 불일치 |
|---|---|---:|---:|---:|---:|---:|---:|
| t0 | entry 4, J 3.2 ms, 시나리오 uniform, seed 0 | 81,920 | 75,853 | 67,919 | 4 | 7,930 | 0 |
| t1 | entry 4, J 0.8 ms, 시나리오 skewed-synchronized, seed 1 | 81,920 | 41,371 | 38,328 | 4 | 3,039 | 0 |
| t2 | entry 6, J 3.2 ms, 시나리오 skewed, seed 2 | 81,920 | 69,866 | 66,691 | 6 | 3,169 | 0 |

xsim과 Verilator 결과가 같다. 재생 전에 entry E개를 하나씩 적재하며 entry마다 다른 값을 쓰고, compute array 쪽 port A·B·params로 맞는 entry를 읽는지도 확인했다.

### 3.2 오류를 잡는가

Verilator로 돌렸다.

| 고장 | t0 | t1·t2 |
|---|---|---|
| 같은 점수면 최근 entry를 내보냄 | 불일치 360 | — |
| queue가 빈 모델을 먼저 내보내는 규칙을 뺌 | 불일치 6 | — |
| 가장 최근 entry(연산 중)도 후보에 넣음 | 불일치 4,310, 연산 중 entry를 내보냄 1,626 | — |
| 남은 수 칸 경계를 3에서 4로 | 불일치 380 | — |
| 첫 추론 요청 전 δ_G 분기를 끔 | 통과 | 불일치 322, 190 |
| 추론 요청 주기를 도착 시각으로만 셈 | 통과 | — |

δ_G 분기는 t0 조건(entry 4, J 3.2 ms)에서 한 번도 쓰이지 않았다. 첫 추론 요청이 아직 오지 않은 모델이 cache에 남는 경우가 없었기 때문이다. t1(entry 4, J 0.8 ms)과 t2(entry 6, J 3.2 ms)에서는 각각 수백 번 쓰여 고장을 잡았다. 추론 요청 주기 규칙은 simulator의 t_host가 nominal 시각과 같아 어느 방식이든 결과가 같다. 이 규칙은 실제 Host clock 차이로 확인해야 한다.

### 3.3 표 근사

`p43_pnu_rtl`, 점마다 실행 180개(시나리오 6 × seed 30). DDR3 KiB/추론이다.

| entry | J = 0 | 0.8 ms | 1.6 ms | 3.2 ms |
|---:|---|---|---|---|
| 4, 정확한 식 | 6.37 | 6.38 | 6.56 | 12.37 |
| 4, RTL 표 | 6.37 | 6.38 | 6.56 | 12.45 (+0.67%) |
| 6, 정확한 식 | 6.49 | 6.50 | 6.65 | 7.13 |
| 6, RTL 표 | 6.49 | 6.50 | 6.65 | 7.13 (+0.03%) |

정확한 식의 값은 04_MEMORY.md §3.2·§4 표와 같다. 모든 점에서 최대 response time이 같고 deadline miss는 0이다. J = 3.2 ms·entry 4에서 모델·주기당 재적재는 0.917에서 0.931로 늘었다.

### 3.4 합성

`hardware/vivado/ooc_timing.tcl`(인자 `p43`), wrapper `p43_timing_top.v`. P4.2 wrapper의 entry 4개와 출력 mux를 `weight_cache`로 바꿨다. predictor 설정·도착·queue·교체 계획과 DMA port는 밖으로 냈다.

| 항목 | 첫 배선 | 고친 뒤 |
|---|---:|---:|
| WNS ns | −1.793 | +0.365 |
| 실패 endpoint | 230 | 0 |
| WHS ns | +0.100 | +0.055 |

첫 배선의 실패는 두 곳이었다.

| 경로 | 실패 | 원인 | 고친 방법 |
|---|---:|---|---|
| predictor 도착 처리 | 158 | 주기 위치, 33 bit 뺄셈, tag 비교, 쓰기가 한 cycle(논리 22단, 11.3 ns) | 3단으로 나눔 |
| membrane bank 주소 | 72 | 주소 register 하나가 BRAM 187개로 퍼지는 배선 8.4 ns(논리 0단). P4.2에서 여유 0.348 ns였던 경로 | 트랙 기준 주소를 sub 메모리 17개마다 따로 잡고 주소 덧셈도 sub마다 |

bank 수정은 읽기 지연 2를 그대로 둔다. 그래서 control overhead 67 cycle은 바뀌지 않는다. 고친 뒤 P4.1·P4.2·P4.3 testbench를 다시 돌려 모두 PASS였다.

| 대상 | LUT | LUTRAM | FF | RAMB36 | RAMB18 | DSP |
|---|---:|---:|---:|---:|---:|---:|
| `compute_array` | 6,303 | 224 | 2,795 | 0 | 0 | 80 |
| `weight_cache` | 3,605 | 1,550 | 1,602 | 112 | 6 | 1 |
| ├ `weight_entry` 1개 | 362 | 342 | 256 | 28 | 1 | 0 |
| └ `next_use_predictor` | 812 | 182 | 481 | 0 | 2 | 1 |
| `membrane_storage` | 6,157 | 1,056 | 1,032 | 187 | 0 | 1 |
| └ `membrane_bank` | 3,664 | 0 | 525 | 187 | 0 | 0 |
| wrapper 전체 | 16,056 | 2,984 | 5,453 | 299 | 6 | 82 |

predictor의 RAMB18 2개는 `LUT_U`(1,024 × 16 bit)다. 모델별 기록과 `LUT_G`는 LUTRAM이다.

가장 느린 경로는 compute array의 누산 clear 신호 하나가 DSP 64개로 퍼지는 배선이다(여유 0.365 ns). P4.1·P4.2에서 본 것과 같은 종류로, 전체 설계에서 실패하면 lane 묶음마다 복제한다.

## 4. 검증과 한계

- DMA와 scheduler는 없다. 적재는 바로 끝난 것으로 두었고 계획 순서와 queue 상태는 simulator 기록을 그대로 넣었다. 실제 적재 시간과 batch 구성의 상호작용은 P4.4·P4.5와 통합 test(P4.10)에서 본다.
- 결정 대조의 기준은 RTL 식을 옮긴 `engine.PNURTL`이다. 정확한 식(`engine.PNU`)과의 차이는 §3.3의 DDR3 traffic으로만 보였다. 결정 하나하나는 대조하지 않았다.
- 표는 모델 40개를 합친 G 분포 하나로 만든다(P3.26과 같다). 목표 Host(라즈베리파이 5급)의 지연을 재면 표를 다시 만든다.
- `n_expect`는 제안하는 protocol 확장이다(06_HOST_INTERFACE.md §4.1). PNU-Timeout은 RTL로 만들지 않았다.
- 도착은 3 cycle 뒤에 기록되고 질의는 4 cycle이 걸린다. 같은 때 들어온 도착과 질의의 순서는 simulator와 다를 수 있다. 재생 test에서는 도착을 질의 전에 넣었다.
- engine에 `PNURTL`과 `rtl_tables()`를 더했다(`storage = "pnu_rtl"`). 기존 정책과 결과는 바뀌지 않았고 `test_engine.py`가 모두 ok였다.

## 6. 실행

```bash
bash hardware/testbench/run_weight_cache.sh                                       # 기록 3개 생성, lint, xsim, Verilator
python3 simulation/engine/engine.py simulation/environment/p43_pnu_rtl.toml       # 표 근사 실험(약 4분)

```
