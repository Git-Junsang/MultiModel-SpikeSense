# P3.25 보고서: 시간 기준·jitter 정의 확정과 cache·비교군 재실험

작성일: 2026-10-18

DAC 2027 실험 요청서([DAC_2027_experiment_figure_request.md](../papers/journal/DAC_2027_experiment_figure_request.md))에 따라 simulator를 고치고 실험을 다시 했다. 그 과정에서 deadline의 시간 기준과 jitter의 정의를 사용자와 함께 다시 정했다. 이 보고서는 확정한 정의, 바꾼 simulator, 실험 결과, Host 측정, 남은 일을 한 곳에 모은다.

수치는 따로 적지 않으면 simulation 결과다. 보드 실측이 아니다. Host 처리 지연 측정은 개발 서버급 CPU에서 잰 값이라 최종 Host(라즈베리파이 5급) 성능 근거가 아니다.

> **정정(2026-10-18).** 이 보고서의 simulation은 Host 처리 지연을 추론 요청·주기마다 0~J로 따로 뽑았다. 측정(§4.11)에서 보인 "모델 그룹 지연 + 모델 그룹 안 퍼짐" 구조는 넣지 않은 합성 조건이다. 두 부분을 나누고 cache 예측과 drop 규칙을 고친 재실험은 [P3.26 보고서](<P3.26 Research Report.md>)에 있다. 아래 15.47 ms는 증명된 상한이 아니라 명시한 가정 아래 계산한 조건부 response time이다.

### 1.3 결론

1. DDR3 이득은 Offset Assignment에서 나온다. Jitter 3.2 ms 이하에서 제안은 6.4–7.0 KiB/추론으로 Dysta Method(57–58 KiB/추론)보다 88–89% 적다. 모든 점에서 deadline miss는 0이다.
2. 이전 결과(P3.13~P3.24)의 offset-order cache는 트랙마다 실제 지연을 알고 있었다(미래 정보 누출). nominal offset만 아는 정책(offset-only)은 jitter 3.2 ms에서 41 KiB/추론으로 무너진다. 예상 추론 요청 수를 아는 PNU-Count가 이를 Oracle 수준으로 되돌린다. 추론 요청별 지연만 둔 합성 조건의 결과이며, 모델 그룹 지연이 있으면 예측식을 고쳐야 한다(P3.26 §2.2).
3. Response time 이득은 jitter가 커질수록 줄어든다. Jitter 0.8 ms에서 최대 response time은 Dysta Method의 1/3이고, 3.2 ms에서 1/2이다.
4. Host가 모델 단위로 묶어 계산하면 jitter는 0이 될 수 있다. 이때 cache 정책 사이 차이는 거의 없고 이득은 모두 Offset Assignment에서 나온다. Cache는 jitter 요인(§2.4)이 생겼을 때의 robustness로 주장한다.
5. 즉시 송신으로는 hard deadline을 증명하지 못했다. 모아 보내기의 15.5 ms도 명시한 가정 아래 계산한 조건부 response time이다. 보장하려면 Host 처리 지연 상한, 링크 상한, packet 분할 뒤 단일 적재를 먼저 확인해야 한다. 그 전에는 조건부 계산과 관측 최대만 보고한다.

## 2. 확정한 정의

### 2.1 시간 기준과 deadline

```text
t_host  = frame의 마지막 샘플이 Host에 들어온 시각(Host clock). 응답 시간·deadline의 시작
t_ready = Host가 그 frame의 mel 계산을 마친 시각
t_send  = Host가 추론 요청을 보낸 시각(즉시 송신이면 t_ready)
t_arr   = 추론 요청이 FPGA ingest에 도착한 시각
t_done  = FPGA 연산 완료
t_recv  = Host가 결과를 받은 시각

응답 시간 = t_recv − t_host ≤ 32 ms (system deadline)
         = Host 처리 지연(t_ready − t_host) + 링크(t_arr − t_send) + FPGA(t_done − t_arr) + 링크(t_recv − t_done)
FPGA 예산 c = 32 ms − Host 처리 지연 최대 − 링크 왕복 최대
end-to-end = mic–Host 지연(측정, 우리 수치에서 제외) + 응답 시간
```

- Simulator의 `t_gen`은 이제 t_host로 읽는다. 지금까지의 p325 결과는 추론 요청마다 0~J의 지연을 t_gen에 더해 도착시켰으므로, 그 지연을 Host 처리 지연으로 읽으면 그대로 맞는다. 다만 모델 그룹 지연과 모델 그룹 안 퍼짐을 나누지 않은 합성 조건이다.
- Host 처리 지연이 주기마다 바뀌면 같은 트랙의 다음 추론 요청이 그만큼 일찍 올 수 있다. 최소 간격은 32 ms − (Host 처리 지연 최대 − 최소)다. 처음에 쓴 32 ms − J는 모델 그룹 지연의 변화를 빠뜨린 식이다(P3.26 §2.1).

### 2.2 Offset Assignment와 송신

- 모델 40개가 0.8 ms 간격 offset 40개를 하나씩 맡는다. 모델 하나를 쓰는 트랙(평균 약 25개)은 모두 같은 O_m에서 frame을 자른다.
- Frame은 도착 시각이 아니라 샘플 번호로 정한다. 마지막 샘플이 늦게 오면 보내는 시각만 늦어진다. 샘플을 다음 frame으로 옮기거나 버리지 않는다.
- Host는 추론 요청이 준비되면 바로 보낸다. 같은 모델 추론 요청은 Host 처리 시간 폭 안에서 거의 이어서 FPGA에 도착한다. FPGA는 이를 batch 하나 또는 작은 batch 몇 개로 처리하고, 뒤 batch는 cache hit라 weight를 모델당 한 번만 읽는다.
- Offset 경계 송신(0.8 ms 경계마다 묶어 보냄)과 비교하면 DDR3는 같고(jitter 0.8 ms, 5.27 KiB/추론) response time이 평균 0.6–0.8 ms 짧다. Offset 경계 송신은 packet 수를 1/25로 줄이는 장점이 있다. 비교용 모드로 engine에 남겼다(`host_phase = "offset"`).

### 2.3 Jitter

- Jitter J = 같은 모델·같은 주기 추론 요청들의 Host 처리 완료 시각 중 가장 늦은 것과 가장 빠른 것의 차이다.
- Mic–Host 구간의 장치 차이는 jitter에 넣지 않는다. 이를 지키려면 Host가 O_m에 이미 들어와 있는 샘플까지만 끊어야 한다(§2.5 조건 4).
- 늦은 추론 요청은 다음 offset 추론 요청과 함께 FPGA에 도착한다. 그 모델 weight가 cache에 남아 있으면 hit다. 다시 읽는 것은 그 사이 쫓겨났을 때뿐이다.
- Simulation의 J는 이 퍼짐의 최대 폭이다. uniform은 0~J 균등, tail은 95%가 0–0.8 ms이고 5%가 0.8 ms~J다.
- Host 처리 지연은 모델 그룹 지연(주기마다 바뀜)과 추론 요청별 지연으로 나뉜다. Jitter는 뒤의 것의 퍼짐이다. 앞의 것은 jitter가 아니지만 다음 도착 시각을 바꾸므로 cache 예측에 넣어야 한다. 이 보고서의 simulation은 둘을 나누지 않았다(P3.26에서 나눔).

### 2.4 Jitter가 생길 수 있는 요인

Host에서 모델 단위로 묶어 계산해도 아래 요인이 같은 모델 추론 요청의 도착 시각을 벌릴 수 있다. Mic–Host 구간은 정의상 뺐지만 새어 들어올 수 있어 함께 적는다.

| --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------ | ----------- |

### 2.5 Jitter를 0에 가깝게 두는 Host 규칙

1. 한 모델의 트랙은 한 Host가 처리한다.
2. 한 모델의 트랙 mel을 한 번에 묶어 계산한다.
3. 결과를 묶어 보낸다(packet 수를 최소로, 이어서).
4. O_m에 이미 Host에 들어와 있는 샘플까지만 끊는다. Mic buffer 주기가 32 ms의 약수(1·2·4·8·16 ms)여야 끊는 위치가 주기마다 같아져 hop 512샘플이 유지된다.

### 2.6 Cache 교체 정책

| 정책             | 쓰는 정보                                              | 역할                                                                                           |
| ---------------- | ------------------------------------------------------ | ---------------------------------------------------------------------------------------------- |
| LRU              | 과거 접근                                              | 일반 기준선                                                                                    |
| offset-only      | 모델별 nominal offset, 지금 queue                      | jitter를 모르는 기준선. 옛 offset-order에서 누출을 뺀 것과 같다                                |
| PNU-Timeout      | 위 + jitter 분포, timeout                              | 예상 추론 요청 수 없이 동작하는 안                                                                  |
| PNU-Count (제안) | 위 + Host가 추론 요청 packet에 싣는 그 주기의 예상 추론 요청 수 | 제안 cache. Predicted-Next-Use Weight Cache                                                           |
| Oracle MIN       | 실제 미래 도착열                                       | 구현할 수 없는 미래 정보 기준선. Batch 구성이 cache 결정에 따라 바뀌어 적재 수의 하한은 아니다 |

PNU-Count의 교체 규칙은 다음과 같다.

1. 연산 중인 entry와 적재 대상은 후보에서 뺀다.
2. Queue에 추론 요청이 있는 모델은 다음 사용을 지금으로 본다. 점수가 같아도 queue가 빈 모델을 먼저 내보낸다.
3. 이번 주기의 예상 추론 요청이 남았고 nominal offset 뒤 경과 시간 el이 τ보다 작으면, 다음 사용 = 지금 + δ(el, r)이다. δ는 남은 r개 추론 요청 중 가장 먼저 올 추론 요청까지의 조건부 기대 시간이다(uniform이면 (J − el)/(r + 1)).
4. 아니면 다음 사용 = 다음 주기 offset + δ(0, n)이다.
5. 다음 사용이 가장 늦은 모델을 내보낸다. 같으면 가장 오래 안 쓴 모델을 내보낸다.

이 규칙은 추론 요청별 지연만 있다고 본 식이다. 모델 그룹 전체가 늦으면 3의 조건(el < τ)이 먼저 깨져 곧 올 모델을 내보낸다. 모델 그룹 지연을 반영한 식은 P3.26 §2.2에 있다.

예상 추론 요청 수는 그 주기의 첫 추론 요청이 도착해야 안다(packet의 빈 byte 12–15에 싣는 protocol 확장, §8). 그 전에는 직전 주기의 값을 쓴다. 미래 도착 시각, 미래 추론 요청열, 난수는 읽지 않는다(§3.2 test 1). hardware 비용은 BRAM 0.5 tile(LUT)과 모델별 계수기다.

적재 수의 진짜 하한은 각 실행이 실제로 만든 batch 순서에 offline Belady를 적용해 따로 낸다. 이 하한은 작은 예 300개에서 전수 탐색 최솟값과 같았다.

모아 보내기 계산의 가정은 다음과 같다. 모두 성립하면 상한이 되지만, 지금은 A1·A2를 측정 최대로만 채웠으므로 보장이 아니다.

- A1. Host 처리 지연에 상한이 있고 D가 그 상한 이상이다. 여기서는 모델 그룹 지연을 0으로 두어 상한을 J로 썼다. 모델 그룹 지연이 있으면 상한은 그 최대 + J다(P3.26 §3.4).
- A2. 링크 지연에 상한이 있다(지금은 PCIe 표본 최대이고 보장값이 아니다. Ethernet은 재지 않았다).
- A3. 한 주기의 작업 R_single이 같은 모델 송신 사이 최소 간격보다 짧다. 그래서 바쁜 구간 하나에 같은 모델의 송신이 두 번 들어가지 않는다. engine의 모아 보내기는 다 준비되면 D 전에도 보내므로 최소 간격은 32 ms − (D − Host 처리 지연 최소)다(처음에는 32 ms로 적었다).
- A4. 한 모델·주기의 추론 요청이 한 번에 보내져 적재가 한 번뿐이다. Ethernet에서 packet 여러 개로 나뉘면 다시 확인해야 한다(P3.26 §3.4).

이 가정 아래 response time ≤ D + 링크 + R_single + 링크다. 작은 사례 전수 탐색(아래)과 adversarial search에서 모아 보내기는 모델·주기당 적재가 항상 1번이었다.

**작은 사례 전수 탐색**: 모델 5개, offset 간격 Δ = 6.4 ms, 트랙 10개, 지연 조합 435,456개다.

- 분석식 상한을 넘은 경우는 0이다.
- 모아 보내기는 모든 정책·entry에서 모델·주기당 적재가 1번이다.
- 즉시 송신 + PNU-Count는 entry ≥ ⌊J/Δ⌋ + 2일 때 재적재가 0이었다. LRU와 in-loop Oracle MIN은 이 조건에서도 재적재가 났다.

**1,024트랙 adversarial search**: 즉시 송신은 entry 4, jitter 0.8 ms(위 조건을 만족)에서도 한 모델이 한 주기에 2번 적재된 경우가 나왔다. 모든 입력 spike인 편중 시나리오에서 큰 모델 batch가 오래 연산하는 동안 여러 모델 추론 요청이 겹치기 때문이다. 그래서 위 조건은 일반 증명이 될 수 없고, 즉시 송신은 조건부 계산과 관측 최대만 보고한다.

### 4.8 Mic–Host 지연 분포 (end-to-end 참고)

## 6. 한계

- Response time의 Host 처리 지연은 0~J 균등이나 tail 분포로 넣었다. 측정에서 보인 "모델 그룹 지연 + 모델 안 퍼짐 0" 구조는 넣지 않았다(P3.26에서 넣음).
- 06 §4.3의 drop 규칙(같은 트랙의 이전 추론 요청이 끝나기 전에 온 추론 요청은 버림)을 simulation에 넣지 않았다(P3.26에서 넣음).
- 링크 지연은 PCIe 64 B 표본이다. Ethernet은 재지 않았다.
- Host 처리 지연 측정은 Xeon과 Python에서 timer로 깨어나는 방식으로 쟀다. 최종 Host와 오디오 callback에서는 다르다.
- 비교군은 원문 정책을 이 simulator의 FPGA scheduler 자리로 옮긴 것이다. 결정 시간과 회로는 0으로 뒀다.
- 41번째 모델은 학습·export가 없어 40모델 spike 표를 모아 썼다. 정확도는 P2.1~P2.2 기록(40개 평균 ROC-AUC 0.9563, 41개 0.9510)을 쓴다.
- PNU-Count의 예상 추론 요청 수는 06 §4.1 packet에 없는 필드다. protocol을 바꿔야 한다.
- 즉시 송신의 hard deadline은 증명하지 못했다.
