# P3.18 보고서: Offset Assignment 선행연구 검색 (IEEE Xplore API 대체 검색)

작성일: 2026-10-17

IEEE Xplore API가 HTTP 403(계정 비활성)으로 막혀서 IEEE 논문을 담은 OpenAlex와 Semantic Scholar로 같은 질문을 검색했다. 주기적으로 들어오는 카메라 데이터의 도착 시각을 맞춰 batch를 키운 연구(Nakayama 등)를 찾았다. [09_RELATED_WORK.md](../design_references/09_RELATED_WORK.md) §3의 주장 1과 겹치므로 신규성 경계를 좁혀야 한다. IEEE Xplore 검색은 계정이 활성화된 뒤 다시 한다.

## 1. 요약

### 1.1 환경

| 구분 | 내용 |
|---|---|
| IEEE Xplore API | HTTP 403, `ERR_403_DEVELOPER_INACTIVE`(Account Inactive). vault 키 형식은 정상(영숫자 24자) |
| 대체 검색 | OpenAlex는 IEEE 출판물만 제목·초록 boolean 검색. Semantic Scholar는 모든 출판사 제목·초록 boolean 검색 |
| 질의 | 주제 18개(§5). 도착 시각 맞추기, 주기 작업 batch, 다중 모델 가속기, model cache 교체, 다중 모델 SNN, membrane potential 저정밀 저장 |
| 확인 수준 | 초록과 서지. 전문은 받지 못했다 |

### 1.2 결과

| 질문 | 답 |
|---|---|
| 주기 센서 데이터의 도착 시각을 일부러 맞춰 batch를 키운 연구 | 있다. Nakayama·Onodera 등 3편(IEEE CCNC 2021, IEEE IoT-J 2022, JOCN 2023) |
| 같은 모델 트랙에 같은 offset을 주고 모델마다 offset을 다르게 둔 연구 | 못 찾았다 |
| offset 순서로 다음 모델 weight를 고르는 cache | 못 찾았다. 가장 가까운 것은 이미 확인한 RT-Swap |
| 여러 SNN 모델을 한 가속기에서 실행 | IncineRate(MCSoC 2025), Loihi 2 다중 network(2026). 주기 deadline과 weight DDR3 traffic은 다루지 않는다 |
| membrane potential 저정밀 저장 | IM-SNN(ICONS 2024) 등. 이미 주장하지 않는 범위다 |

### 1.3 결론

1. 주기 센서 데이터를 같은 시각에 도착시켜 기다리지 않고 batch를 만드는 일은 Nakayama 외가 먼저 했다. 이들은 TWDM-PON 상향 대역을 배정해 카메라 영상이 edge GPU 서버에 같은 시각에 도착하게 하고 batch를 키웠다.
2. 이번 검색에서도 못 찾은 부분은 두 가지다. 하나는 모델마다 offset을 따로 주는 배정이고, 다른 하나는 그 offset 순서로 FPGA weight cache를 교체해 DDR3 traffic을 줄이는 결합이다.
3. 09 §2·§3과 DAC 원고에 Nakayama 외를 넣고 주장 1을 모델 단위로 좁혀야 한다. 수정안은 §4에 있다. 사용자 결정 전이라 설계 정본과 원고는 고치지 않았다.

### 1.4 한계와 남은 일

- IEEE Xplore 자체 검색은 하지 못했다. developer.ieee.org 계정을 활성화한 뒤 §5 질의로 다시 한다.
- 단어 검색이라 다른 표현으로 쓴 연구는 놓쳤을 수 있다. Semantic Scholar 의미 검색은 호출 제한(HTTP 429)에 걸려 거의 쓰지 못했다.
- Nakayama 등 전문을 받지 못해 여러 모델을 다루는지 모른다. IoT-J판은 구독 논문이고, 저자 기관 저장소는 HTTP 403으로 막혀 있다.
- 이상음 탐지 hardware 질의(H, Semantic Scholar 131건)는 선별하지 않았다.

## 2. 방법

### 2.1 IEEE Xplore API

`ieeexploreapi.ieee.org/api/v1/search/articles`를 https와 http로, `querytext`와 `article_number` 질의로 불렀다. 세 번 모두 같은 403과 `X-Error-Detail-Header: Account Inactive`가 왔다. 키 값이 아니라 IEEE 개발자 계정 상태가 원인이다. 가입 이메일 확인이나 IEEE의 키 승인이 끝나지 않은 것으로 보인다(추정).

### 2.2 대체 검색

| 도구 | 범위 | 쓴 방식 |
|---|---|---|
| OpenAlex `title_and_abstract.search` | IEEE 출판물(publisher `P4310319808`, `P4322697011`) | boolean 질의. IEEE 논문 초록이 거의 다 들어 있다 |
| OpenAlex `search` | 위와 같고 본문까지 검색 | 처음 10개 질의에서 관계없는 결과가 대부분이라 버렸다 |
| Semantic Scholar `paper/search/bulk` | 모든 출판사 | boolean 질의. DOI로 IEEE 논문인지 본다 |
| OpenAlex 인용 관계 | Nakayama 등 3편을 인용한 12편 | 여러 모델로 넓힌 후속 연구는 없었다 |

결과는 제목으로 고르고, 고른 논문은 초록을 읽었다. OpenAlex는 API 키 없이 IP당 하루 $0.10(검색 약 100회) 한도 안에서 썼다.

## 3. 결과

### 3.1 가장 가까운 연구: Nakayama·Onodera 등

| 저자 | 서지 |
|---|---|
| Onodera, Inoue, Hisano, Nakayama | IEEE CCNC 2021, pp. 1–6, DOI 10.1109/CCNC49032.2021.9369452 |
| Nakayama, Onodera, Nguyen, Hara-Azumi | IEEE Internet of Things Journal 9(18), pp. 17348–17358, 2022, DOI 10.1109/JIOT.2022.3155606 |
| Onodera, Inoue, Hisano, Yoshimoto, Nakayama | Journal of Optical Communications and Networking 15(7), 2023, DOI 10.1364/JOCN.476116 |

초록 내용은 이렇다. network camera 여러 대가 주기적으로 영상을 올리고 edge GPU 서버가 물체를 검출한다. 카메라와 서버는 TWDM-PON으로 이어진다. PON의 상향 wavelength와 bandwidth를 배정해 데이터가 낮은 지연으로, 같은 시각에 서버에 도착하게 한다(time-synchronized 데이터 arrival). 한 번에 도착하는 데이터가 늘어 batch가 커지고 GPU 계산 효율이 오른다. IoT-J판은 배정 문제를 SAT로 풀었다. 세 편 모두 computer simulation으로 확인했다.

| 비교 | Nakayama 등 (초록 기준) | 이 설계 |
|---|---|---|
| 도착 시각을 맞추는 곳 | network(PON 상향 대역 배정) | Host(frame을 자르는 위치 = offset) |
| 모델 | 모델별 구분 언급 없음 | 모델 40개, 모델마다 다른 offset |
| 가속기 | GPU | FPGA, BRAM weight cache |
| 줄이는 것 | GPU 계산 시간·에너지(batch 크기) | DDR3 traffic, response time |
| 다음 모델 정보 | 언급 없음 | offset 순서로 cache 교체 |
| 추론 요청 사이 state | 언급 없음 | 트랙별 membrane potential |

### 3.3 찾지 못한 것

아래는 이번 검색 범위에서 보지 못한 것이다. 같은 연구가 없다는 뜻은 아니다.

- 같은 모델 트랙에 같은 offset을 주고 모델마다 offset을 다르게 두는 배정
- Host가 정한 offset 순서로 다음 모델 weight를 고르는 가속기 cache
- 다중 모델·다중 트랙 SNN 가속기에서 트랙별 membrane potential을 따로 두고 weight를 함께 쓰는 구조

## 4. 신규성 경계 수정안 (사용자 결정 필요)

| 위치 | 지금 | 수정안 |
|---|---|---|
| 09 §2 표 | 없음 | Nakayama 등 행 추가. 하는 일: 주기 카메라 영상이 edge GPU에 같은 시각에 도착하도록 PON 상향 대역을 배정해 batch를 키운다. 다른 점: 모델별로 도착 시각을 나누지 않고 weight cache와 DDR3 traffic을 다루지 않는다(초록 기준) |
| 09 §3 주장 1 | 같은 모델을 쓰는 센서 stream에 같은 frame offset을 주어, FPGA에 도착한 순간부터 weight 재사용이 가능하게 만든다 | 모델마다 다른 frame offset을 주고 같은 모델 트랙은 같은 offset을 받게 한다. 그래서 모델별 추론 요청이 함께 도착하고, 다음에 쓸 모델이 미리 정해진다 |
| 09 §3 주장하지 않는 범위 | 없음 | 주기 센서 데이터의 도착 시각을 맞춰 기다리지 않고 batch를 키우는 것 자체 (Nakayama 등) |
| 09 §4 남은 조사 | 웹 검색·OpenAlex 결과 없음. IEEE Xplore API 승인 대기 | IEEE Xplore API 계정 비활성. 대체 검색에서 Nakayama 등 발견. Nakayama 등 전문 미확보 행 추가 |
