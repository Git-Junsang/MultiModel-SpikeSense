# P4.8 보고서: 라즈베리파이 5 Host program

작성일: 2026-10-25

라즈베리파이 5에서 돌릴 Host program `mmss_host`를 C로 만들었다(`software/host`). 시작 설정, 특징 추출, Offset Assignment, 즉시 송신, FPGA 시각 맞추기, 판정, deadline 확인을 한다. 라즈베리파이 5가 아직 오지 않아 개발 서버에서 aarch64로 크로스 빌드하고 qemu-aarch64(유저 모드 에뮬레이션)로 돌렸다. FPGA 자리에는 Python으로 만든 FPGA mock을 두었다. 기능 확인이고, 시간 값은 Pi나 보드의 값이 아니다.

## 1. 요약

### 1.1 환경

| 구분 | 내용 |
|---|---|
| 빌드 | 개발 서버 LXC 200(i5-14600K). `aarch64-linux-gnu-gcc-11`(11.5.0), glibc 2.39 정적 링크, `-O2 -mcpu=cortex-a76`. 정적 링크라 Pi OS의 glibc 판과 상관없다 |
| 실행 | `qemu-aarch64` 8.2.2(유저 모드). FPGA mock `mock_fpga.py`와 localhost UDP |
| FPGA mock | 06 §4 packet과 §7 주소 공간(정보·상태·제어·시각·설정·counter·오류·PNU 표·DDR3 창)을 흉내 낸다. 결과는 Host가 DDR3 창에 적재한 slot을 02 §6 배치로 읽어 snn_int8과 같은 정수 연산으로 낸다(12 bit 저장). NOW_US는 시작 5초 뒤 2^32에서 되감긴다 |
| 기준 | 특징: `p325_mel_load.py`의 `mel_db`·`SegNorm`과 `snn_int8.quantize_input`(numpy 2.4.6, librosa 0.11.0). 결과: `snn_int8.forward`(checkpoint 양자화, `store_bits=12`). PNU 표: 04 §3.1 식, engine `PNURTL._tables` |
| 입력 | 2채널 WAV. 채널 0은 `fan/test/normal_id_06_00000000.wav`, 채널 1은 `anomaly_id_06_00000000.wav`(10 s). 트랙 34개: 0–29는 모델 5(`fan_id06`), 30–33은 모델 0·1·39·20. 트랙 i는 채널 i % 2 |
| 시험 | `software/host/verify_host.py`. `run --pace`(실시간 속도), 결과 1개 버림(트랙 31 seq 40), 결과 1개 45 ms 늦춤(트랙 7 seq 70) |

### 1.2 결과

| 질문 | 답 |
|---|---|
| 시작 설정이 맞는가 | 모델 image 40개(slot마다 131,648 B)가 DDR3 창에 그대로 있다. 설정 블록, `OFFSET_TABLE`, `N_REG`가 맞다 |
| PNU 표 | `TAU_G`·`TAU_U`·`EG`·`LUT_G`·`LUT_U`가 04 §3.1 식과 같다. engine 표와는 `LUT_G` 최대 6 µs, `EG`·`TAU_G` 0 µs 다르다(§2.4) |
| 추론 요청 필드 | 10,573개 모두 `model_id`, `RESET_STATE`(k % 31 = 0), `n_expect`(모델별 트랙 수), 빈 byte 0이 맞다. 트랙 30개 모델은 datagram 23개 + 7개로 나뉜다 |
| `t_host_us` | FPGA 시각 기준이다. 받은 시각보다 0–5.7 ms 앞서고, 같은 트랙의 이웃 frame 차이가 31,991–32,013 µs, 다시 돌린 실행에서 31,973–32,027 µs다. 1초마다 시각 차이를 다시 구해 수십 µs 움직인다. 2^32 되감기를 1번 지났다 |
| 특징 | 값 422,920개(추론 요청 10,573개 × mel 40개)가 Python 기준과 모두 같다. 일부러 offset을 1샘플 틀린 기준과 비교하면 트랙 하나에서 330/12,440개, 373/12,400개가 다르다 |
| 결과 | 버린 추론 요청이 없는 판정 주기 339개의 out0·out1이 `snn_int8.forward`와 모두 같다. 모델 image 적재와 `RESET_STATE`가 맞다는 뜻이다 |
| 판정 | 판정 339개의 decision이 Python 판정과 같고 score 차는 1e-9 미만이다. 버린 추론 요청이 든 판정 주기는 판정하지 않았다. 모델 5 트랙은 정상 채널 150개 중 이상 판정 0개, 이상 채널 150개 중 150개다 |
| deadline 집계 | sent 10,573, recv 10,572, lost 1, late 1, deadline miss 2, 판정 못 한 판정 주기 1, unmatched 0 |
| stdin 입력 | WAV와 raw 2채널을 pipe로 넣어도 추론 요청 10,573개, 특징 차이 0 |
| 처리량(참고, x86) | i5-14600K 한 core(native 빌드, `--cpu 2`)에서 추론 요청 하나의 특징 추출 p50 3.9 µs. 1,024트랙이면 주기 32 ms마다 4.0 ms다. Pi 5 값이 아니다 |

### 1.3 결론

1. 06 §2의 Host 역할 중 입력·특징 추출·Offset Assignment·즉시 송신·예상 추론 요청 수·시각·판정·deadline 확인·시작 설정을 한 program으로 만들었다.
2. 특징 추출은 Python 기준과 0–127 값까지 같다. 판정도 같은 결과로 Python과 같다.
3. `run --log`가 남기는 모델 그룹 표는 모델 그룹 지연 표 형식(`epoch, model_id, delay_us`)이다. engine `TraceJitter`가 그대로 읽는다. 그래서 Pi에서 잰 모델 그룹 지연을 PNU 표(`setup --model-group-delay-trace`)와 simulation(`host_model_group_delay_trace`)에 바로 넣을 수 있다.

## 2. 설계

### 2.1 구성

```text
mmss_host setup  06 §6 1~6: ID·MIG 보정 확인 → 모델 image 적재·다시 읽기 → 설정 → PNU 표 → SOFT_RESET → RUN = 1
mmss_host run    오디오 → frame → 특징 추출 → 추론 요청 송신 → 결과 수신 → 판정·deadline 확인
mmss_host stop   IDLE = 1을 기다려 RUN = 0, counter와 첫 오류 출력
```

| 파일 | 내용 |
|---|---|
| `main.c` | 하위 명령과 사용법 |
| `mel.c` | Hann 창, 실수 FFT 1,024(복소 FFT 512 + 분리), Slaney mel 40, dB, seg 정규화, 0–127 |
| `ctl.c` | 제어 packet(응답이 없으면 같은 tag로 다시 보냄), 시각 맞추기, 트랙 → 모델 대응 |
| `setup.c` | 시작 설정, PNU 표 계산, 종료 |
| `run.c` | 실행. thread 3개(계산, 수신, 시각) |

`run`의 계산 thread만 `--cpu`로 고정한다(06 §2 가정 1). 수신 thread는 결과를 받자마자 시각을 찍고 판정한다. 시각 thread는 1초마다 FPGA 시각과의 차이를 다시 구한다.

### 2.2 입력과 frame 경계

| 항목 | 규칙 |
|---|---|
| 입력 | S16LE 16 kHz. WAV(RIFF)면 머리말에서 채널 수를 읽고, 아니면 `--channels` 채널 raw. 파일이나 stdin(`arecord` pipe) |
| 트랙 | `--map` 파일 한 줄 = 트랙 하나의 model_id. 없으면 트랙 i의 모델은 i % 40. 트랙 i는 채널 i % C |
| offset | 모델 m의 offset은 12.8m 샘플에 가장 가까운 샘플 `(512m + 20) / 40`(정수 나눗셈). nominal offset과 차이는 25 µs 이하다 |
| frame | 모델 m 주기 k = 샘플 `[O_m + 512k, O_m + 512k + 1,024)`. 모든 frame 끝이 offset 순서라 사건 번호 하나(n → m = n % 40, k = n / 40)로 차례대로 처리한다 |
| `t_host` | 그 frame의 마지막 샘플이 든 block이 들어온 시각. `--pace`(파일을 실시간 속도로 읽음)면 block이 들어올 예정 시각, pipe면 `read()`가 돌아온 시각 |

`--pace`에서 계산이 늦어도 `t_host`는 예정 시각으로 둔다. 그래야 밀린 시간이 모델 그룹 지연에 들어간다. 다음 block 시각까지 계산을 못 끝낸 횟수는 `overrun`으로 센다.

### 2.3 특징 추출과 송신

특징 식은 학습 특징을 frame 하나에 쓴 `p325_mel_load.py`와 같다(02 §3·§4). 실시간 정규화는 아직 정하지 않았다(02 §5, TASKS P2.9). 그래서 P3.21에서 손실이 가장 적던 seg 방식을 쓴다. 판정 주기 첫 frame부터 지금까지의 최대·최소 dB로 늘이고, 최소는 최대 − 80 dB 아래로 내리지 않는다.

```text
x → periodic Hann 1,024 → FFT → |X|² → Slaney mel 40 → 10·log10(max(S, 1e-10))      (float32)
seg 정규화 → clip(rint(x × 127), 0, 127)                                              (float64)
```

모델 그룹은 트랙을 모두 계산한 뒤 datagram 하나에 23개씩 이어서 보낸다(06 §2 가정 2·3). `n_expect`는 그 모델의 트랙 수, `RESET_STATE`는 k % 31 = 0이다. 학습의 파일 단위 평균 빼기는 하지 않는다. Slaney mel 첫 filter의 0 Hz 칸 weight가 0이라 영향이 작다.

### 2.4 PNU 표

`setup --model-group-delay-trace <CSV> --jitter-us J`가 06 §7.4 표를 만든다. CSV는 `delay_us` 열만 읽는다.

```text
LUT_G[i]     = G > e인 표본의 (G − e) 평균, e = (i + 0.5) × 256 µs      EG = G 평균     TAU_G = G 최대(올림)
LUT_U[i][rb] = (J − x) / (r_rb + 1), x = (i + 0.5) × 256 µs < J          TAU_U = J
r_rb         = 1, 2, 3.5, 6.5, 12.5, 24                                 (rb 6·7은 0)
```

engine은 δ_G를 5 µs 칸으로 반올림한 e에서 수치 적분한다. 그래서 같은 표본(Xeon CPU 고정·부하 없음 모델 그룹 지연 표의 앞 절반, 187,160개)에서 `LUT_G`가 최대 6 µs 다르다. 표 칸이 256 µs라 무시한다. `LUT_U`, `EG`, `TAU_G`는 같다.

### 2.5 시각과 판정

| 항목 | 규칙 |
|---|---|
| 시각 | `NOW_US`를 5번 읽어 왕복이 가장 짧은 값으로 `clock_diff = f − (h1 + h2) / 2`(06 §5). 시작할 때와 1초마다. µs 32 bit라 2^32로 되감아 더한다 |
| 결과 짝 | 트랙마다 최근 추론 요청 8개의 (주기, `t_host`)를 둔다. 결과의 seq로 주기를 찾는다. 같은 트랙의 8번째 다음 추론 요청(약 256 ms 뒤)을 보낸 뒤에 온 결과는 unmatched로 센다 |
| response time | 결과를 받은 시각 − `t_host`(Host clock). 32 ms를 넘으면 late |
| 판정 | 판정 주기마다 out0·out1 합. 합이 더 큰 쪽(같으면 0). score = 1 / (1 + e^(−(s1 − s0) / 31 × scale)), scale은 manifest의 `weight_scales[3]` |
| 결과 누락 | 31개를 못 채운 판정 주기는 판정하지 않는다. 끝에서 (다 보낸 판정 주기 수 − 판정 수)를 `missing_cycles`로 낸다 |
| deadline miss | late + lost(보냄 − 받음) |

### 2.6 출력

| 출력 | 내용 |
|---|---|
| stdout | 판정 `track_id, cycle, model_id, decision, score` |
| stderr 끝 줄 | `summary sent= recv= late= lost= deadline_miss= judged= missing_cycles= unmatched= response_time_mean_us= response_time_max_us= overrun= send_err= sync_ok= sync_fail= sync_rtt_max_us= audio_s=` |
| `<이름>_result.csv` | 결과마다: 결과 32 B 필드, 주기, `t_host_ns`, `t_recv_ns`, `response_time_us` |
| `<이름>_model_group.csv` | 모델 그룹마다: `epoch, model_id, delay_us`(= 계산 끝 − `t_host`), 추론 요청 수, `t_host_ns`, 계산 시작, 계산 끝, 마지막 datagram 송신 |

## 3. 검증과 한계

- qemu와 FPGA mock에서 한 기능 확인이다. qemu response time(평균 3.0 ms)과 overrun 2번에는 에뮬레이션과 Python 대역의 시간이 섞여 있어 성능 근거가 아니다.
- 라즈베리파이 5와 보드에서는 돌리지 않았다. Pi의 1,024트랙 처리량과 모델 그룹 지연은 P3.16 측정 1이다.
- pipe 입력의 `t_host`는 `read()` 시각이다. Mic의 block 도착 시각과 다를 수 있다. Mic를 붙이면 ALSA timestamp로 바꾼다.
- 실시간 정규화는 임시로 seg 방식이다. 방식을 정하면(P2.9) `mel.c`의 `seg_norm_q`를 바꾼다.
- FPGA mock의 batch는 datagram 단위다. 실제 Grouping batch, `LATE` flag, 드롭 규칙(06 §4.3 오류 5)은 흉내 내지 않는다.
- FPGA가 없을 때 connect한 UDP socket은 ICMP를 받은 뒤 송신이 실패한다(`send_err`). 보드와 직접 연결하면 해당하지 않는다.
