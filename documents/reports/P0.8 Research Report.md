## 1. 요약

Phase 0의 마지막 항목이다. 할 일은 두 가지였다. 하나는 저장소 디렉터리 골격 확정이고, 다른 하나는 선행 SpikeSense-Edge의 NumPy 순전파(`test_model_numpy.py`) 재현이다. 이 프로젝트는 P1.4에서 40대 학습을 먼저 끝냈다. 그래서 선행 코드 재현에 더해, 학습한 새 모델(`40→384→256→64→2`)의 순전파를 PyTorch 없이 NumPy로 다시 구현하고 PyTorch와 출력이 같은지 확인했다.

| 항목 | 결과 |

이 단계의 핵심 판단은 **"FP 단계에서는 판정·AUC 일치를 통과 기준으로 하고, 비트 일치는 INT8 이후에만 요구한다"**는 것이다. FP32 행렬곱은 덧셈 순서에 따라 결과가 조금씩 달라서 임계값에 붙은 뉴런은 발화 여부가 드물게 뒤집힌다. 정수 연산에는 이런 차이가 없다.

이로써 Phase 0(P0.1~P0.8)이 끝났다.

## 2. 이 단계의 목적과 제약

### 2.1 왜 NumPy 순전파를 따로 두는가

하드웨어 검증에 쓰는 골든 참조(P1.7)는 PyTorch 없이 NumPy로 만든다. PyTorch는 학습용 프레임워크라 자동 미분, surrogate gradient, GPU 배치 처리가 들어 있고, 뉴런 갱신이 모듈 내부에서 처리된다. 골든 참조는 RTL이 하는 일을 타임스텝·층 단위로 한 줄씩 드러내야 이후 RTL과 값을 하나씩 대조할 수 있다.

손으로 다시 구현하면 옮기는 과정에서 세부 규칙이 틀어질 수 있다. 틀어지기 쉬운 곳은 다음과 같다.

- 시간상수 표현: `beta = sigmoid(w_beta)`인지, 1/τ인지
- 입력에도 감쇠를 곱하는지
- 리셋 방식: hard reset인지 soft reset인지
- 충전·발화·리셋 순서와 막전위 초기값
- 임계값 비교가 `>=`인지 `>`인지
- 판정 방식: 스파이크 수로 하는지, 막전위 시간 평균으로 하는지

INT8로 바로 가면 결과가 어긋났을 때 원인이 양자화 오차인지 구현 오류인지 구분할 수 없다. 그래서 오차 원인을 한 단계씩 분리한다.

> PyTorch FP → **NumPy FP (P0.8)** → NumPy INT8 (P1.7) → RTL (P3.1)

### 2.2 제약

| 제약 | 근거 |
|---|---|
| 선행 저장소는 읽기만 한다 | 동결된 설계 보호 (AGENTS.md). 선행 코드는 `software/model_develop/references/` 사본으로 실행하고, 가중치·골든 벡터만 선행 저장소에서 읽었다 |
| NumPy 구현에 PyTorch를 쓰지 않는다 | 순전파는 NumPy만으로 수행. `.pth` 파일 읽기에만 torch를 쓴다 |
| 뉴런 규칙은 P1.3과 같다 | 누설 → 적분 → 발화 → soft reset, `plift_core.v`와 같은 순서 (P1.3 리포트 §5) |
| GPU를 쓰지 않는다 | 학습 GPU는 다른 작업이 쓰고 있었다. 비교는 개발 서버 CPU(12스레드)에서 FP32로 수행 |

## 4. 선행 NumPy 순전파 재현

### 4.1 방법

선행 `test_model_numpy.py`는 INT8 정수 연산으로 `40→128→32→2` 순전파를 수행한다. 이 코드를 선행 저장소의 가중치 HEX(`hardware/src/weights/w1~3.hex`, `beta.hex`, `vth.hex`)로 실행하고, 선행 골든 벡터와 비교했다.

선행 코드를 `--golden` 옵션으로 실행하면 선행 저장소 안에 파일을 덮어쓴다. 그래서 스크립트를 그대로 실행하지 않고, 검증 스크립트에서 선행 코드의 함수(`snn_forward`)만 불러 메모리 안에서 비교했다.

### 4.2 결과

| 입력 | 출력 막전위 `[31, 2]` (npy) | 출력 스파이크 (npy) | 출력 막전위 (`$readmemh` hex) | 판정 |
|---|---|---|---|---|
| normal (31×40) | 일치 | 일치 | 일치 | 0 |
| anomaly (31×40) | 일치 | 일치 | 일치 | 0 |

두 입력 모두 **비트 단위로 일치**했다.

### 4.3 해석

선행 골든 입력은 선행 스크립트가 베타 분포 난수로 만든 합성 mel이다. 이름과 달리 anomaly 입력도 정상(0)으로 판정된다. 따라서 이 재현이 보여 주는 것은 **선행 코드와 선행 벡터 사이의 정합성**이다. 선행 모델의 탐지 성능과는 관계가 없다. 이 결과로 선행 INT8 정수 연산 스펙(Q0.8 beta, `>> 8`, INT16 포화, 층 1 `>> 7`)이 문서와 코드와 벡터에서 서로 맞다는 것을 확인했고, P1.7에서 이 연산을 그대로 가져올 수 있다.

## 5. 새 모델 FP32 NumPy 순전파

### 5.1 구현

`software/model_develop/snn_numpy.py`에 두 함수를 두었다.

- `load_params(pth)`: 체크포인트에서 층별 `W`, `beta = sigmoid(w_beta)`, `thr = max(w_thr, 0.1)`을 float32 NumPy 배열로 꺼낸다
- `forward(layers, x)`: 타임스텝마다 층 1 → 4 순서로 아래를 수행한다

```
mem   = beta · mem + W · x      # 누설 → 적분 (bias 없음)
spike = (mem >= thr)
mem   = mem - spike · thr       # soft reset
```

막전위 초기값은 0이다. 층 1 입력은 mel 특징값(연속값 [0, 1])이고 층 2~4 입력은 앞 층 스파이크다. 판정은 출력층 막전위(리셋 후 값)의 시간 평균 argmax다. 모든 연산을 float32로 맞췄다. NumPy 기본인 float64로 두면 PyTorch(float32)와 반올림이 달라져 비교 대상이 흐려진다.

### 5.2 비교 방법

`software/analysis_develop/check_numpy_fp.py`로 수행했다.

| 항목 | 내용 |
|---|---|
| 대상 모델 | `software/model_weights/<장비>/last.pth` 40개 (P1.4 채택본) |
| 입력 | 각 장비의 DCASE test 평가 세트. 학습과 같은 `train.prepare`(supervised, seed 42) 분할로 P1.4 평가와 같은 세그먼트다. 40대 합계 129,792개, 세그먼트당 31 타임스텝 |
| PyTorch 쪽 | CPU FP32. 층별 스파이크를 받기 위해 층 루프를 직접 돌렸고, 그 결과가 `AnomalySNN.forward`와 같은지 assert로 확인했다 |
| 비교 항목 | 층별 스파이크(4개 층·모든 타임스텝), 출력 막전위, 세그먼트 판정, 파일 단위 ROC-AUC. AUC는 P1.4 `results.csv`(GPU 평가값)와도 비교 |
| 소요 | 40대 약 1분 |

### 5.3 결과

| 항목 | 결과 |
|---|---|
| 스파이크가 완전히 같은 장비 | **29 / 40** |
| 스파이크가 다른 장비 | 11 / 40. 전체 스파이크 약 28.4억 개 중 200개 (7×10⁻⁸), 세그먼트 14개 |
| 스파이크가 같은 장비의 출력 막전위 최대 오차 | 3.8×10⁻⁵ |
| 세그먼트 판정 불일치 | 129,792개 중 **1개** (ToyConveyor_id03) |
| 파일 단위 AUC (NumPy vs PyTorch CPU) | 39대는 소수 6자리까지 같다. ToyConveyor_id03은 0.986303 → 0.986296 (차이 7×10⁻⁶) |
| 파일 단위 AUC (NumPy vs P1.4 GPU) | 40대 모두 소수 4자리까지 같다 |

### 5.4 스파이크 차이는 반올림에서 온다

FP32 행렬곱의 덧셈 순서는 BLAS 구현(NumPy, PyTorch CPU, GPU)마다 다르다. 막전위가 임계값에 거의 닿은 뉴런은 이 반올림 차이만으로 발화 여부가 달라진다. 한 번 뒤집힌 스파이크는 soft reset과 다음 층 입력을 거쳐 같은 세그먼트의 뒤쪽 타임스텝과 뒤쪽 층으로 퍼진다. 차이가 출력층까지 퍼진 8대에서는 출력 막전위 최대 오차가 0.6~1.5로 커졌다. 은닉층에서 멈춘 3대(fan_id04, valve_id00, ToyCar_id06)는 10⁻⁵ 수준에 머물렀다.

구현 오류가 아님을 확인하려고, 스파이크가 다른 11대 전부에서 세그먼트별로 **처음** 스파이크가 달라진 지점을 찾고 그 순간의 |mem − thr|를 쟀다.

| 장비 | 분기 세그먼트 | 첫 분기 \|mem − thr\| 최대 |
|---|---|---|
| fan_id04 | 1 | 1.0×10⁻⁶ |
| pump_id00 | 1 | 1.2×10⁻⁷ |
| slider_id02 | 1 | 2.1×10⁻⁷ |
| valve_id00 | 1 | 3.0×10⁻⁷ |
| valve_id04 | 1 | 1.2×10⁻⁷ |
| ToyCar_id02 | 2 | 7.2×10⁻⁷ |
| ToyCar_id04 | 1 | 1.8×10⁻⁷ |
| ToyCar_id05 | 1 | 0 (정확히 임계값) |
| ToyCar_id06 | 1 | 0 (정확히 임계값) |
| ToyConveyor_id02 | 1 | 6.0×10⁻⁸ |
| ToyConveyor_id03 | 3 | 3.1×10⁻⁶ |

14개 분기가 모두 FP32 반올림 범위(~10⁻⁶) 안에서 시작했다. 구현 규칙이 하나라도 달랐다면 분기는 임계값과 무관한 곳에서 대량으로 생겼을 것이다. 예를 들어 `>` 비교였다면 임계값과 정확히 같은 막전위에서 체계적으로 달라지고, 리셋 방식이 달랐다면 첫 발화 직후부터 모든 세그먼트가 달라진다. 이 결과로 **NumPy 구현의 뉴런 규칙이 PyTorch와 같다**고 판단한다.

유일한 판정 불일치(ToyConveyor_id03의 세그먼트 1개)도 이 분기가 출력층까지 퍼진 결과다. 파일 단위로는 세그먼트 확률을 평균하므로 AUC 변화는 7×10⁻⁶에 그쳤다.

## 6. 확인한 것과 확인하지 않은 것

**확인한 것**

- 선행 INT8 NumPy 순전파가 선행 골든 벡터(막전위·스파이크·hex)를 비트 단위로 다시 만든다
- 새 모델 FP32 NumPy 순전파가 40대 test 세트에서 PyTorch와 판정 129,791/129,792, 파일 AUC 소수 4자리까지 일치한다
- 스파이크 차이 200개는 모두 임계값 ±3.1×10⁻⁶ 이내의 반올림에서 시작한다 (11대 전수 확인)
- 디렉터리 골격이 현재 산출물 전부를 수용한다

**확인하지 않은 것**

| 항목 | 어디서 하는가 |
|---|---|
| NumPy INT8 순전파와 정확도 저하폭 | P1.5, P1.7 |
| NumPy INT8 골든과 RTL의 비트 일치 | P3.1 (xsim) |
| 선행 모델의 탐지 성능 재현 | 수행하지 않음. 선행 골든 입력은 합성 데이터라 성능 확인에 쓸 수 없다 |
| Host 응용 코드 폴더 위치 | Phase 3 |

## 7. 이후 작업에 남기는 사항

1. **P1.7 골든 참조 작성 방식**: `snn_numpy.py`의 층 루프에 선행 `test_model_numpy.py`의 정수 연산(Q0.8 beta, `>> 8`, INT16 포화, 층 1 시프트)을 넣는다. 층이 3개에서 4개로 늘었으므로 선행처럼 층을 펼쳐 쓰지 않고 반복문으로 일반화한다.
2. **검증 기준의 분리**: FP 참조 사이의 비교는 판정·AUC 일치로 판단한다. 비트 일치는 INT8 골든 ↔ RTL에서만 요구한다. P1.5에서 INT8 정확도를 볼 때도 FP 기준값은 PyTorch 또는 `snn_numpy` 중 어느 쪽을 써도 결과가 같다.
3. **층 1 입력 형식**: 새 모델도 선행처럼 mel 연속값을 층 1에 직접 넣는다(스파이크 부호화 없음). INT8에서 선행과 같은 `round(mel × 127)`과 층 1 `>> 7` 시프트를 그대로 쓸지는 층 1 누적값 범위를 보고 P1.5·P1.7에서 정한다.
4. **선행 스크립트 실행 주의**: 선행 `test_model_numpy.py --golden`은 가중치 폴더 안에 파일을 쓴다. 선행 저장소를 대상으로 이 옵션을 쓰지 않는다.

다음 단계는 **P1.2의 남은 항목(트랙↔모델 매핑 초안)**이고, 그다음은 P1.5 INT8 양자화다.
