## 1. 이 논문은 어떤 문제를 푸는가

레이어별 파이프라인 가속기는 신경망의 각 레이어에 전용 연산 장치를 배정한다. 여러 입력이 서로 다른 레이어를 동시에 지나갈 수 있어 처리량을 높이기 좋다. 그러나 각 레이어의 가중치를 온칩에 보관하려면 많은 메모리가 필요하다.

AutoWS는 **가중치의 일부만 온칩에 계속 두고, 나머지는 필요할 때 외부 메모리에서 가져오는 방식**을 자동으로 설계한다. 어떤 레이어의 가중치를 얼마나 내보낼지 정할 때 온칩 용량, 연산 자원, 외부 메모리 대역폭을 함께 고려한다.

핵심은 온칩 저장 공간을 줄이는 대신 전송을 늘리는 것이다. 메모리에 안 들어가던 모델을 실행할 수 있게 되지만, 대역폭이 부족하면 오히려 느려질 수 있다.

## 2. 가중치 저장과 전송을 어떻게 나누는가

### 계속 보관할 부분과 교체할 부분을 정한다

각 레이어의 가중치를 여러 **조각(fragment)** 으로 나눈다. 각 조각에는 온칩에 계속 남기는 부분과 오프칩에서 공급하는 부분이 있다. 오프칩 부분은 작은 공유 버퍼를 거쳐 연산 장치에 전달된다.

예를 들어 가중치의 일부를 온칩에 남겨두면, 연산 장치가 그 부분을 읽는 동안 버퍼에 다른 가중치를 채울 수 있다. 이렇게 교대로 읽고 채우면서, 모든 가중치를 동시에 온칩에 둘 필요를 줄인다.

오프칩에 두는 비율이 커질수록 필요한 전송 대역폭도 커진다. **온칩 공간을 얼마나 아낄 수 있는지는 남은 대역폭에 달려 있다.**

### 여러 레이어가 전송기를 기다리지 않게 한다

여러 레이어가 하나의 **DMA**, 즉 메모리 전송 장치를 함께 사용한다. DMA가 한 레이어의 가중치를 오래 쓰고 있으면 다른 레이어는 필요한 데이터가 올 때까지 멈출 수 있다.

AutoWS는 조각 수를 조정해 레이어별 전송 버스트의 반복 횟수를 맞춘다. 이를 **write burst balancing**이라고 부른다. 전송 순서와 각 레이어에 할당할 구간도 미리 정한다. 레이어의 실행 순서가 정해진 파이프라인이므로 가능한 정적 계획이다.

공유 버퍼는 읽기와 쓰기를 각각 처리할 수 있는 듀얼포트 BRAM으로 구성한다. 계산 쪽과 DMA 쪽에 서로 다른 클럭을 사용할 수 있으며, 아직 쓰지 않은 데이터를 먼저 읽지 않도록 제어한다.

### 가장 느린 레이어부터 개선하고, 부족한 공간을 확보한다

설계 자동화는 두 작업을 반복한다. 먼저 파이프라인에서 가장 느린 레이어에 연산 자원을 더 배정한다. 그 결과 온칩 메모리가 부족해지면, 가중치를 일부 오프칩으로 옮긴다.

이때는 **같은 저장 공간을 확보하더라도 추가 대역폭이 덜 드는 레이어**부터 선택한다. 모든 조합을 전부 탐색하는 대신, 현재 조건에서 유리한 변경을 반복하는 탐욕적 설계공간 탐색이다.

## 3. 어떤 결과를 보였는가

ResNet-18을 ZCU102에 배치한 설계점에서, 모든 가중치를 온칩에 두는 구성과 AutoWS를 비교한 결과는 다음과 같다. 단위는 논문 표 3의 표기를 따른다.

| 항목 | 전체 가중치 온칩 | AutoWS |
|---|---:|---:|
| 가중치 저장 메모리 | 8.3 MB | 4.6 MB |
| 전체 온칩 메모리 | 8.7 MB | 5.1 MB |
| 장치 메모리 대비 사용률 | 172% | 99% |
| 전체 오프칩 대역폭 | 0.1 Gbps | 105.1 Gbps |
| 처리량 | 141 FPS | 142 FPS |

왼쪽 구성은 요구 메모리가 장치 용량을 초과하므로 그대로 배치할 수 없는 설계점이다. AutoWS는 **비슷한 처리량을 목표로 하면서 메모리 요구량을 장치 용량 안으로 줄였다.** 이때 21개 레이어 중 5개의 가중치 일부를 오프칩으로 옮겼다.

논문 본문에는 ‘BRAM 70% 절감’이라는 표현이 있지만, 표의 용량을 기준으로 계산하면 전체 메모리 감소는 약 41%, 가중치 저장 메모리 감소는 약 45%다. 이 요약에서는 오해를 줄이기 위해 **8.7 MB → 5.1 MB라는 절대값**을 기준으로 읽는다.

효과는 장치와 모델에 따라 다르다. ResNet-50/U50에서는 기존 레이어 파이프라인의 지연 15.0 ms를 3.4 ms로 줄였다. 반면 MobileNetV2/Zedboard에서는 AutoWS가 325.9 ms, 레이어를 순차 실행하는 방식이 8.3 ms였다. 대역폭이 부족하면 가중치를 계속 공급하는 방식이 불리해질 수 있음을 보여준다.

## 4. 우리 연구에는 어떻게 적용할 수 있는가

### 모델 전체 캐시와 부분 상주를 비교할 때 참고한다

AutoWS는 한 모델 안에서 레이어별 가중치를 나눈다. 이를 우리 다중 모델 문제로 확장하면, ‘소수 모델 전체를 캐시할 것인가’와 ‘모든 모델의 일부를 남겨둘 것인가’를 비교할 수 있다.

설명을 위해 **40개 모델이 709.375 KiB의 캐시 공간을 나눠 쓴다**고 가정해 보자. 이 모델 수는 비교용 예시이며 전체 실험 조건을 뜻하지 않는다.

| 저장 방식 | 간단한 용량 계산 | 의미 |
|---|---|---|
| 모든 모델에 동일한 부분 상주 공간 배정 | 모델당 약 17.7 KiB, 전체 가중치의 13.95% | 매번 모델 전체가 필요하다고 보면 전송량을 약 13.95% 줄일 수 있다. |
| 모든 모델의 첫 레이어 상주 | 15,360 B × 40 = 600 KiB | 모델별 가중치의 11.80%를 계속 보관한다. |
| 모델 전체를 캐시 | 동시에 5개 모델 보관 가능 | 같은 모델의 트랙을 연속 처리할수록 재사용 효과가 커진다. |

두 방식의 비교에는 **처리 순서와 모델 공유 정도**도 들어가야 한다. 예를 들어 512트랙이 40개 모델을 공유하고, 32 ms마다 모델당 한 번만 읽도록 모두 묶을 수 있다면 전송량은 약 162.72 MB/s다. 매 트랙마다 전체 모델을 다시 읽는 경우의 약 2.09 GB/s보다 12.8배 적다. 이는 도착과 마감이 그런 순서를 허용한다는 이상적인 조건의 계산이다.

따라서 이 예시는 모델 단위 캐시와 배칭을 먼저 검토할 근거는 되지만, 부분 상주가 항상 불리하다는 증명은 아니다. 모든 트랙이 서로 다른 모델을 쓰거나 요청을 충분히 묶을 수 없다면 결과가 달라진다. 두 방식을 섞은 구성도 별도로 비교할 수 있다.

### 첫 레이어가 도착하면 연산을 시작할 수 있는지 확인한다

현재 모델의 전체 가중치는 130,176 B이고, 실효 2.0 GB/s에서 순수 전송에 약 65.1 µs가 걸린다. 첫 레이어만 보면 15,360 B이므로 약 7.68 µs다.

전체 모델을 기다리는 대신 첫 레이어가 도착했을 때 계산을 시작하고, 그동안 다음 레이어를 가져오는 방식을 검토할 수 있다. 이는 첫 연산 시작 시점을 앞당길 수 있다. 다만 두 번째 레이어에 가중치의 약 75.3%가 몰려 있어, 다음 단계에서 다시 기다릴 가능성이 있다.

**연산을 일찍 시작하는 것과 총 전송량을 줄이는 것은 다르다.** 모델 전송량이 그대로라면 지속 처리에 필요한 대역폭도 그대로다. 트랙 연산 40.68 µs 동안 다음 모델 전체의 전송 65.1 µs를 숨기려면, 단순한 모델 간 겹치기 조건에서는 최소 두 트랙의 연산 시간이 필요하다. 레이어별 프리페치가 이 조건까지 해결한다고 가정해서는 안 된다.

실험에서는 첫 연산 시작 시간, 레이어별 대기 시간, 전체 완료 시간을 따로 측정해야 한다.

### 배치 길이보다 ‘전송을 끝낼 시간’에 주목한다

AutoWS의 버스트 횟수 맞추기는 여러 레이어가 DMA를 공유하는 조건에서 나온 기법이다. 우리에게 그대로 같은 수식을 적용할 수는 없다.

우리 스케줄러에서 확인할 것은 **현재 배치가 끝나기 전에 다음 모델을 가져올 수 있는가**이다. 짧은 배치에서는 전송을 숨길 시간이 부족할 수 있지만, 배치 길이가 서로 다르다는 이유만으로 항상 정지가 생기는 것은 아니다. 다음 모델이 이미 캐시에 있으면 추가 전송이 필요하지 않을 수도 있다.

따라서 모든 배치를 같은 길이로 강제하기보다는, 캐시 상태와 남은 전송 시간, 각 요청의 마감을 함께 고려하는 편이 적절하다.

### 메모리 용량을 늘렸을 때 병목이 어떻게 바뀌는지 본다

AutoWS는 온칩 메모리 예산을 늘리면서, 용량 부족으로 배치하기 어려운 구간에서 대역폭이 중요한 구간을 거쳐 연산 능력이 한계가 되는 구간으로 넘어가는 모습을 보였다.

우리도 캐시 크기를 바꾸며 가중치 전송량과 연산 대기 시간을 측정할 수 있다. 다만 ‘캐시 몇 개부터 어느 병목’인지는 모델 공유 정도와 도착 패턴에 따라 달라진다. 구간의 경계를 미리 단정하지 말고 실험으로 확인해야 한다.

## 5. 적용 범위와 원문 확인 위치

AutoWS는 단일 모델의 레이어 순서가 정해진 파이프라인을 대상으로 한다. 목표는 주어진 자원에서 처리량을 높이는 것이며, 비동기로 도착하는 여러 모델의 요청과 요청별 마감 시간을 다루지는 않는다.

우리 설계에서는 가중치를 나누어 가져오는 원리, 전송과 연산을 겹치는 버퍼 구조, 자원·대역폭을 함께 계산하는 방법을 참고할 수 있다. 계산과 DMA 클럭이 다르다면 서로 다른 클럭 사이의 안전한 데이터 전달도 필요하다. 듀얼포트 BRAM만 두면 충분한 것이 아니라, 데이터 기록 완료와 읽기 가능 시점을 맞추는 제어가 있어야 한다.

| 다시 확인할 내용 | 원문 위치 |
|---|---|
| 가중치 분할과 전송 구조 | §III~IV |
| 여러 레이어의 전송 버스트 조정 | §IV-B |
| 장치·모델별 지연과 대역폭 부족 사례 | 표 2, §V-B |
| 메모리 예산별 결과와 ResNet-18의 자원 배분 | 표 3, 그림 6~7 |

후속 작업은 공개 코드에서 자원·대역폭 모델링 방식을 확인하고, 레이어별 프리페치를 우리 메모리 경로의 비교 옵션으로 구현할지 판단하는 것이다.
