# 문서 작성 규칙

## 1. 기본 원칙

- 쉬운 말로 짧게 쓴다.
- 한 문장에는 한 내용만 넣는다.
- 결론을 먼저 쓰고 근거를 뒤에 쓴다.
- 같은 설명을 여러 문서에 복사하지 않는다. 기준 문서를 링크한다.
- 전문 용어는 현장에서 쓰는 한국어 또는 영어를 쓴다. 억지 번역은 쓰지 않는다.
- 이 프로젝트 용어는 [01_OVERVIEW.md §3](design_references/01_OVERVIEW.md#3-용어)의 표기만 쓴다. 영문 용어는 영문 그대로 쓰고, 같은 개념을 한글과 영문으로 섞어 쓰지 않는다. 문서·코드·그림 모두 같다.

예: `dataflow`, `cache`, `prefetch`, `scheduler`, `runtime`, `deadline`, `bitstream`, `testbench`, `membrane potential`, `offset`, `batch`.

## 2. 문서 구조

새 문서는 아래 순서를 기본으로 한다. 필요 없는 절은 뺀다.

1. 제목
2. 요약
3. 조건 또는 설계
4. 결과
5. 검증과 한계
6. 다음 작업
7. 관련 문서

보고서는 환경, 방법, 결과, 결론을 구분한다. 설계 문서는 목표, 조건, 선택지, 판단 기준을 구분한다.

## 3. 수치와 주장

- 목표, 가정, 계산, simulation, 구현 결과, 보드 실측을 구분한다.
- 표에는 단위를 쓴다.
- 용량은 B와 KiB를 구분한다. bandwidth는 MB/s와 GB/s를 쓴다.
- `p99 < 32 ms`만으로 deadline 보장을 주장하지 않는다.
- 검증하지 않은 내용은 `제안`, `가정`, `미정`으로 표시한다.
- 실패와 한계도 결과와 함께 적는다.

## 4. 표와 목록

- 세 항목 이상을 비교할 때 표를 쓴다.
- 긴 작업 이력은 표로 줄인다.
- 표 한 칸에 여러 문단을 넣지 않는다.
- 목록 단계는 가능하면 두 단계까지만 쓴다.
- 명령과 식은 code block에 둔다.

## 5. 링크와 수정

- 상대경로 링크를 쓴다.
- 파일명을 추측하지 말고 실제 경로를 확인한다.
- 수치를 바꾸면 연결된 표, 식, 요약도 확인한다.
- 자동 생성 파일은 직접 고치지 않는다. 생성 코드나 원자료를 고친다.
- 과거 보고서는 당시 결과를 남긴다. 최신 기준과 다르면 차이를 쓰고 최신 문서를 링크한다.
