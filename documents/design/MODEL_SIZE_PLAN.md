# 모델 크기 검증과 시나리오 설계 계획 — P3.6~P3.8

작성일: 2026-10-10 | 개정: r7 (2026-10-12, §5.10 점수 방식 개선, §5.11 문헌 기반 스케줄러 후보 비교, §5.12 최종 비교 대상·구현 선택(SlackBatch). r4 2026-10-11, §5 P3.8 마무리: XL 시나리오별 최대 트랙, 합성 목표 1,024트랙, 3축 24조합 측정. 이전 r3: 결과 종합은 [P3.6~3.8 리포트](<../reports/P3.6~3.8 Research Report.md>)) | 관련 작업: [TASKS.md](TASKS.md) P3.6~P3.8, [SIM_PLAN.md](SIM_PLAN.md)

## 0. 왜 하는가

- P3.5 시뮬레이션에서, 실측 조건(DDR3 3.015 GB/s, 512트랙)으로는 스케줄러·캐시가 없어도 마감을 지켰다([SIM_PLAN.md](SIM_PLAN.md) §6).
- 차이를 보이려고 조건을 키우면 "작은 모델로 풀 수 있는 문제를 큰 모델로 바꾼 것"이 될 수 있다.
- 이 위험은 이미 미결 항목으로 적혀 있었다([P2.1~2.2 리포트](<../reports/P2.1~2.2 Research Report.md>) §7: "`40→384→256→64→2`가 선행 `40→128→32→2`보다 정확도 이득이 있는지 측정해 근거로 삼아야 한다").

그래서 두 단계로 진행한다.

1. **모델 크기가 정말 필요한지 정확도로 확인한다.** 결과로 확정한 "효율적인 모델"을 이후 설계의 기준으로 삼는다.
2. **확정 모델로, 현실적인 요청 시나리오를 모두 마감 위반 0으로 통과하는 캐시·스케줄러·연산 방식을 찾는다.**

목표(40모델·512트랙·32 ms)와 모델 수는 바꾸지 않는다. 1단계 결과로 40모델이 모두 온칩에 들어가면, "이 응용에는 다중 모델 캐시가 필요 없다"를 그대로 결론으로 기록한다.

- 허용 폭을 0.01로 넓혀 동등성으로 판정해도 결론은 같다. L INT6은 신뢰구간 하한이 −0.006이라 통과하고, M은 −0.013이라 미달이다.

- 가중치 4 bit는 양자화만으로는 모든 구조에서 크게 떨어졌다. 재학습을 포함한 양자화(QAT)는 하지 않았다.
- 한계: 장비마다 학습 시드가 하나다. 다만 시드 잡음은 방향이 무작위이므로, 34/40처럼 한쪽으로 몰린 결과를 설명하기 어렵다. M의 29/40은 상대적으로 덜 확실하다.
- **효율 모델 후보: L INT6** (모델당 97,632 B + β·vth). 확정 전에 두 가지가 남았다.
  - 정수 파이프라인 확인: 스케일이 INT8의 약 1/4이라 vth 정밀도 설계가 필요하다.
  - 하드웨어 정리: 32레인 × 6 bit = 192 bit word, 엔트리 21.5 + β·vth 0.5 = 22 타일로 7벌 가능(계산값, INT8은 5벌).

### 1.5 위쪽 확인 — XL (2026-10-10)

**왜:** §1.4는 L보다 작은 구조만 확인했다. 그래서 "L은 줄이면 안 된다"까지만 말할 수 있었다. L이 포화 지점인지 보려고 은닉층을 2배로 키운 **XL `40→768→512→128→2`**(가중치 489,728개)를 같은 조건으로 학습했다.
- 학습 조건: `train_all.py --layers 40,768,512,128,2 --tag XL`. 지도학습, 배치 512, 60에포크, 시드 42로 L과 같다.
- 실행: RTX 3090 Ti 독점, 6개 동시, 52분.
- 실측 에너지: GPU 0.149 kWh(평균 173 W) + CPU 패키지 0.095 kWh(평균 115 W) = 0.244 kWh. 보드·팬 등은 측정하지 않았다.
- 평가: `size_sweep.py`로 했고, 전체 표는 [size_sweep/summary.md](../../software/analysis_develop/size_sweep/summary.md)다.

|---|---:|---:|---:|---|

**해석**

1. **필요한 모델 크기는 장비 종류에 따라 다르다.**
   - 밸브를 뺀 33대는 M(5만)에서 이미 포화한다. M, L, XL의 차이가 ±0.006 이내이고 유의하지 않다.
   - 밸브 7대는 크기를 키울수록 계속 좋아진다(0.87 → 0.90 → 0.94). XL에서도 포화하지 않았을 수 있다.
   - M의 전체 결손(−0.0067)은 대부분 밸브 몫이다(−0.033 × 7/40 = −0.0058).
2. **모델을 모두 같은 크기로 두는 것은 비효율적이다.** 밸브는 XL, 나머지는 M으로 섞으면 다음과 같다(계산값).
   - 40모델 가중치 합계: 33 × 51 KB + 7 × 490 KB ≈ 5.1 MB로, 40 × L(5.2 MB)과 거의 같다.
   - AUC 평균: L보다 약 +0.005 높다.
   - 트랙이 모델에 고르게 배정되면 요청당 평균 연산량도 L과 비슷하다(약 0.98배).
   - 대신 모델 하나의 크기가 약 10배까지 차이 난다.
3. **하드웨어 연구와의 연결:** 모델 크기가 서로 다르면 모델마다 전송 비용과 연산 시간이 달라진다. 같은 크기에서는 점수 스케줄러가 묶음 크기만 보게 되어 그룹핑과 같아졌다(§4.6). 크기가 다르면 무엇을 상주시키고 무엇을 흘려보낼지, 어떤 모델을 먼저 처리할지가 비용에 따라 달라진다. 정확도에서 나온 조건이라 억지로 만든 조건이 아니다.
4. **한계:**
   - 장비마다 시드가 하나다. 밸브는 7/7이 같은 방향이고 크기에 따라 단조로 변해 시드 잡음으로 보기 어렵다.
   - ToyCar_id05의 XL 하락(−0.126)은 장비 하나의 결과라 원인을 확인하지 않았다(과적합 가능).
   - 학습 설정(에포크·학습률)은 L 기준 그대로다.

## 2. 2단계 — 시나리오와 구조 결정 (P3.7~P3.8)

### 2.1 시나리오 (모두 통과해야 함)

| 이름 | 상황 | 시뮬레이터 설정 |
|---|---|---|
| U 균등 | 트랙이 40모델에 고르게, 트랙마다 다른 시각에 도착 | 균등 배정, 위상 무작위 (현재) |
| K 편중 | 몇 개 모델에 트랙이 몰림 (같은 종류 장비가 많은 공장) | 모델 k의 비율 ∝ 1/(k+1), 상위 5모델 53 % |
| S 동시 | 멀티채널 오디오 인터페이스가 모든 채널을 같은 클럭으로 샘플 → 512개 요청이 동시에 도착 | 위상 모두 같음 + PCIe 지연 표본 |
| I 띄엄띄엄 | 장비가 켜졌다 꺼지거나 소리가 있을 때만 요청 → 트랙마다 요청이 간헐적 | 주기마다 요청 확률 p(가정, 예: 0.25) |
| S+K | 동시 도착 + 편중 | 위 두 설정 결합 |

### 2.2 하드웨어 조건과 설계 변수

- **하드웨어 조건:** 실측 보드(DDR3 3.015 GB/s). 1단계 모델로도 병목이 없다면, 대역폭이 낮은 구성(16 bit DDR3, 1.5 GB/s)을 근거와 함께 추가할지 그때 정한다.
- **설계 변수:** 저장 정책(캐시 벌 수, 부분 상주), 스케줄러, 연산 방식.
- **판정:** 모든 시나리오에서 마감 위반 0인 조합 중 BRAM이 가장 적은 것. 같으면 DDR3 전송량이 적은 것.
- **비교 기준 구조:** "스케줄러·캐시 없음" = 도착 순서 처리 + 이중 버퍼. 이 구조가 어느 시나리오에서 1 % 이상 위반하는지, 무엇을 추가하면 0이 되는지를 보인다.

## 3. 설계 공간 탐색 — 최대 트랙 수 기준 (2026-10-10 추가)

1단계 결과로 모델은 **L INT8**로 고정한다. 하드웨어 구성(트랙·레인·온칩 배분)은 마감을 지키는 범위에서 바꿀 수 있지만, 복잡해진 만큼 효용(예: 트랙 증가)이 있어야 한다. 연구의 세 축은 **스케줄러, 메모리 접근(무엇을 어디에 두고 어떻게 가져오나), 연산 방식(읽어서 계산하는 순서)**이다.

### 3.1 지표

설계마다 **시나리오 U·K·S·I·SK × 시드 2개에서 모두 마감 위반 0인 최대 트랙 수**를 찾는다. 32트랙 단위 이분 탐색이며, 위반이 하나라도 나면 그 실행을 바로 멈춘다(`dse.py`).

이 지표를 쓰면 세 축의 선택이 모두 같은 단위(트랙 수 = 효용)로 비교된다. BRAM 배치가 불가능하면 그 트랙 수는 실패로 본다.

### 3.2 설계 변수

| 축 | 후보 |
|---|---|
| 레인 | 32, 64, 128 (word 256·512·1024 bit) |
| 막전위 위치 | 온칩(트랙 수만큼 BRAM 사용) / DDR3(요청마다 2,824 B 왕복, 준비 버퍼만 BRAM) |
| 메모리 접근(저장) | A 전체 캐시(남은 예산 최대 벌, 2벌 미만 불가), B 40모델 L1 상주, C 혼합, **D 스트림(가중치 보관 없음, 매 묶음 전체 전송)** |
| 스케줄러 | FCFS, 그룹핑, 점수 |
| 연산 방식 | 한 번에(트랙 순서, 모델 전체 버퍼 필요) / 한 줄씩(그룹 순서, 슬라이스 버퍼 + 막전위 DDR3면 묶음 막전위 버퍼, 묶음 ≤ 64) |

### 3.3 계산으로 본 예상

- **32레인:** 연산 한계(715트랙)가 묶지 않을 때의 DDR3 한계(733)보다 먼저 와서 차이가 작다.
- **64레인 + 막전위 온칩:** 묶지 않을 때 DDR3 한계 733, 막전위 BRAM 한계 약 830~970트랙. BRAM을 막전위와 가중치가 나눠 쓰므로 세 축이 모두 최대 트랙 수를 바꿀 것으로 예상한다.
- **막전위 DDR3:** 연산 한계(64레인 1,430)까지 갈 수 있으나, 막전위 왕복 DMA가 추가된다.

세 축의 효과 (64레인 기준):

- **스케줄러:** 묶지 않는 FCFS는 DDR3 한계(묶지 않을 때 약 733트랙) 근처에서 멈춘다. 온칩 D·한 줄씩은 672 대 928(+38 %), DDR3 A·한 줄씩은 864 대 1,408(+63 %)이다. 128레인 DDR3에서는 768 대 2,528(3.3배)이다. 그룹핑과 점수(초안)는 대부분 같고, 점수가 몇 경우 조금 낮다.
- **메모리 접근:** 막전위가 온칩이면 BRAM을 막전위와 가중치가 나눠 쓴다. 묶음 스케줄러를 쓰면 가중치 캐시가 필요 없으므로, 캐시를 두지 않는 D 스트림이 BRAM을 막전위에 몰아줘 가장 많은 트랙을 받는다. 그룹핑·한 줄씩 기준 D 928 > A 800(엔트리 2벌) > C 736 > B 480(L1 상주 156.5 타일)이다. 막전위를 DDR3로 옮기면 928에서 1,408로 늘지만, 요청마다 2,824 B를 DMA로 왕복한다. 묶지 않는 FCFS에서는 캐시가 묶음을 일부 대신한다(DDR3 막전위: D 672 → C 896).
- **연산 방식:** 한 줄씩이 한 번에보다 같거나 많다. 차이가 큰 경우는 모델 전체 버퍼가 필요한 한 번에 × 캐시 없음이다. 예: 온칩 D·FCFS 672 대 480, DDR3 D·그룹핑 1,408 대 1,312, 128레인 DDR3 D 2,496 대 2,368. BRAM이 한계인 구성에서도 한 줄씩이 버퍼가 작아 928 대 896으로 많다.

해석: 묶음(스케줄러)과 캐시는 같은 재사용을 두고 경쟁한다. 묶음을 쓰면 BRAM은 캐시보다 막전위(트랙)에 쓰는 편이 낫고, 그때는 한 줄씩(스트리밍) 연산이 버퍼를 가장 적게 쓴다. 선행 A16의 "막전위와 가중치의 공간 경쟁"이 여기서 트랙 수로 나타난다.

한계 (아직 반영하지 않은 것):

- 트랙이 많아지면 초당 요청이 늘어난다(928트랙이면 2.9만 건/s). 호스트 입력(H2C)을 묶어 보내야 하는데, 지연 표본은 16 kHz 실측을 그대로 썼다.
- 막전위 DDR3 왕복은 대역폭만 넣고 지연은 숨긴다고 가정했다.
- 64·128레인의 LUT·타이밍과 PLIF 갱신 처리량은 확인하지 않았다.
- 점수 스케줄러는 초안이고, 시드는 2개다.

## 4. 최대 트랙 실험 (2026-10-10 계획)

§3의 탐색은 512트랙 기준 가정을 그대로 썼다. 트랙이 900~2,500개가 되면 그 가정 일부가 틀려진다. 이 절에서는 그 가정을 고친 뒤 최대 트랙 수를 다시 찾는다. 모델은 L INT8, 보드는 XC7A200T와 DDR3 2칩으로 고정하고, 마감은 입력 생성부터 결과가 호스트에 돌아올 때까지 32 ms다.

### 4.1 질문

1. 모든 시나리오에서 마감 위반 0인 **최대 트랙 수 N\***는 얼마이고, 어떤 설계(레인 × 막전위 위치 × 저장 × 스케줄러 × 연산 방식)가 그 값을 내는가.
2. N\*를 막는 것은 무엇인가. 후보는 연산, BRAM, DDR3, PCIe다.
3. 세 축은 각각 N\*를 얼마나 바꾸는가. 한 축씩 차례로 골라도 N\*에 닿는가, 아니면 함께 골라야 하는가.

### 4.2 §3에서 바꾸는 가정 (트랙이 많아지면 틀려지는 것)

| 항목 | §3 | 이번 | 근거 |
|---|---|---|---|
| 호스트 입출력 | 요청마다 64 B DMA 1회. 지연은 62.5 µs 주기 실측 표본 | **호스트가 W_h = 1 ms마다 그사이 생긴 입력을 모아 H2C 1회**를 보낸다. 결과도 1 ms마다 C2H 1회로 읽는다. 전송 지연 = 1 ms 주기 64 B 실측 표본(p50 98 µs) + (묶음 크기 − 64 B) ÷ 758 MB/s. 입출력 대기는 각각 최대 W_h | 64 B DMA 1회가 27 µs라 한 채널은 초당 약 3.7만 건이 한계다. 1,184트랙(3.7만 건/s) 이상은 하나씩 보낼 수 없다(P3.3 §4.3). 이 크기 항으로 계산한 24 KiB 지연은 130 µs이고, 32 ms 주기 실측 p50은 134 µs다 |
| 막전위 DDR3 비용 | 왕복 2,824 B를 읽기 대역폭으로 계산 | 읽기 1,412 B ÷ 3.015 GB/s + 쓰기 1,412 B ÷ 2.768 GB/s | P3.1 rbc 순차 쓰기 실측(1 KiB 버스트) |
| 한 줄씩의 묶음 버퍼 | 막전위가 온칩이면 묶음 크기 제한 없음, 층간 버퍼 없음 | 묶음 ≤ 64트랙. 입력·층간 스파이크 버퍼 64 × 128 B(입력 40 + 층1 48 + 층2 32 + 층3 8) = 2 타일 | 그룹 순서로 돌면 층 2를 계산하는 동안 묶음 전체 트랙의 층 1 스파이크를 들고 있어야 한다 |
| 요청 큐·트랙 메타 | 계산하지 않음 | 분산 RAM(구성 D와 같음). BRAM은 쓰지 않고, LUT 추정(트랙당 약 11개)만 보고한다 | P3.2 fit: 512 × 512 bit 큐 = LUTRAM 5,472개 |
| 레인 | 32·64·128 | **256 추가**(상한 확인용, 자원·타이밍 미확인) | 출력 고정 방식에서는 층 3(64뉴런)·층 2(256뉴런)가 레인을 다 쓰지 못해 요청당 word가 721 아래로 거의 줄지 않는다 |
| 스케줄러 | FCFS·그룹핑·점수 | **EDF 추가**(4종 전수) | — |
| 시나리오 | U·K·S·I·SK | **R 추가**: 무작위 혼잡도(주기마다 활성 비율을 0.25~1에서 무작위로 정하고, 트랙마다 그 확률로 요청). 위상과 모델 배정도 무작위 | 사용자 정의: "무작위 순서로, 무작위 혼잡도로, 무작위한 시간에 요청이 들어온다" |
| 시드·탐색 간격 | 2개, 32트랙 | 3개, 16트랙. 상위 설계는 20개로 다시 확인 | — |

시뮬레이터는 `configure(rev=2)`와 `make_workload(host=1000)`으로 이 가정을 켠다. 기본값은 §3과 같아 이전 결과를 다시 만들 수 있다.

### 4.3 계산으로 본 상한 (시뮬레이션 전)

| 레인 | 요청당 연산 | 연산 한계 | 막전위 온칩 BRAM 한계 (D 스트림 · 한 줄씩) | 묶지 않을 때 DDR3 한계 |
|---:|---:|---:|---:|---:|
| 32 | 44.75 µs | 715 | 약 960 | 729 |
| 64 | 22.37 µs | 1,430 | 약 944 | 729 |
| 128 | 12.60 µs | 2,540 | 약 896 (슬라이스 버퍼 28.5 타일) | 729 |
| 256 | 7.93 µs | 4,034 | 약 816 (슬라이스 버퍼 57 타일) | 729 |

묶지 않을 때 DDR3 한계 = 32 ms ÷ (0.244 µs + 131,588 B ÷ 3.015 GB/s)다. 요청마다 모델 전체를 가져오면 레인과 무관하게 약 729트랙에서 멈춘다.

예상:

- **막전위 온칩:** BRAM이 한계이며 64레인 근처가 최대(약 940)다. 이 영역에서는 막전위와 가중치 버퍼가 BRAM을 나눠 쓰므로 세 축이 모두 N\*를 바꾼다.
- **막전위 DDR3:** 연산이 한계라 N\*가 레인에 비례해 커진다. 묶음 스케줄러가 없으면 729에서 멈추므로, 레인을 늘리는 효용은 스케줄러가 있어야 생긴다. 호스트 입출력 대기(최대 약 2 × W_h)가 마감 여유를 줄이므로 연산 한계보다 몇 % 낮을 것이다.

### 4.4 절차

1. **전수 탐색.** 레인 4 × 막전위 2 × 저장 4 × 스케줄러 4 × 연산 2 = 256 설계를 탐색한다. 설계마다 시나리오 6 × 시드 3에서 위반이 0인 최대 N을 16트랙 단위 이분 탐색으로 찾는다(`dse.py --rev 2`).
2. **정밀 확인.** (레인, 막전위)마다 가장 좋은 설계를 N\*에서 시나리오 6 × 시드 20으로 다시 돌린다. 위반 0인지, 최소 여유(32 ms − 최대 응답)가 얼마인지 기록하고, N\* + 16에서는 실패하는지도 확인한다. (실행 중 보완: N\*가 시드 20에서 실패하면 통과할 때까지 16씩 내려 찾는다. 막전위 DDR3는 S의 최악 위상 해석 상한도 계산한다, §4.6)
3. **축별 기여.** 최고 설계에서 한 축만 바꿨을 때의 N\* 변화를 본다. 또 기준안(A 전체 캐시 · FCFS · 한 번에)에서 출발해 한 번에 한 축씩 최적으로 바꾸는 방식(6가지 순서)이 전수 최적에 닿는지 비교한다. 1단계 표만으로 계산하므로 추가 실행이 없다.
4. **민감도.** 최고 설계들에 아래 조건을 바꿔 적용한다.
   - W_h: 0.25, 0.5, 2 ms
   - DDR3: 2.0 GB/s (제안서 가정값)
   - PCIe 꼬리 지연: 관측 최대 795 µs가 모든 전송에서 나는 경우

### 4.5 판정과 보고

- **N\* 정의:** 1단계(시나리오 6 × 시드 3)와 2단계(시드 20)를 모두 위반 0으로 통과한 가장 큰 16의 배수. 막전위 DDR3는 이 값과 S 최악 위상 해석 상한 중 작은 값을 **보장값**으로 쓴다(§4.6).
- **보고 1 — 최대 트랙 구성:** (레인, 막전위)별 N\*, 한계 요인, BRAM, 연산 가동률, 큐 LUT 추정.
- **보고 2 — 연구용 구성:** 세 축이 모두 N\*를 바꾸는 구성을 따로 보고한다. 최대 트랙 구성에서는 한 축만 남을 수 있기 때문이다.
- **해석 범위:** 이 결과는 시뮬레이션 값이다. 레인 128·256의 LUT·타이밍, PLIF 갱신 처리량, 막전위 DDR3 지연이 숨는다는 가정(우선순위 인터리빙)은 확인하지 않았다.

1. **1단계 N\*가 시드 20에서 실패했다.** 막전위 DDR3 설계의 1단계 N\*는 시드 20에서 S·SK의 일부 시드가 0.15~0.55 ms 넘쳤다. 그래서 통과할 때까지 16씩 내려 찾았다.
2. **해석 상한을 추가했다.** 시드는 호스트 주기의 위상을 무작위로 뽑을 뿐이라 최악 위상을 보장하지 않는다. S(동시 도착)는 응답이 거의 결정적이다. 그래서 다음 식을 만족하는 가장 큰 N을 해석 상한으로 계산했다.
   - 식: 입력 대기 W_h + H2C 실측 최대(크기 항 포함) + 첫 모델 전송 + N × 요청당 연산 + 결과 대기 W_h + C2H 실측 최대 ≤ 32 ms
   - **보장값** = min(시드 20 통과 N, 해석 상한)

**최대 트랙 수**

| 레인 | 막전위 온칩: N\* | 한계 | 여유 | 막전위 DDR3: 시드 20 통과 | 해석 상한 = **보장값** | 한계 | 여유 |
|---:|---:|---|---:|---:|---:|---|---:|
| 32 | 656 | 연산 | 0.59 ms | 656 | 656 | 연산 | 0.59 ms |
| **64** | **944** (D 스트림 · 그룹핑 · 한 줄씩) | BRAM (960은 배치 불가) | **8.60 ms** | 1,328 | **1,312** | 연산 | 0.12 ms |
| 128 | 896 | BRAM | 18.14 ms | 2,368 | **2,336** | 연산 | 0.12 ms |
| 256 | 832 | BRAM | 21.60 ms | 3,744 | **3,696** | 연산 | 0.12 ms |

여유 = 32 ms − 시드 20 전체의 최대 응답(생성 → 결과가 호스트에 도착). 32레인은 막전위 위치와 관계없이 연산이 한계이므로 두 구성이 같다.

1. **막전위 온칩의 최대는 64레인 944다(현재 목표 512의 1.84배).**
   - BRAM이 한계이며, 960은 배치할 수 없다.
   - 레인을 늘리면 슬라이스 버퍼가 넓어져(14.5 → 28.5 → 57 타일) 막전위 자리가 줄고 N\*도 896, 832로 줄어든다.
   - 최대 응답은 23.4 ms이고, 민감도 조건 5가지에서도 모두 944 그대로다. 마감 여유가 커서 입출력·DDR3 조건이 바뀌어도 BRAM이 먼저 한계에 닿는다.
2. **막전위 DDR3에서는 N\*가 레인 수에 비례하며, 보장값은 연산 한계의 92 %다.**
   - 보장값: 1,312 / 2,336 / 3,696.
   - 남는 8 %는 호스트 입출력 대기(최대 2 × W_h)와 전송 시간이다.
   - 여유가 0.12 ms라 입출력 조건에 민감하다(1단계 N\* 기준, [dse2_sens.md](../../software/sim_result/dse2_sens.md)):

     | 조건 | N\* 변화 |
     |---|---:|
     | W_h 0.25 ms | +1.2~2.4 % |
     | W_h 2 ms | −2.4~3.8 % |
     | PCIe 꼬리 +700 µs | −4.8~5.9 % |
     | DDR3 2.0 GB/s | 0~−1.2 % (묶음으로 가중치 전송이 줄어 거의 영향 없음) |

3. **§3(rev 1)과의 차이**
   - 64레인 온칩 928 → 944: 탐색 간격을 32에서 16으로 줄인 결과다. 스파이크 버퍼 2 타일을 더해도 BRAM 한계 안에 든다.
   - 64레인 DDR3 1,408 → 1,312: 호스트 묶음 입출력 대기를 반영한 결과다.

**세 축의 효과** (3단계)

| 구성 (최고 설계 N\*, 1단계) | 스케줄러 축 범위 | 저장 축 범위 | 연산 축 범위 |
|---|---:|---:|---:|
| 64레인 온칩 (944) | 288 (FCFS·EDF 656 → 그룹핑·점수 944) | **448** (B 496, C 736, A 816, D 944) | 32 (한 번에 912) |
| 128레인 온칩 (896) | 240 | 448 | 32 |
| 64레인 DDR3 (1,360) | **704** | 0 | 80 |
| 256레인 DDR3 (3,840) | **3,040** | 160 | 16 |

범위 = 최고 설계에서 그 축만 바꿨을 때 최대 트랙 수의 최대 − 최소.

- **EDF는 256개 설계 모두에서 FCFS와 같다.** 둘 다 기준 요청 뒤로 같은 모델이 이어지는 만큼만 묶으므로, 트랙이 많으면 묶음이 거의 1이다.
- **점수(초안)는 그룹핑과 같거나 낮다.** 차이는 최대 −848(256레인 DDR3 D·한 번에)이다. 묶음 상한 K = 16 때문으로 보이며 확인하지 않았다.
- **막전위 DDR3에서는 스케줄러 하나가 N\*를 정한다.** 묶지 않으면(FCFS·EDF) 레인과 관계없이 656~880에서 멈춘다. 729는 요청마다 모델 전체를 가져올 때의 한계이고, 캐시 적중이 있으면 조금 넘는다. 저장·연산 방식의 차이는 0~160트랙이다.
- **막전위 온칩에서는 세 축이 모두 N\*를 바꾸며, 한 축씩 고르면 최적에 닿지 않는다.** 기준안(A · FCFS · 한 번에)에서 한 번에 한 축씩 최적으로 바꾸는 6가지 순서를 비교했다.
  - 64레인: 2가지 순서만 944에 닿는다. 나머지는 736·816·912에서 멈춘다.
  - 128·256레인: 모든 순서가 기준안 656에서 멈춘다.
    - 그룹핑만 바꾸면 A의 엔트리 2벌이 BRAM을 차지한 채라 변화가 없다(656).
    - 저장만 D로 바꾸면 FCFS가 요청마다 모델 전체를 가져와 오히려 줄어든다(544).
    - 둘을 함께 바꿔야 896이 된다.

  묶음 스케줄러가 있어야 캐시를 버릴 수 있고, 캐시를 버려야 BRAM이 막전위(트랙)로 간다. 이 상호작용이 막전위 온칩 구성에서 세 축을 함께 설계해야 하는 근거다.

**두 선택지**

| | 막전위 온칩 · 64레인 | 막전위 DDR3 · 128레인 (256레인) |
|---|---|---|
| 최대 트랙 (보장) | 944 | 2,336 (3,696) |
| 한계 | BRAM | 연산 |
| 마감 여유 | 8.6 ms | 0.12 ms |
| 입출력·PCIe 꼬리 민감도 | 없음 | W_h 2 ms −3 %대, PCIe 꼬리 −5 %대 |
| 세 축 연구 | 셋 모두 N\*를 바꾸고, 함께 골라야 최적 | 스케줄러만 남음 |
| 요청 큐 LUT 추정 | 약 1.0만 | 약 2.5만 (4.0만) |
| 확인하지 않은 위험 | 64레인 타이밍·PLIF 처리량 | 128·256레인 LUT·타이밍, 막전위 DDR3 지연이 숨는다는 가정 |

**판단:**
- 세 축 연구와 트랙 수를 함께 얻는 구성은 **64레인 막전위 온칩(944, D 스트림 · 그룹핑 · 한 줄씩)**이다.
- 막전위 DDR3 구성은 같은 보드의 트랙 상한(연산 한계)을 보여 주는 참고값으로 기록한다.
- 목표 트랙 수를 512에서 바꿀지는 지도교수 결정 사항이다.

**한계:**
- 모든 수치는 시뮬레이션 값이다.
- 호스트 주기는 1 ms 주기 실측 지연을 0.25~2 ms에 그대로 썼다.
- 점수 스케줄러는 초안 그대로다.
- 막전위 온칩 결과는 BRAM 타일 계산식(P3.4)에 달려 있다. 944트랙 구성(막전위 325.5 + 버퍼 17 = 342.5 / 344.5 타일)은 배치·배선으로 확인하지 않았다.

### 4.7 모델을 키우면 — XL 크기로 같은 실험 (2026-10-10, 시뮬레이션)

**질문:** 모델이 커지면 다시 "스케줄러만으로 위반이 갈리는" 형태가 되는가.

**방법**
- 시뮬레이터는 가중치 값을 쓰지 않고 크기(바이트·뉴런·사이클)만 쓴다. 그래서 학습 없이 구조만 바꿔 §4와 같은 1~4단계를 다시 실행했다(더미 가중치와 같다).
- XL = `40→768→512→128→2`(은닉층 2배). 가중치는 489,728 B(L의 3.8배), 뉴런은 1,410개(2배), 모델 하나는 492,548 B다.
- XL의 정확도는 측정하지 않았다.
- 실행: `dse.py --rev 2 --arch 40,768,512,128,2 --tag xl`
- 결과 파일: [dse2_xl_capacity.md](../../software/sim_result/dse2_xl_capacity.md), [dse2_xl_verify.md](../../software/sim_result/dse2_xl_verify.md), [dse2_xl_axes.md](../../software/sim_result/dse2_xl_axes.md), [dse2_xl_sens.md](../../software/sim_result/dse2_xl_sens.md)
- 그림: `figures/fig7~13_dse2_xl_*.png`
- 시뮬레이터 변경: `configure(arch=…)`로 구조를 받도록 바꿨다. 자체 시험 14개 PASS, L 결과(944)가 바뀌지 않음을 확인했다.

**최대 트랙 수 (보장값)**

| | L | XL |
|---|---:|---:|
| 연산 한계 (64 / 128 / 256레인) | 1,430 / 2,540 / 4,034 | 380 / 760 / 1,341 |
| 묶지 않을 때 DDR3 한계 | 729 | **195** |
| 막전위 온칩 최대 | 944 (64레인, BRAM) | **448** (128레인, BRAM, 여유 9.5 ms) |
| 막전위 DDR3 (64 / 128 / 256레인) | 1,312 / 2,336 / 3,696 | 336 / **688** / 1,120 |
| 목표 512를 넘는 구성 | 32레인을 빼고 모두 | **막전위 DDR3 + 128레인 이상만** |

**세 축의 효과** (3단계, 1단계 값)

| 구성 | 스케줄러 축 | 저장 축 | 연산 축 |
|---|---|---|---|
| XL 128레인 온칩 (448) | FCFS 176 → 그룹핑 448 | A 160, B·C 배치 불가, D 448 | 한 번에 320 → 한 줄씩 448 |
| XL 128레인 DDR3 (720) | FCFS 176 → 그룹핑 720 | A 720, B·C 배치 불가, D 560 (한 번에) · 688 (한 줄씩) | A는 차이 없음, D는 560 → 688 |
| (참고) L 64레인 DDR3 (1,360) | FCFS 656 → 그룹핑 1,360 | 차이 없음 | 1,280 → 1,360 |

**해석**

1. **스케줄러는 여전히 첫 관문이다.** 묶지 않으면 모든 설계가 약 176트랙(묶지 않을 때 DDR3 한계 195)에서 멈춘다. XL에서는 그룹핑이 있어야만 목표 512를 넘는다.
2. **다만 L과 달리 스케줄러만 남지는 않는다.** XL은 요청당 전송 시간이 연산의 약 3.9배(128레인: 163 µs 대 42 µs)라, 막전위를 DDR3에 두어도 다음 차이가 남는다.
   - 저장: A 2벌 캐시 720, D 스트림 560~688. B·C는 BRAM에 들어가지 않는다.
   - 연산 방식: D는 한 번에 560, 한 줄씩 688.

   같은 DDR3 영역에서 L은 저장 차이가 0이었다.
3. **막전위 온칩에서는 상호작용이 L보다 강하다.** 128레인에서 기준안(A · FCFS · 한 번에) 160에서 한 축씩 바꾸면 6가지 순서 모두 160에 멈춘다. 셋을 함께 바꿔야(D · 그룹핑 · 한 줄씩) 448(2.8배)이 된다.
4. **XL은 온칩에서 목표 512를 넘지 못한다.** 막전위 2.8 KB/트랙 때문에 BRAM 한계가 약 450이다. 512 이상에는 막전위 DDR3와 128레인이 필요하다.

**결론**
- 모델을 키워도 "스케줄러만 남는" 형태로 돌아가지는 않는다.
- 스케줄러가 먼저 필요하고, 그다음 저장·연산 방식이 4~30 % 차이를 낸다. 목표 512에서는 세 축이 모두 통과 여부에 관여한다(FCFS 불가, B·C 배치 불가, 한 번에·한 줄씩의 여유 차이).
- 다만 XL을 쓸 근거는 정확도(소음·간섭 조건)이며 아직 측정하지 않았다. 이 결과는 "XL이 필요해지면 하드웨어 설계가 이렇게 바뀐다"는 조건부 결과다.

## 5. P3.8 마무리 — XL 합성 목표와 3축 24조합 (2026-10-11, 시뮬레이션)

### 5.1 질문

확정안(P3.6~3.8 리포트 §4: XL INT8, 256레인, 막전위 DDR3)으로 다음 세 가지를 정한다.

1. 시나리오마다 마감 위반 0인 최대 트랙 수, 즉 합성할 수 있는 트랙 수는 얼마인가.
2. 이를 바탕으로 하드웨어를 몇 트랙으로 합성할 것인가(목표 하나).
3. 그 목표에서 3축 조합 24가지(저장 3 × 스케줄러 4 × 연산 2)의 마감 위반율, 평균 처리 시간, 오프칩 접근 횟수, 사이클은 각각 얼마인가.

### 5.2 고정 조건

| 항목 | 값 | 근거 |
|---|---|---|
| 모델 | XL `40→768→512→128→2` INT8. 모델 1개 = 가중치 489,728 B + β·vth 2,820 B = **492,548 B** | §1.5, 리포트 §2 |
| 연산 | 256레인, word 256 B. 요청당 2,169 word × 1.1 = **2,385.9사이클 = 23.859 µs** @ 100 MHz → 연산 한계 `32 ms ÷ 23.859 µs = 1,341`트랙 | 제어 오버헤드 10 %는 가정 |
| 모델 전송 | `0.244 µs + 492,548 B ÷ 3.015 GB/s = 163.6 µs` (연산의 6.9배) | P3.1 실측 |
| 막전위 | DDR3. 요청마다 읽기 2,820 B(3.015 GB/s) + 쓰기 2,820 B(2.768 GB/s) = 1.95 µs | P3.1 실측, §4.2 |
| BRAM 예산 | 344.5 타일 = 365 − XDMA 20.5 | P3.2 실측 |
| 입출력 · 마감 | 호스트 1 ms 묶음 H2C·C2H, 마감 = 생성 → 결과가 호스트에 도착 32 ms | §4.2 |
| 시나리오 | U 균등, K 편중, S 동시 도착, I 띄엄띄엄(0.25), SK, R 무작위 혼잡도 | §2.1, §4.2 |

**시뮬레이터 rev 4 (보정 1개):** 한 줄씩 연산은 묶음의 트랙마다 뉴런 그룹 전체를 다시 읽는다. 그래서 그룹 하나가 슬라이스 이중 버퍼의 한 칸에 모두 들어가야 한다. rev 3은 칸을 512 word로 고정했는데, XL 128·256레인의 층 2 그룹은 768 word다. rev 4는 칸을 `max(512, 가장 큰 그룹)`으로 잡는다(256레인 이중 버퍼 57 → **85.5 타일**). L은 가장 큰 그룹이 384 word라 값이 바뀌지 않는다. 이 보정은 §4.7의 XL 결과 중 보관 없는 저장(B·D) × 한 줄씩의 BRAM을 28.5 타일 적게 잡았던 부분에 해당한다.

### 5.3 저장 축 — 중간보고의 세 정책을 XL 예산에 맞춤

중간보고는 전체 모델 캐시, 모든 모델 부분 상주, 혼합의 세 정책을 **같은 자원 예산으로** 비교하도록 했다. 이 세 정책이 24조합의 저장 축이다. 그런데 XL 256레인에서는 원래 정의로 B·C가 들어가지 않는다(리포트 §4.2).

- B(40모델 층 1 상주): 418~457 타일 > 344.5.
- C(엔트리 LRU + 층 1 상주): 엔트리가 1벌뿐이다. 교체하려면 지금 연산 중인 엔트리에 적재해야 하므로 적재와 연산을 겹칠 수 없다.

그래서 정의는 유지하고 크기만 예산에 맞췄다(`policies.PartialAll`, `PinnedHybrid`). D 스트림(가중치 보관 없음)은 §3에서 추가한 기준점이라 **참고 8조합**으로 함께 돌렸다.

| 저장 | 내용 | 한 번에 | 한 줄씩 |
|---|---|---:|---:|
| A 전체 캐시 | 모델 엔트리 2벌(143.5 타일씩), LRU. 미스면 빈 엔트리에 모델 전체를 적재하므로 연산과 다음 모델 적재가 겹친다 | 288.5 | 335 |

### 5.7 해석 — 축마다 무엇을 바꾸는가

1. **스케줄러가 통과 여부를 가른다.**
   - FCFS·EDF는 저장·연산과 무관하게 위반 100 %다. 묶음이 1.0~1.1이라 요청마다 모델 전체를 가져온다(요청당 408~464 KB, C는 고정 모델 덕에 조금 적음).
   - 그래서 요청당 DMA 사이클이 13,900~15,800으로 연산(2,386)의 약 6배다. DMA가 처리량을 정해 큐가 계속 쌓이고, 평균 처리 시간이 4.8~6.5 s로 발산한다.
   - EDF는 FCFS와 사실상 같다(±0.1 %). 둘 다 기준 요청 뒤로 같은 모델이 이어지는 만큼만 묶기 때문이다.
2. **묶는 스케줄러 안에서는 저장 정책이 지연과 전송량을 맞바꾼다.**
   - A(엔트리 2벌)는 연산하는 동안 다음 모델을 다른 엔트리에 미리 올린다. 그래서 묶음이 차기 전에 바로 시작하고, 평균 7.8~8.5 ms로 가장 짧다.
   - S 몰림 사이클도 2,390~2,490으로 연산만인 2,386에 가깝다. 적재가 거의 다 숨는다는 뜻이고, 이것이 A의 보장값이 가장 큰(1,232) 이유다.
   - 대신 묶음이 작아(5.2~6.6) 요청당 전송이 79~84 KB로 가장 많다.
   - B·C·D는 버퍼가 비기를 기다리는 동안 요청이 쌓여 묶음이 커진다(6.0~11.5). 그래서 전송은 47~77 KB로 줄고 지연은 9.0~13.9 ms로 늘어난다.
3. **부분 상주(B)와 고정 혼합(C)은 XL에서 D와 거의 같다.**
   - 같은 스케줄러·연산 방식이면(실패하는 점수 · 한 번에 제외) B·C·D의 전송 차이는 1.5 KB, 평균 지연 차이는 0.8 ms 이내다. 보장값 차이는 32트랙이다.
   - BRAM 344.5 타일에 들어가는 상주분이 모델의 4 %(B) 또는 1개 모델(C)뿐이기 때문이다.
   - 중간보고의 가설 "부분 상주가 유리하다"는 이 구성(XL · 256레인 · 막전위 DDR3)에서는 **지지되지 않는다.** 다만 C의 인기 모델 고정은 편중 K에서 평균을 줄였다(C · 점수 · 한 줄씩 K 4.7 ms, D 5.9 ms).
4. **연산 방식은 보관 없는 저장(B·C·D)의 통과 여부를 가른다.**
   - 한 번에는 적재 버퍼가 1벌이라 적재와 연산이 번갈아 일어난다. 동시 도착에서 S 몰림 사이클이 약 3,000~3,400으로 커지고, 그룹핑도 S·SK에서 0.1~0.9 % 위반한다.
   - 한 줄씩은 그룹 단위로 미리 받아 모두 통과한다.
   - 한 번에는 가중치 DMA가 묶음당 1회라 접근 횟수(2.09)와 전송(47 KB)이 가장 적다. 접근 횟수만 보면 한 번에가 유리하고 마감은 한 줄씩이 유리하다.
   - A는 엔트리가 버퍼 역할을 겸하므로 두 방식 모두 통과한다.
5. **점수 스케줄러(초안)**
   - A에서는 그룹핑보다 평균이 0.5 ms 짧다.
   - B·C·D · 한 번에에서는 묶음 상한 K = 16 때문에 동시 도착 몰림을 처리하지 못해 53~82 % 위반한다(리포트 §4.2와 같은 원인).
6. **사이클로 보면 XL 1,024트랙은 연산이 아니라 가중치 전송이 묶음 크기를 정한다.**
   - 통과 설계의 DMA 사이클(1,600~2,850)이 연산 2,386과 같은 크기다. 연산 배열은 측정 구간의 62 %를 연산하고 30 %는 가중치를 기다린다(A · 그룹핑).
   - 요청이 계속 도착하는 U·K·I·R에서는 FPGA 안에 대기 요청이 늘 있다. 그래서 연산 배열이 쉬는 시간이 모두 정지로 잡히고, 요청당 (연산 + 정지)는 설계와 무관하게 측정 구간 ÷ 요청 수(U 3,125)가 된다.
   - 남는 시간은 유휴가 아니라 더 작은 묶음, 즉 더 잦은 전송으로 쓰인다. 묶는 스케줄러가 부하에 맞춰 묶음 크기를 스스로 조절하기 때문이다. 설계 차이는 동시 도착의 몰림 처리 사이클에서 드러난다.

### 5.8 판정

- 1,024트랙에서 위반 0인 조합은 24개 중 8개다: A의 묶는 설계 4개, B·C의 한 줄씩 4개. 참고인 D는 그룹핑 · 한 줄씩 1개다.
- §2.2 판정 규칙(모든 시나리오 위반 0 중 BRAM 최소, 같으면 DDR3 전송량 최소)을 그대로 쓰면 다음 순서다.

### 5.9 한계

- 모든 값은 실측 비용 모델을 쓴 **시뮬레이션**이다. 256레인 데이터 경로의 LUT·타이밍, PLIF 갱신 처리량, 막전위 DDR3 지연이 숨는다는 가정, 제어 오버헤드 10 %는 구현으로 확인하지 않았다.
- B·C는 XL 예산에 맞게 다시 정의했다. 원래 정의(층 1 전체 상주, 엔트리 LRU)와는 상주량·교체 방식이 다르다.

- I의 5,328은 연산 기준이다. 큐·메타를 분산 RAM에 두는 구성은 3,888트랙에서 다 찬다(P3.2 fit 비례 추정).
- 점수 스케줄러는 초안(`T_urgent = 4 ms`, `K = 16`) 그대로다.
- 사이클은 100 MHz 연산 배열 기준 시뮬레이션 회계이며, RTL 사이클 시뮬레이션 값이 아니다.

### 5.10 점수 방식 개선 (2026-10-12, 시뮬레이션)

**문제:** §5.6에서 점수 초안(`T_urgent = 4 ms`, 묶음 상한 `K = 16`)은 그룹핑보다 나빴다. 보관 없는 저장 × 한 번에에서 위반 53~82 %, 전 시나리오 최대 트랙 784~1,056(그룹핑 1,008~1,200)이었다.

**원인 진단** (1,024트랙, 시드 0 실행 기록, 진단 스크립트는 남기지 않음):

1. **묶음 상한 16.** 동시 도착(S)에서 모델당 요청이 약 25개 쌓이는데 16개에서 끊는다.
   - 선택의 51 %가 상한에 걸려 묶음이 12.5개(그룹핑 25.6)가 되고, 요청당 전송이 2배(스트림 · 한 줄씩 38.5 KB 대 18.8 KB)가 된다.
   - 적재 버퍼가 1벌인 한 번에서는 묶음 16개마다 163.6 µs 적재가 직렬로 끼어 처리량이 모자란다. 선택의 94~97 %가 긴급 모드에 빠지며 위반 100 %가 된다.
2. **고정 긴급 기준 4 ms.** 남은 일의 양을 보지 않아, 밀리기 시작한 뒤에야 긴급 처리로 넘어간다.
3. **캐시 우선.** 캐시에 있는 모델(전송 0)은 요청이 1개여도 효율이 최대다. 그래서 편중(K)에서 작은 묶음이 늘어 요청당 전송이 그룹핑보다 많아졌다(A · 한 줄씩 84 KB 대 70 KB).

**바꾼 방식** (`policies.py`):

| 이름 | 바꾼 점 |
|---|---|
| 점수(상한 없음) | 초안에서 `K`만 없앰(비교용) |
| **점수2** | ① 묶음 = 그 모델의 준비된 요청 전부(하드웨어 한도만 적용)<br>② 고정 긴급 기준 대신 **마감 가드**: 효율(요청 수 ÷ 묶음 시간)이 가장 큰 모델을 먼저 처리해도, 나머지 모델을 마감 순서(EDF)로 이어서 처리할 때 모든 모델의 가장 이른 마감이 "완료 + 결과 회수 여유" 안에 들면 그 모델을 고른다. 아니면 마감이 가장 이른 모델을 고른다<br>③ 묶음 시간 = 남은 전송 + 막전위 DMA + 연산의 **직렬 합**(보수적). 연산 중인 묶음의 남은 시간부터 센다. 전송 비용은 묶음 시간에 한 번만 들어간다 |
| **점수3** | 점수2 + **마감 여유 안에서 일부러 기다리기**(Channel Window). EDF로 이어서 처리해도 되는 가장 늦은 시작 시각을 구하고, 다음 도착 뒤에도 그 시각까지 여유(slack)가 남으면 기다렸다가 다시 고른다. 같은 모델 요청이 더 모여 묶음이 커진다 |

**조정:** 평가와 겹치지 않는 조정 시드(100~104)로 정했다.

- 겹침 추정(전송과 연산을 max로 봄)은 K·R에서 위반이 나서 버렸다. 직렬 합을 쓴다.
- slack 1~4 ms에서 A와 한 줄씩 B·D는 모두 위반 0이었다. 한 번에는 slack이 클수록 K·R 위반이 줄어 **4 ms**로 정했다.
- 결과 회수 여유 = 호스트 결과 읽기 주기 W_h + C2H 실측 최대 132 µs + 20 µs = **1.15 ms**.

- **점수2 = 그룹핑 + 지연 단축.**

- **점수3 = 전송 절반.**
  - 그룹핑이 통과하는 설계에서 모두 위반 0을 유지한다.

  - 대가는 평균 지연 증가(A 8.5 → 12 ms, +40 %. 한 줄씩 B·C·D +26~30 %)와 최대 응답 31.9 ms다. 마감 여유를 전송 절감에 쓰는 것이다.

- **위험 — 가드 여유가 실제 경로보다 작으면 위반한다** (`p38s_margin_n1024.md`).
  - 스케줄러가 모르는 상태로 호스트 주기가 2 ms가 되거나 PCIe 꼬리가 700 µs 늘면, 점수2는 175~3,149건, 점수3은 1,411~7,615건 위반한다(639만 개 중). 그룹핑은 0건이다. 그룹핑은 여유를 쓰지 않기 때문이다.
  - 같은 조건이라도 가드 여유를 실제 경로(W_h + C2H 최대 + 꼬리)로 맞추면 위반 0이 된다(D · 점수2 · 한 줄씩 꼬리 조건 1건 제외). 점수3의 전송은 32~33 KB로 유지된다.
  - 제어 오버헤드 20 %, DDR3 2.0 GB/s는 스케줄러가 비용 추정에 그대로 반영하므로 위반 0이었다.
  - 따라서 점수 방식은 **결과 회수 경로의 최악 지연을 정확히(보수적으로) 설정해야** 쓸 수 있다. 하드웨어에서는 W_h를 설계값으로 두고, PCIe 최악은 실측 최대(관측 795 µs)를 넣어야 한다.
- **하드웨어 비용(추정):** 결정마다 모델 40개의 (가장 이른 마감, 요청 수, 남은 전송)을 마감 순으로 훑어 누적합과 비교한다. 결정 간격이 수십~수백 µs(수천 사이클 이상)라 순차 FSM으로 충분할 것으로 보지만, RTL로 확인하지 않았다.

**정리:** 처음 점수 방식이 나빴던 이유는 점수식이 아니라 고정 묶음 상한과 고정 긴급 기준이었다. 상한을 없애고 마감 가드로 바꾸면 그룹핑과 같아진다(점수2). 여기에 마감 여유 안의 대기를 더하면, 같은 위반율에서 오프칩 전송을 절반으로 줄인다(점수3). 이것이 중간보고의 "캐시·전송 비용·마감을 반영하는 점수 기반 스케줄링"에 해당하는 결과다. 단 여유를 쓰는 만큼 지연이 늘고, 결과 회수 경로의 최악 지연을 정확히 알아야 한다.

**권고 갱신(확인 필요, §5.11이 다시 대체함):**
- 스케줄러는 그룹핑과 점수3을 런타임 레지스터로 고르게 한다(P4.5).
- 기본은 그룹핑이다(여유가 크고 외란에 강하다).
- 전송·에너지를 줄일 때 점수3을 쓴다. 이때 가드 여유를 W_h + PCIe 실측 최대로 둔다.

### 5.11 문헌 기반 스케줄러 후보 비교 (2026-10-12, 시뮬레이션)

**왜:** §5.10에서 점수2는 그룹핑과 같아졌고, 점수3은 전송을 절반으로 줄였다. 그러나 점수3은 최대 응답이 31.9 ms로 마감에 붙고, 스케줄러가 모르는 PCIe 꼬리 지연에서 위반했다. 시험한 방식도 두 가지뿐이었다. 그래서 선행 문헌의 스케줄링 방식을 우리 문제(모델 전송 비용 + 주기적 하드 마감)에 맞게 옮긴 후보를 더 만들어 같은 조건에서 비교했다.

**문헌에서 가져온 것과 뺀 것**

| 문헌 | 핵심 방식 | 우리 문제에 쓴 방법 |
|---|---|---|
| B03 Sparse-DySta (MICRO 2023) | 점수 = 잔여 처리 시간 + η × 마감 여유가 가장 작은 요청부터. 실행 중 갱신, 선점 억제 항 | **Dysta식**: 모델 묶음 단위로 "요청당 잔여 시간(전송 + 연산 ÷ n) + η × 여유". 선점이 없어 억제 항은 뺐다 |
| B01 Terastal (RTCSA 2026) | 마감을 층별 가상 예산으로 나누고, 최선의 경우 여유로 긴급도를 정함 | 마감 가드의 "결과 회수 여유"(마감에서 입출력 몫을 뺀 연산 몫 예산)로 반영. 별도 후보는 만들지 않음 |
| B02 IsoSched, PREMA(B02가 인용) | 타일·층 단위 선점 | 쓰지 않음. 묶음 중간 막전위·스파이크 상태를 저장해야 하고, 동시 도착 몰림에서는 이득이 없다 |
| B05 FairFirm | (m,k)-firm, 테넌트별 허용 위반 수 | 쓰지 않음. 우리 목표는 위반 0(하드 마감) |
| LazyBatching류 (수집 문헌 밖, 원문 미확인) | 마감 여유가 있으면 묶음을 늦게 시작해 크게 만듦 | **지연 그룹핑**: 순서는 그룹핑(마감 순) 그대로, 마감 가드가 허락하는 만큼만 대기 |
| Triton·Clipper식 동적 배칭 (수집 문헌 밖, 원문 미확인) | 대기 상한 시간(max queue delay) 안에서 묶음을 모음 | **시간제한 묶음 W**: 지연 그룹핑 + 가장 오래된 요청이 W ms 기다리면 시작 |

LazyBatching, Triton, Clipper는 수집 문헌(`documents/papers/`)에 없다. 이 문서의 설명은 일반적으로 알려진 방식 수준이며, 인용하려면 원문을 확보해 확인해야 한다(RELATED_WORK §8 후속 조사).

**해석**

1. **점수3이 외란에 약했던 원인은 기다리기가 아니라 순서 바꾸기였다.**
   - 지연 그룹핑은 점수3과 같은 가드로 기다리지만 순서는 마감 순 그대로 둔다. 그 결과 전송은 더 적고(31 대 36 KB), 최대 응답은 마감에서 더 멀며(28.8 대 31.8 ms), 꼬리 지연에도 위반이 없다.
   - 효율 우선으로 순서를 바꾸면 자주 오는 모델(편중 K의 상위 모델, 캐시 적중 모델)을 자주 처리해 그 모델들의 묶음이 작아진다. 동시에 나머지 모델은 가드의 경계까지 밀린다. 마감 순 그대로 기다리면 모든 모델이 고르게 모여 묶음이 커진다(평균 18.9 대 13.4).
2. **순서를 바꾸는 점수식(Dysta식·점수2)은 평균 지연을 5~8 % 줄이는 데 그친다.** 전송은 오히려 1~4 % 늘고, 가드가 없거나(Dysta식) 경계까지 쓰므로(점수2) 외란에 위반한다. 모든 트랙의 마감이 32 ms로 같은 이 문제에서는 마감 순(그룹핑)이 이미 좋은 순서다.
3. **점수가 값을 내는 곳은 "어느 모델을 먼저"가 아니라 "언제 시작해 얼마나 모을지"다.** 마감 여유를 남은 전송·연산 시간으로 계산해 시작 시각을 늦추면, 같은 위반율에서 전송이 절반 이하가 된다. 이것이 중간보고의 "Channel Window: 배치 길이를 다른 요청의 마감 여유와 전송·연산 비용으로 제한"을 그대로 구현한 형태다.
4. **간이 가드도 충분히 강하다.** 합계 하나로 보수적으로 잡아도 전송이 A −49 %, D −38 %이고, 최대 응답·p99가 그룹핑과 같다(대기가 일찍 끝나 여유가 남음). 정렬이 필요 없어 하드웨어가 가장 싸다.
5. **트레이드오프:** 평균 지연(그룹핑 8.5 → 간이 11.3 → 지연 14.0 ms)과 전송(78.8 → 40.2 → 31.0 KB)이 맞바뀐다. 마감은 32 ms로 같고 p99·최대는 거의 같으므로, 평균 지연이 요구사항이 아니라면 대기형이 우세하다.

- 스케줄러는 런타임 레지스터로 다음 셋을 고르게 한다.
  - **지연 그룹핑(간이 가드)**: 기본. 전송 −38~49 %, 위반·최대 응답·외란 강건성은 그룹핑과 같다.
  - **지연 그룹핑(마감 순 누적합 가드)**: 전송 최소. −52~61 %, 최대 응답 +0~1.6 ms.

### 5.12 최종 비교 대상과 구현 선택 (2026-10-12, 시뮬레이션)

| 선행연구 | Dysta | 요청당 남은 처리 시간 + η × 마감 여유가 가장 작은 모델부터(η = 0.01) | Sparse-DySta (B03, MICRO 2023) |
| | Timeout | 가장 오래된 요청이 FPGA에 도착한 지 W가 될 때까지 기다린 뒤 Grouping. **마감 가드 없음** | 동적 배칭의 대기 상한(Triton max queue delay·Clipper류, 수집 문헌 밖) |
| 제안 | SlackBatch-Lite | Grouping 순서 + 마감 여유 안에서 대기. 가장 늦은 시작 시각을 합계 하나로 보수적으로 계산 | 이 연구 |
| | **SlackBatch** (구현) | Grouping 순서 + 마감 여유 안에서 대기. 가장 늦은 시작 시각을 모델별 마감 순 누적합으로 계산 | 이 연구 |

- §5.11의 "시간제한 묶음"은 대기 상한에 우리 마감 가드를 붙인 혼합형이라 선행연구 비교 대상에서 뺐다. 선행연구 Timeout은 가드 없는 원래 형태로 다시 구현했다(`policies.Timeout`).
- Timeout의 W는 선행연구에 가장 유리하게, 설계마다 조정 시드(100~104)에서 위반 0인 가장 큰 값으로 정했다: A 5 ms, D 2 ms(`target_exp.FINAL_TIMEOUT_W`).
- 조정 시드에서 W = 6~8 ms는 동시 도착(S·SK)에서 위반했다. 몰림 전체가 W만큼 늦게 시작하기 때문이다.
- 점수 초안·점수2·점수3, 시간제한 묶음, 강건 변형은 기록으로만 남긴다(§5.10~5.11).

**해석**

1. **선행연구 두 방식은 우리 문제에서 한계가 분명하다.**
   - Dysta는 처리 순서만 바꾼다. 평균 지연이 6 % 줄 뿐이고 전송은 그대로이며, 마감 가드가 없어 DDR3가 느려지면 위반한다.
   - Timeout은 고정 대기 상한이라, 몰림(동시 도착)에서도 W만큼 늦게 시작한다. 그래서 W를 작게(2~5 ms) 둘 수밖에 없고 전송 절감이 3~13 %에 그친다. 그 W조차 평가 시드나 외란에서 마감을 넘는다.
2. **제안 방식은 대기 시간을 고정하지 않고 남은 일(전송 + 연산)과 마감 여유로 정한다.**
   - 몰림에서는 기다리지 않고, 한산할 때는 오래 기다린다.
   - 그래서 Grouping과 같은 위반율(0), 최대 트랙, 외란 강건성을 유지하면서 오프칩 전송과 동적 에너지를 절반 이하로 줄인다. SlackBatch는 전송 −61 %, 에너지 −58 %다.
3. **대가는 평균 지연이다**(Grouping 8.5 → SlackBatch 14.0 ms). 마감 안의 여유를 전송 절감에 쓰는 것이다. 최대 응답은 외란 최악에서 29.8 ms로 마감 안이다.

**구현 선택: SlackBatch**
- 전송·에너지가 가장 적고 외란 5조건에서 위반이 없다.
- 하드웨어(추정, RTL 미확인)는 다음과 같다.
  - 모든 트랙의 마감이 "생성 + 32 ms"로 같으므로, 마감 순서가 곧 "요청이 먼저 쌓이기 시작한 모델 순서"다. 정렬기 없이 모델 FIFO(최대 40칸)로 순서를 유지한다.
  - 표의 각 칸에는 가장 오래된 요청 시각, 쌓인 요청 수, 캐시 여부가 들어간다.
  - 결정마다 표를 앞에서부터 훑으며 "묶음 시간 누적 ≤ 각 모델의 마감 − 회수 여유"를 확인한다. 약 40~80사이클이다.
  - 한 줄씩 연산에서 묶음 한도(64)를 넘어 남은 요청이 있으면 그 모델은 FIFO 앞에 남겨야 한다.
- SlackBatch-Lite는 같은 블록에서 누계 비교만 쓰는 형태라, 같은 하드웨어에 모드로 넣을 수 있다.
- 비교 실험(P6.1)은 위 7개를 런타임 레지스터로 전환한다. FCFS·EDF·Grouping·Timeout은 SlackBatch 블록의 대기 규칙을 끄거나 고정 W로 바꾸면 되고, Dysta는 점수 계산이 따로 필요하다.

이전 그림 14~17은 최종 비교 대상 정리 전의 그림이라 `sim_result/figures/discarded/`로 옮겼다(`plot_target.py --old`로 다시 그림).
